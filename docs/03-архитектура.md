# 03. Архитектура

Статус: v0.2, 2026-10-21 (v0.1 — 2026-10-09). Решения, помеченные [ДОПУЩЕНИЕ], заменимы до начала реализации (этап 05-SDD). Изменение v0.2: внешний сервис обогащения КБ `kb-enrichment` (docs/15).

## 1. Принципы

1. **Клинический движок = чистый SDK** (ядро без I/O). Вся клиническая логика (шкалы, скоринг, триаж, эскалации, генерация чек-инов) — чистые функции/структуры. Это: (а) максимальная тестируемость (TDD-полигон), (б) бело-брендовый актив для Авинейро — «переиспользуемый движок», (в) переносимость без переписывания.
2. **Порты и адаптеры**: ядро не знает про HTTP/БД/внешние сервисы. API-слой — тонкий адаптер.
3. **Внешние подсистемы (LLM-чат, TTS) — за SPI**, по умолчанию mock-и: демо работает офлайн, нет утечек ПДн в сторонние API.
4. **152-ФЗ конфигурацией**: согласие обязательно; без согласия — только демо-режим без персональных данных. Никакой логики «на усмотрение UI».
5. **Аудит append-only** на уровне БД-инварианта + сервиса.
6. **Демо-истина**: всё, что показываем жюри (дашборд, тренды, эскалации), работает на симуляторе данных реалистичной динамики.
7. Контракты фиксируются до реализации (SDD), реализация — только под красные тесты (TDD).

## 4. Модули ядра (SDK) — контрактная поверхность

```python

class Scale: code, title, items, scoring (пороги severity)
class ScaleResult: total_score, severity, per_item

# core/scoring.py
def score(scale: Scale, answers: dict[str, int]) -> ScaleResult          # чистая
def triage(result: ScaleResult, context) -> Triage                       # GREEN|YELLOW|RED

# core/checkin.py
def plan(answers: Mapping[str, int]) -> CheckinPlan                     # ядро + модули по правилам, ≤12 пунктов
def safety_level(answers: Mapping[str, int]) -> str                     # none|review|signal|unassessed

# core/trend.py
def trends(runs: Sequence[ScaleResult]) -> Trend                          # скользящее среднее, дельта 7/30 дней
```

Детальные сигнатуры и таблицы порогов — в 05-SDD (дизайн) и 06-TDD (тесты). Пороги PHQ-9/GAD-7/HADS — по официальным руководствам, подтверждаются медиком команды.

## 6. Сервисные инварианты (проверяются тестами интеграции)

- Ответы принимаются только в открытом `questionnaire_run`; после `/finish` run закрыт (апдейты — 409 CONFLICT).
- `assessment` вычисляется сервером (ядро), клиент не передаёт баллы.
- Чтение медданных пациента — только врач из `clinician_roster` (проверка в сервисе, не в UI).
- Эскалация RED: при `finish` сервер создаёт запись `escalation` (kind SUICIDAL|SEVERE) и возвращает `help_resources` в ответе клиенту — атомарно в той же транзакции, фиксируется в `audit_log`; канал оповещения врача — внутрисистемное событие (clinician panel shows new escalation), а не DB-триггер. Целевая метрика `<1 с` измеряется от момента `POST /runs/{id}/finish` до коммита транзакции и появления карточки escalation в UI врача.
- Все обращения к спецкатегориям пишутся в `audit_log` (append-only), включая чтения по roster.
- Без активного согласия PATIENT не может создавать персональные данные (только демо-объекты с флагом `is_demo`).
- Клинические сессии (FR-38/39): доступ — roster + активное согласие пациента, `patient_id` берётся из БД сессии (IDOR), протокол правится только в `draft` (409 `PROTOCOL_LOCKED`), `approve` требует обязательные разделы §5.2 (409 `PROTOCOL_NOT_READY`), завершение сессии идемпотентно создаёт один `visits` по `session_id`; артефакты (аудио/расшифровка/PDF) — только шифротекст на диске (AES-256-GCM, `document_artifacts`), аудит `APPOINTMENT_*`/`SESSION_*`.

## 7. Развёртывание (демо и пилот)

- docker compose: `postgres` + `qdrant` + `api` + `kb-seed` + `kb-enrichment` + `ui` (nginx: статика + reverse proxy; TLS 1.2+ терминирует nginx, на демо — за localhost, на пилоте — сертификат Let's Encrypt) + `seed` (одноразовый генератор симуляции).
- `kb-enrichment` — отдельный контейнер (`infra/docker-compose.yml`) с тем же образом, что `api`: цикл прогонов по `CC_ENRICH_INTERVAL_HOURS`, advisory-lock Postgres `hashtext('kb-enrichment')` против параллельных прогонов; схема — миграция `c1d2e3f4a5b6` (применяется lifespan API под advisory-локом, §12). Исходящий трафик в PubMed/IRIS есть только у этого контейнера (docs/15 §11).
- Резервирование: `pg_dump` daily (крипт. том), retention 30 d + weekly 12 mo — чек-лист включён в демо-прогон.
- Хостинг: РФ (Яндекс/VK Cloud) или on-prem вуза [ДОПУЩЕНИЕ, 152-ФЗ ст. 12 — без трансграничной передачи].
- Секреты: продакшн-ключи — `.env`/env/KMS (вне git), пароли argon2, ротация JWT-ключа. Демо (docker-compose, `infra/docker-compose.yml`) — исключительно фиксированные демо-секреты (`POSTGRES_PASSWORD=compass`, `CC_JWT_SECRET=demo-jwt-secret-…`, `Demo-Pass-1`, `CC_DEMO_TOTP=JBSWY3DPEHPK3PXP`), они не валидны вне локального демо.

## 12. Async-рантайм API (2026-10)

API исполняется на одном event loop на процесс, БД — через async-драйвер
(`postgresql+psycopg` + `AsyncSession`). Границы, которые нельзя размывать:

- **Request-path — только async.** `get_db()` выдаёт одну `AsyncSession` на
  запрос и в `finally` (под `anyio.CancelScope(shield=True)`) откатывает
  незакоммиченную транзакцию и закрывает сессию: отмена запроса клиентом не
  оставляет соединение занятым.
- **Синхронные библиотеки — только в потоке.** Qdrant-клиент, эмбеддер
  (torch), LLM-роутер (urllib), pywebpush, FCM и argon2id вызываются через
  `anyio.to_thread.run_sync` / `asyncio.to_thread`; иначе один запрос
  блокирует весь процесс (argon2 — десятки мс и 64 МиБ на логин).
- **Alembic — не в loop и не параллельно.** `init_db()` (upgrade head +
  триггер аудита) выполняется в потоке и под `pg_advisory_lock(hashtext(
  'cc_alembic_migrations'))`: при `uvicorn --workers N` воркеры не гоняются
  за одни и те же DDL, второй дожидается первого.
- **Соединения считаются как бюджет.** `db.validate_pool_budget()` на старте
  складывает `WEB_CONCURRENCY × (CC_DB_POOL_SIZE + CC_DB_MAX_OVERFLOW + 2)` и
  `CC_DB_BACKGROUND_PROCESSES × (CC_DB_BG_POOL_SIZE + CC_DB_BG_MAX_OVERFLOW + 2)`
  и падает, если сумма больше `CC_DB_MAX_CONNECTIONS`. Фоновые сервисы
  (`reminders-worker`, `kb-enrichment`) работают с маленьким пулом
  (`profile="background"`). Синхронный движок (alembic/seed/CLI) живёт на
  `NullPool` и соединений не удерживает.
- **Исчерпание пула — это 503.** `sqlalchemy.exc.TimeoutError` маппится в
  `503 DB_UNAVAILABLE` с `Retry-After: 2`, а не в 500.
- **Shutdown закрывает пулы.** Lifespan в `finally` делает
  `await engine.dispose()` и `sync_engine.dispose()`; воркер напоминаний
  закрывает свой async-движок.
- **Кеш корпуса KB — per-process.** `build_corpus()` кешируется на
  `CC_KB_CORPUS_TTL_SECONDS` (снимок неизменяем, сборка вне лока);
  персональные исключения врача применяются ПОСЛЕ кеша и в него не попадают.
- **Агент — под своим лимитером и дедлайном.** RAG-прогон
  (`AgentFactory.invoke`) блокирующий, поэтому уходит в поток, но под
  `AGENT_LIMITER` с потолком `CC_ASSISTANT_THREAD_LIMIT` (по умолчанию 8
  одновременных прогонов на процесс), а не под общим пулом AnyIO: всплеск
  запросов ассистента ждёт на лимитере, а остальные `to_thread`-задачи (push,
  эмбеддинги, Qdrant) продолжают получать потоки. Весь прогон (ожидание
  лимитера + retrieval + LLM) ограничен `CC_ASSISTANT_DEADLINE_S` (по умолчанию
  60 с); по истечении — `503 ASSISTANT_TIMEOUT` с `Retry-After: 5`, ответ
  ассистента в тред не пишется (вопрос врача персистируется до вызова агента).
  Поток при отмене бросается (`abandon_on_cancel`): иначе `run_sync` дожидается
  его конца и дедлайн не срабатывает; брошенный прогон держит токен лимитера
  до возврата агента.
- **Ответ пишет LLM, но только по сниппетам.** Узел `answer` графа
  (`AgentFactory._answer`) при заданном `CC_ASSISTANT_LLM_URL` вызывает
  `llm_router.compose_answer` в том же рабочем потоке агента (в event loop
  urllib не попадает): на вход — деперсонализированный вопрос, история треда
  (≤8 реплик × ≤800 символов) и пронумерованные найденные фрагменты, карта
  пациента не передаётся. Сервер проверяет ссылки `[n]` (≥1 валидная, ≤3, без
  дублей по `guideline_id`) и строит `citations` только из реальных чанков;
  пустой ответ, таймаут (`CC_ASSISTANT_LLM_ANSWER_TIMEOUT`), ошибка HTTP или
  отсутствие валидных ссылок → детерминированный `build_rag_answer`. Отказы
  (red line) и запросы «только по карте пациента» до LLM не доходят.
- **Реранк — синхронный torch в том же потоке.** `CC_RERANKER` (кросс-энкодер,
  docs/08 §4) считается внутри `AgentFactory.search_kb`, т.е. в том же
  `to_thread`, что Qdrant и эмбеддер; в event loop он не попадает. Модель —
  процессный синглтон (`app.services.reranker.get_reranker`), грузится лениво
  при первом поиске; недоступность весов/пакета деградирует к порядку RRF с
  warning в лог, запрос не падает.
- **Rate limiter логина — общий счётчик в Redis.** `app.ratelimit` считает
  неудачные попытки по паре (IP, email) и по IP. При заданном `CC_REDIS_URL`
  (сервис `redis` в compose) запись идёт в общее хранилище: `INCR` + `EXPIRE`
  на ключ фиксированного окна (номер окна — в ключе, TTL = 2 окна), ключи —
  HMAC-SHA256 с серверным `CC_DATA_KEY` от (IP, email)/IP, без открытых ПДн:
  голый `SHA-256(ip)` перебирается по пространству IPv4 за минуты, поэтому
  дайджест ключуется секретом. Поэтому `uvicorn --workers N` и
  все реплики api тратят ОДИН бюджет `CC_RATE_MAX`. Режим фиксируется на старте
  (`CC_RATE_BACKEND=auto|memory|redis`, PING Redis): без URL, без extra
  `api[redis]` или при недоступном Redis — memory с WARNING. Ошибка Redis в
  рантайме — fail-open в memory (счётчик `redis_errors` + WARNING), а короткий
  `CC_RATE_REDIS_TIMEOUT` (0.3 с, без ретраев) не даёт логину зависнуть.
  В redis-режиме сетевой ввод-вывод лимитера уходит в рабочий поток
  (`acheck_rate`/`arecord_rate_hit`, как argon2) — event loop не блокируется;
  активное хранилище и число отказов видны в `GET /health`
  (`rate_limit.backend`, `rate_limit.redis_errors`).

- **ML-сайдкар — один внутренний HTTP-хоп.** Эмбеддинги/реранк/маскирование
  идут в GPU-сервис `ml` (`http://ml:8080` в выделенной внутренней сети
  `mlnet`, docs/08 §4) синхронным клиентом, уведённым в рабочий поток;
  таймаут — `CC_ML_TIMEOUT` (5 с), ровно один повтор только на сетевой
  сбой/5xx. `mlnet` объявлена с `internal: true`: у `ml` нет egress и он не
  видит postgres/qdrant/redis; к `default` и `mlnet` подключены `api`,
  `kb-seed` и `kb-enrichment` (сид и обогащение эмбеддят тем же профилем).
  Веса качает одноразовый `ml-warmup` (единственный контейнер с egress),
  после чего `ml` работает с `HF_HUB_OFFLINE=1` и не пишет ПДн на диск
  (docs/10). Без `CC_ML_TOKEN` сайдкар не стартует (fail-closed). Отказные
  режимы: 503 `model_loading`/`model_unavailable` во время загрузки моделей
  → `MlUnavailable` у клиента; поиск/реранк деградируют к локальному пути,
  маскирование ПДн в прод-режиме — fail-closed, в том числе при
  `degraded=true` в ответе сайдкара (docs/12). Сеть `mlnet` считается
  доверенной, доступ в неё есть только у api и ml.

Ограничения: в режиме memory (без Redis) словари пар (IP, email) и IP
ограничены `_MAX_KEYS`, чтобы перебор не рос в памяти (`CC_RATE_IP_MAX`
закрывает перебор разных email с одного адреса), но бюджет остаётся
per-process — при `WEB_CONCURRENCY > 1` допустимо до `N × CC_RATE_MAX` попыток,
а рестарт обнуляет окно; для прода с N>1 или несколькими репликами нужен
`CC_REDIS_URL` (docs/10 R24). В Redis окно фиксированное: на стыке окон
допустим всплеск до `2 × CC_RATE_MAX` (в памяти — скользящее). Потоковый пул
AnyIO ограничен дефолтом (40 потоков на процесс), поэтому `to_thread`-работа
вне ассистента при пике стоит в очереди к потокам; лимитер и дедлайн
ассистента — per-process, при `WEB_CONCURRENCY > 1` общий потолок прогонов
умножается на число воркеров.
- **Egress в LLM — fail-closed по ПДн.** Весь исходящий текст (`/assistant/*`,
  FR-31 `chat_insights`) проходит деперсонализацию: структурные правила +
  контрольные числа + ML-маскирование (`hybrid` локально или `remote` через
  ML-сайдкар `/v1/mask`) + deny-list ростра. В `CC_PROD_MODE` с настроенным
  LLM-egress backend обязателен, а его недоступность (модель не загрузилась,
  сайдкар не ответил) даёт `503 DEPERSONALIZATION_UNAVAILABLE` — сырой текст не
  уходит. Вне prod допустима деградация до regex с логом (docs/10 R25, docs/12).
- **Тяжёлые списки ограничены, связанные сущности — батчем.** Очереди НЯ
  (`/clinician/adverse-events`, `/me/adverse-events`), история приёмов и
  уведомления отдают не больше `limit` строк (1..200, по умолчанию 100/50), а
  названия назначений и справочник ГРЛС для НЯ подтягиваются двумя запросами
  на весь список, не на строку; карточка пациента собирает «последнюю»,
  «историю» и 90-дневный тренд одним запросом с `LIMIT` вместо всей истории.
- **Карточка врача не везёт каталог шкал и не считает лишних запросов.** Каталог
  (`GET /clinician/scales`, 7 шкал с текстами и anchors) вынесен из `report`:
  ответ карточки ужался с 23 404 до 1 231 байта на том же пациенте. Замер
  `before_cursor_execute` через ASGI: было 12 SQL (пациент без НЯ) и 13 (с НЯ),
  стало 11 и 11 — анамнез читается LEFT JOIN в первом запросе карточки
  (`PatientAnamnesis.patient_id` unique, строк 0..1), НЯ — одним джойном с
  назначением и ГРЛС. До 8 счёт не опускается: `diary`, `escalations`,
  `checkins`, `adherence`, `chat_insights` — списки с `EncryptedText`, их
  свёртка требует `json_agg` + ручного `pgp_sym_decrypt`, то есть дублирования
  слоя шифрования; плюс `auth`-SELECT и обязательный `READ_REPORT` INSERT.

## 13. Сид демо-данных: идемпотентность и запрет на разрушение при деплое

`python -m app.seed` **идемпотентен**: учётки и пациенты ищутся по email
(get-or-create), существующие не пересоздаются, их пароль/TOTP не
перезаписываются, история скринингов и дневник не дублируются, роспись
дозаполняется `ON CONFLICT DO NOTHING`. Разрушающий режим — только явный
`--reset` (TRUNCATE всех таблиц), и он остаётся ручной операцией.

Причина правила: `infra/docker-compose.yml` содержит one-shot сервисы
`seed` и `kb-seed`. Пока они жили в базовом наборе, любой `docker compose up`
пересоздавал их (compose поднимает и уже завершившиеся one-shot контейнеры), а
`seed` тогда запускался с `--reset` — каждый такой деплой обнулял демо-данные
**и реестр КБ** (`kb_works`, `kb_work_approvals`), и восстановление требовало
повторного обогащения и повторных одобрений статей. Поэтому:

- `seed` и `kb-seed` вынесены в **профиль `seed`**: обычный `up` их не трогает;
- `seed` в compose стартует без `--reset`;
- `kb-seed` стартует без `--reset` (идемпотентный upsert по `text_hash`);
- `ui` и `kb-enrichment` больше не зависят от one-shot сервисов, иначе профильный
  сервис нельзя было бы выключить обычным `up`;
- сброс — вручную: `docker exec infra-api-1 /app/.venv/bin/python -m app.seed --reset --patients 12`.

Отсюда три разные команды:

```
# обычный деплой/обновление кода — сид не перезапускается
docker compose -f docker-compose.yml -f docker-compose.dev.yml \
  --profile gpu up -d --build api ui reminders-worker kb-enrichment

# первый запуск с нуля (или осознанное дозаполнение демо-данных и индекса КБ)
# те же -f, что у обычного деплоя: без dev-override compose поднимет
# одноразовые контейнеры в другом проекте
docker compose -f docker-compose.yml -f docker-compose.dev.yml \
  --profile seed up -d seed kb-seed

# изменился код сида/индексатора — у них свои образы, их надо пересобрать
docker compose -f docker-compose.yml -f docker-compose.dev.yml \
  --profile seed up -d --build seed kb-seed

# ручной разрушающий сброс демо-данных — только осознанно, не при деплое
docker exec infra-api-1 /app/.venv/bin/python -m app.seed --reset --patients 12
```

Проверено эмпирически: после `--profile seed up -d` обычный
`up -d --build api ui` не меняет `StartedAt` у `seed`/`kb-seed` и не пишет
новых строк в БД.

Восстановление реестра КБ после потери: `python -m app.enrichment run`
(гайдлайны с открытой лицензией публикуются сами, статьи — кандидаты на
персональное ревью врача), либо `python -m app.enrichment reindex` при целом
реестре, либо `tools/rechunk_collection.py` при целом индексе (docs/15 §11).

Флаги функций доходят до контейнера только если `infra/docker-compose.yml`
их пробрасывает: значение в `infra/.env` без строки `environment` в compose
не действует. Так было с `CC_SESSION_AI_ENABLED` (FR-38…FR-44): ИИ-блок
приёма — запись, расшифровка, черновик протокола, диалог по сессии — было
невозможно включить в compose-деплое, карточка всегда показывала «выключен
администратором». Сейчас api получает `CC_SESSION_AI_ENABLED`,
`CC_SESSION_AI_AUTODRAFT`, `CC_SESSION_AI_TIMEOUT`, `CC_SESSION_AI_SOURCES`,
`CC_SESSION_AUDIO_MAX_MB`, а также границы диалога по сессии
`CC_SESSION_CHAT_MESSAGE_CHARS`, `CC_SESSION_CHAT_HISTORY`,
`CC_SESSION_CHAT_MAX_TURNS`, `CC_SESSION_CHAT_SOURCES`; включать — осознанно:
нужны `CC_ML_URL` (сайдкар) и `CC_ASSISTANT_LLM_URL`, иначе кнопки
записи/расшифровки вернут ошибку, а не сработают.

## 14. dev-stage: постоянный контур интеграционных тестов

Интеграционные прогоны (api-тесты и Playwright) идут в стенде
`tools/dev-stage.sh` — отдельный compose-проект `cc-dev-stage` из тех же
сервисов, что и прод (`postgres`, `qdrant`, `redis`, `api`, `ui`,
`reminders-worker`, `kb-enrichment`), но со своими контейнерами, томами и
портами. Публикация только на loopback: Postgres `127.0.0.1:55432`, Qdrant
`127.0.0.1:56333`, UI `127.0.0.1:8097` (`CC_STAGE_PG_PORT` /
`CC_STAGE_QDRANT_PORT` / `CC_STAGE_UI_PORT`). Туннель на стенд не настраивается,
рабочие Postgres `:5432` (база `compass`) и Qdrant `:6333` (`kb`, `kb_600`)
стенду недостижимы; собственный скрипт отказывается стартовать при попытке
указать эти порты или имена `compass`/`kb`.

Две базы в одном контейнере стенда: `compass` — данные стека (демо-сид,
e2e), `compass_test` — цель `api/tests` (фикстура дропает схему, поэтому
стековые данные не страдают). Коллекции: `kb_stage` для стека и `kb_test` для
api-тестов.

Стенд **постоянный**, в отличие от прежнего одноразового `cci`:

- контейнеры и тома переживают прогоны (`down` без `-v`), поэтому Postgres
  не инициализируется заново, а демо-данные и индекс КБ сохраняются;
- образы пересобираются только при изменении кода — отпечаток
  `.stage/images.sha` считается по `git ls-files -s` и `git status` для
  `api`, `core`, `ui`, `ml`, `pyproject.toml`, `uv.lock`, `infra`;
- демо-сид и индексация КБ выполняются только при изменении своих входов
  (`.stage/kb.sha`: источники корпуса `api/app/kb_seed.py`, `api/app/data`,
  `api/app/enrichment`, `core/compass`, а также `CC_EMBEDDER`,
  `CC_KB_CHUNK_CHARS`, `CC_KB_CHUNK_OVERLAP`, имя коллекции) или если
  коллекция пуста. `tools/dev-stage.sh seed` переиндексирует принудительно;
- `.stage/` в `.gitignore`: это локальное состояние стенда, не репозиторий.

Команды и ворота: `tools/dev-stage.sh up|seed|test|status|down|reset`;
`tools/ci.sh` использует стенд для api-тестов и e2e вместо собственных
одноразовых контуров (`--data` поднимает только postgres/qdrant/redis, что
достаточно для api-тестов).

Внешние интеграции: стенд запускает моки профиля `emias` (`emias-mock`,
`remd-mock`) и включает их у api — `CC_EMIAS_ENABLED=true`,
`CC_EMIAS_ALLOW_INSECURE=true` (мок по http внутри сети), `CC_REMD_ENABLED=true`.
Без этого e2e-спека протокола приёма (docs/18, FR-39…FR-41) доходит до
подписи и PDF, но не до регистрации в РЭМД, и падает на ожидании бейджа
«зарегистрирован в РЭМД». Порты моков на хост не публикуются: egress наружу
не открывается. `.github/workflows/ci.yml` поднимает стек с теми же
профилями (`--profile seed --profile emias`) и теми же `CC_*`, чтобы GH-прогон
и локальный стенд проверяли одно и то же.

Ограничение: стенд не изолирует данные между прогонами — e2e-спеки опираются
на собственные создаваемые сущности, но накопленное состояние (эскалации,
напоминания, треды) остаётся. Детерминированный сброс — `tools/dev-stage.sh
reset` (сносит тома) либо `seed` (идемпотентный, без `--reset`).

## 15. Почта и коды подтверждения (FR-48)

Один канал на два сценария: сброс пароля и (по флагу) подтверждение входа
пациента. Зависимостей не добавлено — `api/app/services/mailer.py` работает
через stdlib `smtplib`, а отправка уходит в рабочий поток
(`anyio.to_thread.run_sync`): SMTP-таймаут не блокирует event loop API.

Настройки (любая пустая → канал не настроен): `CC_SMTP_HOST`,
`CC_SMTP_PORT` (587), `CC_SMTP_USER`, `CC_SMTP_PASSWORD`, `CC_SMTP_FROM`,
`CC_SMTP_TLS` (STARTTLS, true). Без канала поведение детерминировано, но
демо-режим требует явного согласия:

- код в ответе (`demo_code`) отдаётся только при `CC_MAIL_DEMO_CODES=true` и
  не `CC_PROD_MODE`; один WARNING в журнал на процесс; так работают локальные
  стенды и e2e без почтового сервера. Одного `CC_ALLOW_DEMO_SECRETS` **не
  достаточно**: публичный демо-контур стартует с этим флагом (демо-JWT), и
  ответ с кодом означал бы сброс пароля любого известного аккаунта по одному
  HTTP-запросу;
- во всех остальных случаях (прод, публичный контур без SMTP) — 503
  `MAIL_UNAVAILABLE`: код не уходит в HTTP-ответ, и ручка не притворяется
  рабочей. Проверка канала идёт до выборки пользователя, поэтому статус
  одинаков для любого адреса.

Если канал настроен, письмо сброса уходит **после** ответа
(`BackgroundTasks`): латентность `POST /auth/password/reset-request` не
зависит от SMTP, ответ остаётся 202 `{sent: true}` даже при отказе релея, а
сбой виден только в журнале (WARNING без адреса и кода) и в аудите
`PASSWORD_RESET_DELIVERY_FAILED` (только id пользователя). Для входа по коду
(`/auth/login`) доставка синхронная: пароль уже проверен, поэтому 503
`MAIL_UNAVAILABLE` там не перечисляет аккаунты.

Коды живут в таблице `auth_codes` (`user_id` → `users.id` ON DELETE CASCADE,
`purpose reset|login`, `code_hash`, `attempts`, `expires_at`, `consumed_at`,
`created_at`; индекс `(user_id, purpose, created_at desc)`). В БД только
`SHA-256(code + CC_DATA_KEY)` — как в rate limiter: dump не даёт действующих
кодов, в логах и аудите нет ни кода, ни адреса (только id пользователя).
TTL — 10 минут, бюджет — 5 проверок, повторная отправка — не чаще раза в
60 секунд (429 `CODE_COOLDOWN`). Счётчик паузы живёт в памяти процесса и
ключуется `(IP, e-mail)` одинаково для существующего и несуществующего
адреса, поэтому пауза не выдаёт наличие аккаунта; сброс дополнительно
ограничен общим `acheck_rate`/`arecord_rate_hit` на `(IP, e-mail)`.

`POST /auth/password/reset-request` отвечает 202 `{sent: true}` для любого
адреса и для несуществующего ничего не пишет в БД. `POST /auth/password/reset`
меняет argon2-хеш, удаляет все `refresh_tokens` пользователя (старые сессии
получают 401) и остальные невыкупленные коды сброса; любая причина отказа —
422 `CODE_INVALID` без подсказок. При `CC_EMAIL_OTP=true` пароль пациента
верный, но токенов нет: `POST /auth/login` → 202
`{otp_required:"email", challenge, demo_code?}`, а пару токенов выдаёт
`POST /auth/login/otp {challenge, code}` — те же поля и httpOnly cookies, что
у обычного входа. `demo_code` тут подчиняется тому же правилу, что и сброс:
только при `CC_MAIL_DEMO_CODES=true` и не `CC_PROD_MODE`; без канала и без
флага ручка отвечает 503 `MAIL_UNAVAILABLE`. Сотрудники продолжают входить по
TOTP (`CC_REQUIRE_OTP`).

UI входа — настоящие формы (`<form onSubmit>`): Enter отправляет шаг с
введёнными значениями, первое пустое поле получает фокус, кнопка блокируется
на время запроса, текст ошибки берётся из `detail` сервера как есть. Шаги:
вход, регистрация, код из письма, «Забыли пароль?» → e-mail → код + новый
пароль. Состояние шага — в компоненте `App`, токены — как раньше (cookies
в web).

### 15.1 Подтверждение адреса при регистрации (мягкое)

Регистрация сразу создаёт учётную запись и выдаёт сессию: подтверждение адреса
— **метка, а не ворота**. `users.email_verified_at` (NULL — не подтверждён)
показывается баннером `<EmailVerifyBanner>` в оболочке `App` — и пациенту, и
врачу. Блокировки входа нет осознанно: опечатка в адресе иначе отрезала бы
человека от собственных данных, а единственным владельцем адреса всё равно
остаётся он сам.

- `purpose = "verify"` в `auth_codes` (тот же TTL, бюджет попыток и хеш).
- `POST /auth/register` при настроенном SMTP выпускает код и отправляет письмо
  «Подтверждение адреса» через `BackgroundTasks`; сбой SMTP регистрацию не
  отменяет (в аудит уходит `EMAIL_VERIFY_DELIVERY_FAILED`). Без канала код не
  выпускается вовсе — не плодим строки, которые некому увидеть.
- `GET /auth/me` → `{id, email, role, email_verified}`; `GET /auth/config`
  дополнительно отдаёт `mail: bool` — интерфейс не показывает баннер там, где
  письма физически не уходят (стенды, e2e).
- `POST /auth/email/verify/request` → 202, пауза 60 с (429 `CODE_COOLDOWN`),
  409 `EMAIL_ALREADY_VERIFIED`. Отправку роут ждёт: `{sent:true}` — письмо
  принято SMTP, отказ провайдера — 202 `{sent:false}` с `EMAIL_VERIFY_DELIVERY_FAILED`
  в аудите. Недоставленный код не коммитится (иначе ретрай при упавшем канале
  копит строки в `auth_codes` до TTL), пауза при этом не съедается. Без канала
  и без `CC_MAIL_DEMO_CODES` — тоже `{sent:false}` и код не выпускается; на
  стендах письма физически нет, поэтому код отдаётся как `demo_code`.
  Повторное письмо гасит предыдущий код: в ящике не остаётся двух «рабочих».
- `POST /auth/email/verify {code}` → 200 `{email_verified:true}`; неверный,
  истёкший или израсходованный код — 422 `CODE_INVALID`; аудит
  `EMAIL_VERIFIED`/`EMAIL_VERIFY_FAILED` (только id пользователя).
- Бэкфилл миграции: адреса, существовавшие до появления проверки, считаются
  подтверждёнными; демо-учётки `app.seed` создаются подтверждёнными.

Провайдер почты для боевого контура выбирается по доставляемости, а не по
удобству: SMTP-ключ транзакционного сервиса (например, Brevo — 300 писем в
сутки бесплатно, подтверждение одного адреса отправителя, домен не обязателен)
вместо личного ящика. Личный Gmail в этой роли опасен: коды сброса приходят в
тот же ящик, поэтому доступ к нему равен возможности сбросить пароль любому
сотруднику, плюс лимит ~500 писем в сутки и переписанный `From` без DKIM.
Настройки — `CC_SMTP_HOST/PORT/USER/PASSWORD/FROM/TLS`; `From` обязан совпадать
с подтверждённым отправителем у провайдера.

## 16. Приглашение пациента врачом (FR-49)

Админский `/admin/roster` — единственный путь привязки врач→пациент, пока врач
не заведёт карту сам. FR-49 даёт врачу карту **до** появления аккаунта:

1. Врач из раздела «Пациенты» заполняет карту (ФИО, телефон, дата рождения,
   e-mail — опционально). Телефон — ПДн: `EncryptedText` (bytea + pgcrypto).
2. Бэкенд создаёт строку `patient_invites` и возвращает ссылку
   `/invite/<token>` **ровно один раз**. В БД лежит только
   `sha256(token + CC_DATA_KEY)`, поэтому «показать снова» невозможно — есть
   перевыпуск (`INVITE_REISSUE`, старый токен сразу гаснет). Токен — 256 бит
   urlsafe, живёт 7 дней; у одного врача ≤200 непринятых (`INVITE_LIMIT`).
3. Пациент открывает ссылку без входа (страница `InviteAcceptView`,
   роут `/invite/<token>` в `main.tsx` — как `/legal/*`, до `<App/>`): видит
   ФИО и врача, вводит e-mail (если врач не знал) и пароль.
4. Активация (`POST /auth/invite/{token}/accept`) создаёт `users`-строку
   (PATIENT, данные карты переносятся), **автоматически** добавляет
   `clinician_roster` и выдаёт сессию через общий `auth.issue_session`.
   Строка приглашения берётся под `FOR UPDATE` — два параллельных принятия
   одной ссылки невозможны (второе видит `accepted_at` → 410 `INVITE_USED`).

Принятые/просроченные ссылки — 410; неизвестный токен — 404; занятый адрес —
409 `EMAIL_TAKEN` (логин пациента — e-mail, он обязан быть уникальным).
`_destroy_patient_pdn` (отзыв согласия) не трогает `patient_invites`:
принятая строка хранит только `accepted_patient_id` и не содержит текста
согласия; непринятые строки удаляет врач кнопкой «Отозвать».

Почта для этого сценария **не нужна**: ссылку передают любым каналом
(WhatsApp, бумажка в кабинете). Это намеренный обход почтовой зависимости:
FR-48 (e-mail) не является предпосылкой приглашений.

Роуты (все `/api/v1`):

| Роут | Смысл | Доступ |
|---|---|---|
| `POST /clinician/patients/invites` | создать карту+ссылку (201: `{…карта, token, link}`) | CLINICIAN |
| `GET /clinician/patients/invites` | непринятые живой карты (без `token/link`) | CLINICIAN |
| `POST /clinician/patients/invites/{id}/reissue` | новый токен (старый гаснет), 409 `INVITE_ACCEPTED` | CLINICIAN |
| `DELETE /clinician/patients/invites/{id}` | отозвать (204), 409 `INVITE_ACCEPTED` | CLINICIAN |
| `GET /auth/invite/{token}` | публичная карта: ФИО, e-mail, ФИО врача | public (токен — учётка) |
| `POST /auth/invite/{token}/accept` | активация: аккаунт + ростер + сессия | public (токен — учётка) |

Аудит: `INVITE_CREATE/INVITE_REISSUE/INVITE_REVOKE/INVITE_ACCEPT` — только
id-строка, без ФИО и e-mail.
