# 17. Локальная модель в контуре (OpenAI-совместимый /v1)

**Артефакт:** docs/17-локальная-модель.md
**Статус:** инфраструктура + инструкция (прод-дефолт не меняется)
**Связано:** docs/03 (внешние подсистемы за SPI), docs/04 FR-17, docs/08, docs/10 (R11), docs/12, `infra/docker-compose.local-llm.yml`, `tools/llm.sh`.

## 1. Зачем

Ассистент врача использует LLM в трёх узких ролях, и все они работают только с
очищенным от ПДн текстом (docs/12):

1. **Роутер раздела базы знаний** — модель обязана вернуть `tool_call`
   `search_<раздел>` (FR-14);
2. **Переформулировка уточняющего вопроса** — «а в каких дозах?» разворачивается
   по последним репликам треда в самодостаточный поисковый запрос (FR-21);
3. **Ответ по найденным сниппетам** — `llm_router.compose_answer` (FR-17):
   модель пишет связный ответ по-русски, опираясь только на пронумерованные
   фрагменты КБ и историю диалога, и ссылается на них как `[n]`.

Границы ответа (жёсткие, проверяются на сервере):

- **Только сниппеты и история.** Модель не видит карту пациента: контекст
  пациента остаётся локальным и в промпт не попадает. Запрос «по карте» без
  находок в КБ отвечает детерминированный `build_rag_answer`.
- **Красные линии — до LLM.** Запросы про диагноз/терапию/дозы отказывает
  `detect_redline` детерминированно, такой текст в модель не уходит (docs/01 §4).
- **Цитаты валидирует сервер.** Ссылки `[n]` разбираются и проверяются: минимум
  одна валидная, не больше трёх, без дублей по `guideline_id`; `citations`
  собираются только из реальных чанков. Ответ без валидных ссылок, пустой ответ,
  таймаут и ошибка HTTP → детерминированный `build_rag_answer` (API не отдаёт
  500 из-за модели).
- **Дефолт офлайн.** Пустой `CC_ASSISTANT_LLM_URL` возвращает прежнее поведение:
  роутинг по всем разделам и детерминированный ответ.

Требования 152-ФЗ (ст. 12 — трансграничная передача, ст. 19 — защита) и модель угроз docs/10 (R11: LLM не должен выходить за red line; R17: egress по умолчанию выключен) означают: в контуре заказчика должен быть **воспроизводимый способ поднять модель рядом с api**, без обращения к внешним API. Этот документ описывает такой способ:

- `infra/docker-compose.local-llm.yml` — оверлей, поднимающий llama.cpp server (`ghcr.io/ggml-org/llama.cpp:server`) в сети `infra_default`;
- api достаёт модель по `http://local-llm:8080/v1` — обычный OpenAI-совместимый endpoint;
- **прод-дефолт не меняется**: в базовом `infra/docker-compose.yml` `CC_ASSISTANT_LLM_URL` остаётся пустым, без оверлея и `.env` поведение прежнее (поиск по всем разделам).

Почему llama.cpp, а не ollama: один статический бинарь + GGUF-файл, нет отдельного демона/магазина моделей, `/v1/chat/completions` с разбором `tool_calls` (`--jinja`), и тот же движок уже используется в `tools/llm.sh` для варианта «модель на хосте».

## 2. Что поднимается

| Параметр | Значение |
|---|---|
| Образ | `ghcr.io/ggml-org/llama.cpp:server` |
| Endpoint внутри сети | `http://local-llm:8080/v1` |
| Публикация на хост | `127.0.0.1:${CC_LOCAL_LLM_PORT:-8080}` (только loopback) |
| Модели | `${CC_LOCAL_LLM_MODELS_DIR:-./models}:/models:ro` (по умолчанию `infra/models`, в `.gitignore`) |
| Healthcheck | `curl -fsS http://127.0.0.1:8080/v1/models`, `start_period: 120s` |
| Сеть | `infra_default` (external) — та же, где живут `api`, `qdrant`, `postgres` |

Сеть объявлена external намеренно: оверлей не создаёт второй bridge, а подключается к сети уже работающего стека, поэтому имя `local-llm` резолвится из api. Egress наружу у контейнера модели нет (образ ничего не скачивает сам), исходящие запросы к внешним API не нужны.

## 3. Выбор модели и ресурсы

Роутеру нужен не «умный собеседник», а стабильный JSON/tool-call на короткий вопрос. Практические ориентиры (GGUF):

| Класс | Файл Q4_K_M | RAM/VRAM при ctx 8192 | На CPU (8 ядер) |
|---|---|---|---|
| 1.5–3B | ≈ 1–2 ГБ | ≈ 2.5–3.5 ГБ | пригодно, секунды на ответ |
| 7–8B | ≈ 4.5–5 ГБ | ≈ 6–7 ГБ | единицы токенов/с, tool_call ~2–5 с |
| 27–32B | ≈ 16–19 ГБ | ≈ 20–24 ГБ | непрактично, нужен GPU |

- Квантизация: Q4_K_M — минимум для роутера; на Q2/Q3 модели чаще ломают `tool_calls` и теряют русский язык. Q5_K_M/Q6_K — если хватает памяти.
- Контекст: 8192 достаточно, в LLM уходит только запрос (без корпуса БЗ и без контекста пациента).
- GPU: `CC_LOCAL_LLM_N_GPU_LAYERS=99` + раскомментировать `gpus: all` в оверлее (нужен nvidia-container-toolkit). Без GPU `N_GPU_LAYERS=0` — считает CPU.
- Чат-шаблон модели обязан поддерживать tools (Qwen2.5/Qwen3, Llama-3.1+, Mistral и т. п.); `--jinja` в оверлее обязателен, иначе `tool_calls` не распарсятся и роутер уйдёт в fallback.

Модель скачивается вручную (контейнер не тянет веса из интернета):

```bash
# пример: Qwen3-8B (Apache-2.0), Q4_K_M ≈ 4.7 ГБ
pip install -U huggingface_hub
cd infra
huggingface-cli download Qwen/Qwen3-8B-GGUF Qwen3-8B-Q4_K_M.gguf --local-dir models
mv models/Qwen3-8B-Q4_K_M.gguf models/model.gguf   # или задать CC_LOCAL_LLM_MODEL_PATH
```

## 4. Поднять сервис

Все команды — из каталога `infra/`, чтобы compose-проект назывался `infra` и сеть совпала с уже поднятым стеком (`infra_default`).

```bash
cd infra

# 1) основной стек (сеть infra_default создаётся здесь)
docker compose -f docker-compose.yml up -d

# 2) модель (можно комбинировать файлы в одной команде)
docker compose -f docker-compose.yml -f docker-compose.local-llm.yml up -d local-llm
docker compose -f docker-compose.yml -f docker-compose.local-llm.yml ps local-llm
```

Оверлей без основного стека (если сеть уже есть от прежнего запуска):

```bash
docker network create infra_default   # только если сети ещё нет
docker compose -f docker-compose.local-llm.yml up -d
```

Проверка синтаксиса без запуска модели:

```bash
docker compose -f docker-compose.yml -f docker-compose.local-llm.yml config -q
docker compose -f docker-compose.local-llm.yml config -q
```

## 5. Переключить ассистента

В `infra/.env` (переменные перечислены в `infra/.env.example`):

```dotenv
CC_LOCAL_LLM_MODELS_DIR=./models
CC_LOCAL_LLM_MODEL_PATH=model.gguf
CC_LOCAL_LLM_CTX=8192
CC_LOCAL_LLM_N_GPU_LAYERS=0
CC_LOCAL_LLM_PORT=8080

# собственно переключение
CC_ASSISTANT_LLM_URL=http://local-llm:8080/v1
CC_ASSISTANT_LLM_MODEL=local        # = --alias в оверлее
CC_ASSISTANT_LLM_API_KEY=           # llama-server без ключа
```

```bash
cd infra
docker compose -f docker-compose.yml up -d local-llm api
```

`CC_ASSISTANT_LLM_MODEL` обязан совпадать с `--alias` контейнера, иначе llama-server вернёт `404 model not found`. Ключ пустой — заголовок `Authorization` не отправляется.

## 6. Проверка

```bash
cd infra
# модель отвечает и загружена (healthcheck тоже смотрит сюда)
curl -fsS http://127.0.0.1:8080/v1/models | python3 -m json.tool

# api видит модель по имени в сети
docker compose -f docker-compose.yml -f docker-compose.local-llm.yml exec api \
  python -c "import urllib.request; print(urllib.request.urlopen('http://local-llm:8080/v1/models').status)"

# роутер: модель должна выбрать раздел (None = вне разделов / ошибка → fallback)
docker compose -f docker-compose.yml -f docker-compose.local-llm.yml exec \
  -e CC_ASSISTANT_LLM_URL=http://local-llm:8080/v1 -e CC_ASSISTANT_LLM_MODEL=local \
  api /app/.venv/bin/python -c \
  "from app.services.llm_router import route_topic; print(route_topic('какие шкалы используют для оценки тревоги?'))"
```

Ожидаемые значения `route_topic`: `ШКАЛЫ`, `ТРИАЖ`, `РЕКОМЕНДАЦИИ`, `ЛЕКАРСТВА`, `НАУЧНЫЕ-СТАТЬИ` или `None`.

Генерация ответа по сниппетам (тот же контейнер, без БД и Qdrant):

```bash
docker compose -f docker-compose.yml -f docker-compose.local-llm.yml exec \
  -e CC_ASSISTANT_LLM_URL=http://local-llm:8080/v1 -e CC_ASSISTANT_LLM_MODEL=local \
  api /app/.venv/bin/python -c \
  "from app.services.llm_router import compose_answer; print(compose_answer(
      [],
      'какой порог умеренной депрессии по PHQ-9?',
      [{'text': 'PHQ-9: 10-14 баллов — умеренная депрессия.', 'source_title': 'Гайдлайн PHQ-9'}]))"
```

Ожидаемо: связный ответ по-русски со ссылкой `[1]`. `None` — модель выключена,
недоступна или вернула пустой текст; API в этом случае отвечает
детерминированным `build_rag_answer`.

Полный путь через API (нужен CLINICIAN и TOTP-код, `CC_REQUIRE_OTP=true`):

```bash
# токен
TOKEN=$(curl -sS -X POST http://127.0.0.1:8090/api/v1/auth/login \
  -H 'content-type: application/json' \
  -d '{"email":"<email>","password":"<password>","otp":"<6 цифр>"}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')

# ответ ассистента: topic выбрала локальная модель, текст — LLM по сниппетам
# (без CC_ASSISTANT_LLM_URL или при сбое модели текст детерминированный)
curl -sS -X POST http://127.0.0.1:8090/api/v1/assistant/ask \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"query":"какие шкалы используют для оценки тревоги?","limit":5}' | python3 -m json.tool
```

Порт 8090 — UI-nginx, который проксирует `/api/v1` (сам api наружу не публикуется, F12).

## 7. Замер качества на `bench/`

`bench/` измеряет **поиск** (dense+sparse RRF), а не LLM: качество ответов определяется корпусом и эмбеддером, а модель лишь формулирует текст по найденным фрагментам (или её заменяет детерминированный `build_rag_answer`). Порядок замера:

```bash
cd bench
~/.local/bin/python3.12 -m venv .venv
.venv/bin/pip install torch --index-url https://download.pytorch.org/whl/cpu
.venv/bin/pip install sentence-transformers FlagEmbedding

.venv/bin/python fetch_sources.py      # PMC + факт-листы ВОЗ
.venv/bin/python build_dataset.py      # 108 чанков, 14 золотых запросов → data/
.venv/bin/python expand_queries.py     # расширение до 55 запросов
.venv/bin/python run_bench.py --model bge-m3   # Recall@1/5/10, nDCG@10, MRR@10
```

Базовые значения — в `bench/README.md`. Замеры до/после изменения корпуса или эмбеддера сравнивайте на одном и том же наборе (`data/queries.jsonl`) — LLM-роутер на эти метрики не влияет.

Что именно даёт локальная модель — **точность маршрутизации** и **латентность**. Мини-замер по 14 золотым запросам (`data/queries.jsonl`) и ручным эталонным разделам:

```bash
cd infra
# файл запросов в контейнер api (compose cp работает и в комбинированном проекте)
docker compose -f docker-compose.yml -f docker-compose.local-llm.yml cp \
  ../bench/data/queries.jsonl api:/tmp/queries.jsonl

docker compose -f docker-compose.yml -f docker-compose.local-llm.yml exec -T \
  -e CC_ASSISTANT_LLM_URL=http://local-llm:8080/v1 -e CC_ASSISTANT_LLM_MODEL=local \
  api /app/.venv/bin/python - <<'PY'
import json, time
from app.services.llm_router import route_topic

# эталон: id запроса → ожидаемый раздел (заполняется вручную по смыслу запроса)
GOLD = {"q-ru-anx-symptoms": "НАУЧНЫЕ-СТАТЬИ", "q-ru-taichi": "НАУЧНЫЕ-СТАТЬИ"}
rows = [json.loads(l) for l in open("/tmp/queries.jsonl", encoding="utf-8")]
ok = n = 0
for r in rows:
    t0 = time.perf_counter(); got = route_topic(r["q"]); dt = time.perf_counter() - t0
    exp = GOLD.get(r["id"])
    print(f'{r["id"]:<22} -> {str(got):<16} {dt*1000:6.0f} ms  {"" if exp is None or got == exp else "MISS"}')
    if exp is not None:
        n += 1; ok += got == exp
print(f"routing accuracy: {ok}/{n}")
PY
```

`-T` отключает TTY — без него `compose exec` с heredoc падает на «the input device is not a TTY». Альтернатива без контейнера: тот же скрипт на хосте с `PYTHONPATH=<repo>/api` и `CC_ASSISTANT_LLM_URL=http://127.0.0.1:8080/v1` (порт опубликован на loopback).

Практические критерии приёмки для локальной модели:

- доля валидных `tool_call` (не `None` на профильных вопросах) — не ниже, чем у эталонного шлюза на тех же запросах;
- `p95` латентности роутера — не выше `CC_ASSISTANT_LLM_TIMEOUT` (по умолчанию 10 с), иначе роутер будет уходить в fallback;
- `bench/` метрики (Recall@5/nDCG@10) не изменились — они не зависят от модели.

## 8. Ограничения

- **Качество на CPU**: 7–8B Q4 на CPU пригодно для роутинга и коротких ответов по 1–3 сниппетам; длинные связные клинические тексты на CPU медленные (генерация упирается в `CC_ASSISTANT_LLM_ANSWER_TIMEOUT`, по умолчанию 25 с). 27B+ на CPU неприменим.
- **Роутинг может деградировать**: маленькие модели путают близкие разделы (ТРИАЖ vs ШКАЛЫ) и иногда не вызывают тулзу. Это не ломает ассистента: `None` → поиск по всем разделам (fallback), ответ строит детерминированный путь.
- **Ответ может деградировать**: модель иногда не ставит ссылки `[n]`, ссылается на несуществующий сниппет или уходит в рассуждения. Сервер это ловит (валидация ссылок, потолок 2000 символов) и отдаёт детерминированный `build_rag_answer`; API не падает из-за модели.
- **Роль LLM узкая**: модель не видит ПДн и карту пациента, не ставит диагноз и не назначает терапию (red line считается до вызова LLM); качество ответа определяется корпусом КБ (docs/08) и поиском (bench), а модель — только формулировкой.
- **e2e ждут детерминированный текст**: проверки UI ищут «По базе знаний найдено следующее:». С включённой моделью текст другой, поэтому e2e и demo-прогоны идут без `CC_ASSISTANT_LLM_URL` (прод-дефолт).
- **Веса не в git**: GGUF-файл (гигабайты) кладётся вручную; `infra/models/` в `.gitignore`. Лицензию модели проверяйте отдельно (Apache-2.0/MIT у большинства open-weights).
- **Первый старт**: загрузка весов с диска занимает десятки секунд — `start_period` healthcheck 120 с; api-роутер имеет таймаут 10 с, поэтому перезапускайте api после `local-llm` стал `healthy`.
- **Прод**: опубликованный порт — только `127.0.0.1`; модель не публикуется в интернет. Для прод-контура с GPU используйте свой compose-оверлей, этот файл — минимальный воспроизводимый вариант.

CC_ASSISTANT_LLM_URL=

## 10. Альтернатива: модель на хосте

Если модель уже запущена на хосте (GPU), `docker-compose.local-llm.yml` не нужен — `tools/llm.sh` поднимает `llama-server` на `127.0.0.1:18080`, а api ходит через `host.docker.internal:18080` (см. комментарий в `infra/docker-compose.yml` и `infra/.env.example`).
