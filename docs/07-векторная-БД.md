# 07. Векторная БД для ИИ-агента (ADR)

Статус: v0.1, 2026-10-16. Решение принято; реализация — этап 08 (ИИ-агент).

---

## 1. Контекст

Добавляем ИИ-агента — чатбота **врача-ассистента** на LangChain/LangGraph с **гибридным поиском по базе знаний** (вкладка для врачей в интерфейсе + функционально). БД наполняется открытым медицинским корпусом: клинические рекомендации Минздрава (тревога/депрессия), инструкции препаратов (в т.ч. АВИАНДР/Маритупирдин), протоколы триажа, описания шкал.

Требования к векторной БД:
- **self-host** в РФ (152-ФЗ), разворачивается **отдельным сервисом в docker-compose**;
- **гибридный поиск** (dense + sparse), т.к. корпус на русском и описывается разными терминами (акроним «ГАД», синонимы, названия шкал);
- лёгкая эксплуатация на 1 ноде под демо;
- русскоязычные эмбеддинги.

## 2. Варианты

| БД | Лицензия | Гибрид (dense+sparse) | Эксплуатация | Комментарий |
|---|---|---|---|---|
| **Qdrant** v1.19.2 | Apache-2.0 | **Нативный**: named vectors (dense/sparse/multivector) + Query API `prefetch` + fusion RRF/DBSF | Один контейнер, один бинарник, без координаторов; memory tiers + скалярная/бинарная квантизация | Лучший fit под BGE-M3 (dense+sparse+ColBERT одним моделью) |
| **pgvector** 0.7.0+ | (расширение Postgres, свободный) | Ограничен: есть `sparsevec`, но **без ANN-индекса на sparse** — только точный перебор; «гибрид» = vector + Postgres FTS (`tsvector`), без встроенного RRF | Уже есть Postgres, ничего нового | KB-вектора попадают в ту же БД, что и спец-категории ПДн — размывает поверхность 152-ФЗ |
| **Weaviate** | NOASSERTION (BSD-3 + source-available модули) | Нативный (BM25 + vector + fusion) | Несколько сервисов/модулей | Больше движущихся частей |
| **Milvus** v2 | Apache-2.0 | Нативный | Standalone проще, но в проде тянет etcd + (MinIO/Pulsar) | Избыточен для корпуса такого объёма |
| **Chroma / LanceDB** | Apache-2.0 | Chroma: без production-гибрида; LanceDB: embedded, без сервера | Максимально просто | Не даёт «отдельного docker-сервиса» |

## 3. Решение

**Qdrant v1.19.2** — отдельным контейнером в `infra/docker-compose.yml`. Это совпадает с вариантом пользователя.

### Обоснование

1. **Нативный гибрид** — dense + sparse и multivector как named vectors, слияние по `prefetch` + `RRF`/`DBSF` в Query API (доступно с v1.10.0). Не нужно собирать fusion вручную, как в pgvector.
2. **Оптимален под BGE-M3** (см. §5): одна модель даёт dense, sparse и ColBERT — ровно три типа, которые Qdrant хранит как named vectors. Отпадает отдельный sparse-пайплайн (SPLADE/BM25).
3. **Лёгкий self-host**: один бинарник (Rust), без координаторов/etcd; память регулируется memory tiers + квантизацией. Для корпуса в несколько тысяч чанков — минимальные ресурсы, помещается в RAM.
4. **Apache-2.0**, поддерживается (последний релиз v1.19.2, ~35k звёзд).
5. **Разделение поверхностей — плюс к 152-ФЗ**: база знаний — это **открытый, не персональный** корпус. Размещение векторов в отдельном Qdrant (а не в Postgres с ПДн) не смешивает их со спец-категорией персональных данных и не расширяет аудит/согласие на публичный контент. Это ключевой аргумент против pgvector.
6. **Экосистема**: зрелая интеграция `langchain-qdrant` + `langchain-huggingface`.

### Принятые компромиссы
- **+1 контейнер и +1 датастор** в стеке.
- Qdrant хранит **только публичный корпус**, без связи с пациентом: никаких `patient_id`, `escalation_id` в векторах. Связь с клиникой только через источник (guideline_id) для цитирования.
- Присоединение LLM/реранкера — за SPI, по умолчанию офлайн-мок (см. docs/03 §1.3): без сети и без утечек ПДн.

## 4. Развёртывание (docker-compose)

```yaml
services:
  qdrant:
    image: qdrant/qdrant:v1.19.2
    ports:
      - "6333:6333"     # REST
      - "6334:6334"     # gRPC
    volumes:
      - qdrant-data:/qdrant/storage
    healthcheck:
      test: ["CMD", "bash", "-c", "exec 3<>/dev/tcp/localhost/6333 && echo -e 'GET /healthz HTTP/1.0\r\n\r\n' >&3 && grep -q '200' <&3"]
      interval: 5s
      timeout: 3s
      retries: 10
```

Индекс создаётся при старте сервиса (контейнер инициализации/seed), идемпотентно: `DELETE collection` + `recreate` при изменении схемы.

## 5. Эмбеддинги и спарс-вектора

**Выбор подтверждён эмпирически: bench/run_bench.py на собственном корпусе
(8 мета-анализов PMC + факт-листы ВОЗ, 108 чанков, **55 золотых запросов RU/EN**,
вкл. кросс-языковые; метрики R@1/5/10, nDCG@10, MRR; плоскости dense /
dense+sparse RRF / dense+BM25 RRF):**

| Модель | dense | hybrid (RRF) | +BM25 | R@1(dense) | R@5(dense) | R@10(dense) | MRR(dense) | Примечание |
|---|---|---|---|---|---|---|---|---|
| hash (офлайн-база, baseline) | 0.417 | 0.471 | 0.512 | 0.173 | 0.427 | 0.573 | 0.437 | без модели, детерминирован |
| deepvk/USER-bge-m3 | 0.809 | 0.665 | 0.755 | 0.436 | 0.873 | 0.955 | 0.806 | RU-focused, dense 1024 |
| ai-forever/FRIDA | 0.789 | 0.653 | 0.724 | 0.409 | 0.861 | 0.952 | 0.793 | dense-only + префиксы |
| **BAAI/bge-m3** | **0.815** | 0.722 | 0.737 | **0.427** | **0.897** | 0.964 | **0.804** | **dense+sparse настоящие** |
| Qwen/Qwen3-Embedding-0.6B | 0.790 | 0.658 | 0.724 | 0.373 | 0.879 | **0.967** | 0.756 | dense-only (sparse=hash) |
| intfloat/multilingual-e5-large | 0.788 | 0.625 | 0.684 | 0.345 | 0.867 | 0.973 | 0.753 | dense-only (sparse=hash) |

nDCG@10 по плоскостям; в скобках — только dense-метрики. Набор расширен с 14 до
55 запросов после того, как на 14 запросах лидировал e5 (0.820 vs 0.742) — на
выборке в 4 раза больше **ранжирование перевернулось**: bge-m3 dense 0.815,
user-bge-m3 0.809, qwen3 0.790, e5 0.788. Это прямая иллюстрация того, что
14 запросов давали шум.

**Статистика e5 vs bge-m3 (dense, попарно по 55 запросам):**
- nDCG@10: разница −0.026 в пользу bge-m3, 95% bootstrap-CI [−0.069, +0.019],
  Wilcoxon p=0.21 — **не значима**;
- **R@1: 0.427 против 0.345, разница −0.082, 95% CI [−0.164, −0.009] — значима**
  (CI не включает 0). R@1 — ключевая метрика для базы знаний: попадает ли
  правильный источник в первую цитату.

**Чтение таблицы (честно):** на этом корпусе **dense-only всюду обгоняет
гибрид** — RRF с любым спарс-каналом (настоящие веса bge-m3, BM25, хеш) даёт
0.62–0.74 против 0.79–0.82 у dense. На 108 чанках плотный косинус уже достаёт
всё релевантное, а лексический канал вносит шум. Это свойство корпуса, а не
приговор гибриду: на масштабе в тысячи чанков фьюжн обычно окупается.

**Замер на прикладном пути** (`bench/eval_app_path.py`: `kb.upsert_documents` +
`kb.hybrid_search`, изолированная коллекция Qdrant, те же 55 запросов/qrels;
nDCG@3/Recall@3 — целевые метрики RU-качества; GPU RTX 5090, fp16):

| Профиль (стратегия) | RU nDCG@3 | RU R@3 | EN nDCG@3 | EN R@3 | all nDCG@10 | p50/p95, мс |
|---|---|---|---|---|---|---|
| hash (dense+sparse RRF, baseline) | 0.142 | 0.139 | 0.413 | 0.450 | 0.434 | 6/8 |
| **bge-m3 (dense-only)** | **0.776** | **0.819** | 0.723 | 0.787 | 0.815 | 49/92 |
| multilingual-e5-large (dense-only) | 0.616 | 0.611 | 0.739 | 0.860 | 0.788 | 17/37 |
| ai-forever/FRIDA (dense-only) | 0.635 | 0.653 | 0.710 | 0.775 | 0.788 | 47/74 |

RU-разрыв hash↔bge-m3 — 5.5x по nDCG@3: feature-hashing не переносит смысл между
языками и морфологией. bge-m3 выбран прод-профилем (лучший RU и overall);
e5 быстрее (17 против 49 мс), но на RU-запросах проигрывает 0.16 nDCG@3.

**Ответ на вопрос «зачем встроенный sparse, если есть BM25 + RRF»:** встроенный
sparse **не обязателен** — это два конкурирующих способа достроить лексический
канал. BM25+RRF даёт то же качество без GPU-инференса для лексики, но требует
второго индекса (Postgres `tsvector`/`ts_rank` или FTS5) и синхронизации при
переиндексации. Встроенный sparse даёт гибрид одним запросом к Qdrant и
обученные веса (ловит морфологию/синонимы лучше BM25 со стеммером). На нашем
корпусе **оба проигрывают dense**, поэтому архитектурный козырь bge-m3 —
страховка на масштаб, а не источник текущего качества.

Почему в демо и тестах оставлен **hash**, а прод-вариант **bge-m3**:
1. **Демо/тесты**: hash — офлайн, детерминирован, без загрузки модели
   (`CC_EMBEDDER=hash` по умолчанию). На 8-чанковом корпусе демо разница качества
   не видна, а воспроизводимость важнее.
2. **Прод**: bge-m3 — лучший по dense nDCG@10 (0.815), R@1 (0.427, значимо выше
   e5), R@5 (0.897) и MRR (0.804) на расширенной выборке, **и** единственный
   кандидат с настоящим sparse (и ColBERT) из одной модели. То есть выигрывает
   и по качеству, и по архитектуре.
3. Переключение — одна переменная `CC_EMBEDDER` (фабрики `build_embedder`
   и процессного синглтона `get_embedder`); профиль настраивается
   `CC_EMBEDDER_MODEL/_DEVICE/_BATCH_SIZE/_MAX_LENGTH` (docs/08 §4).
   Размерность коллекции Qdrant меняется 512→1024, поэтому **обязательна
   переиндексация** (`python -m app.kb_seed --reset` для демо-корпуса);
   несовпадение ловят `ensure_collection` и стартовая проверка
   `kb.check_embedder_compatibility` — приложение падает с инструкцией (docs/08 §4).

Детали воспроизведения — bench/README.md; харнесс не входит в docker-образы.

**BAAI/bge-m3** — мультиязычная модель (100+ языков, включая русский), которая **одновременно** даёт:
- **dense** вектор (семантика),
- **sparse** вектор (лексика: точное совпадение терминов),
- **ColBERT** multi-vector (поземельное сопоставление).

Это снимает необходимость связки «dense-модель + отдельный sparse-индекс»: один encoder, три представления — все три ложатся в named vectors Qdrant.

Русскоязычный клинический корпус выигрывает от dense+sparse одновременно: dense ловит смысл («повышенная тревожность» и «ГАД» близки), sparse — точные идентификаторы и акронимы (код шкалы, МНН препарата), которые dense может упустить. На нашем корпусе (108 чанков) dense-only ранжирует лучше (§5), поэтому **прод-профиль bge-m3 ищет dense-only** (`Embedder.use_sparse=false`): sparse-вектора индексируются и доступны, но RRF-фьюжн включается только для hash-профиля. На масштабе в тысячи чанков фьюжн можно включить без изменения схемы коллекции.

## 6. Схема коллекции

```json
{
  "collection_name": "kb",
  "vectors": {
    "dense":   {"size": 1024, "distance": "Cosine"},
    "colbert": {"size": 1024, "distance": "Cosine", "multivector_config": {"comparator": "max_sim"}}
  },
  "sparse_vectors": {"sparse": {}}
}
```

Каждая точка (чанк) несёт payload: `guideline_id`, `source_title`, `topic`
(ШКАЛЫ | ЛЕКАРСТВА | ТРИАЖ | РЕКОМЕНДАЦИИ | НАУЧНЫЕ-СТАТЬИ), `text`,
`chunk_index`, `text_hash`, а для внешних источников (`app/enrichment/index.py`)
дополнительно `work_id`, `source` (`pubmed` | `who`), `kind`
(`article` | `guideline`), `year`, `source_url`, `license`, `revision`.

Чанки справочника препаратов строятся из таблицы `drugs` (`kb_seed._drug_docs`),
поэтому `drug_id` в payload отдельным полем не дублируется — он внутри
`guideline_id`: `drug-<drug_id>` (основной чанк: форма, РУ, механизм, показания,
режим дозирования) и `drug-<drug_id>-safety` (нежелательные явления и
противопоказания, чтобы запрос «побочные эффекты <препарат>» попадал точно).
`topic` — `ЛЕКАРСТВА`, `source_title` — «<торговое название> (<МНН>) —
инструкция», в `text` входят номер и дата РУ: цитата агента проверяема по
записи ГРЛС, ссылки на первоисточники хранятся в `drugs.source_urls` (docs/11 §1.2).

Контракт провенанса (docs/15): `work_id` — идентификатор записи реестра
`kb_works`, по которому точки удаляются и переиндексируются
(`delete by work_id → upsert`, детерминированные md5-id); `source_url` и
`license` едут в payload, чтобы цитата агента имела проверяемую ссылку, а
индексирование было разрешено лицензией. `work_id` — ключ **персональной
видимости статьи** (FR-36, docs/15 §12): статья участвует в выдаче врача,
только если он сам поставил `decision='approved'` в `kb_work_approvals`;
точки без `work_id` (seed-корпус: шкалы, препараты, демо) и
`kind='guideline'` (гайдлайны ВОЗ) видны всем без решения.

Персональные исключения врача применяются при поиске как
`must_not guideline_id MatchAny` (§7); в самом индексе решения и исключения
не хранятся — источник истины в Postgres.

Индекс — **производный** от реестра: `kb_works`/`kb_runs`/`kb_exclusions`
в Postgres — источник истины, содержимое Qdrant восстанавливается прогоном
`python -m app.enrichment run` (сверка `remote_count` с `chunk_count`).

## 7. Поиск (гибрид)

Запрос → bge-m3 → dense + sparse + ColBERT → Query API с двумя `prefetch` (dense, sparse) → fusion **RRF** → тумблер: при высоком пороге поднять topN, затем **реранкер** (bge-reranker-v2-m3) → отдать топ-k с обязательным `source_title`+`guideline_id` для цитирования. Агент отвечает **только** по найденным фрагментам, при нехватке — явно говорит «в корпусе нет данных», без клинического вывода (red line docs/01).

### 7.1. Карта выбранного пациента в контексте ответа

Когда врач выбрал пациента в треде (FR-21), в промпт ответа уходит его карта —
**обезличенная** (`services.agent.scrub_for_llm`,
`assistant_chat._scrub_patient_contexts`): `fio` → `[ПАЦИЕНТ]`, дневник
маскирован, `patient_id` и контакты не передаются. Блок идёт после сниппетов,
по строке на пациента:

| Поле | Источник | В промпт |
| --- | --- | --- |
| `П1` | порядок карт в треде | номер для ссылки `[П1]` |
| пациент | `fio` | только маска `[ПАЦИЕНТ]` / `без ФИО` |
| пол | в модели данных нет колонки | `—` (не выдумывается) |
| возраст | `contacts.age` (из `birth_date`) | число |
| шкалы | `prescribed_scales` | список кодов |
| последняя оценка | `last_assessment.total_score`/`severity`/`computed_at` | как есть |
| триаж | `last_assessment.triage` | как есть |
| тренд | `trend.moving_avg[-1]`, `delta_7`, `delta_30`, `slope` | как есть |
| открытые эскалации | `open_escalations[].kind` | число и виды |
| дневник | `recent_diary[:3].content` (после скраба) | до 3 записей |

Ссылка модели `[П<n>]` валидируется так же, как `[n]`: в пределах реально
отправленных карт (`ANSWER_PATIENTS`=3 и бюджет символов), и превращается в
citation `{topic: "ПАЦИЕНТ", source_title: "Карта пациента",
guideline_id: "patient:<id>"}` — тот же контракт, что у детерминированного
`build_rag_answer`, поэтому UI-блок «Карта пациента» работает и при
`answer_kind="llm"`. Карта без находок в КБ до модели не доходит: такой запрос
отвечает `build_rag_answer`. Выключатель — `CC_ASSISTANT_LLM_PATIENT_CONTEXT`
(default `true`): при `false` промпт прежний, байт-в-байт.


Персональная видимость (FR-36) — ещё один фильтр того же запроса: `should`-
группа `work_id ∈ allow-list(мой approved)` **или** `is_empty(work_id)` **или**
`kind='guideline'`. Пустой allow-list отсекает все статьи, оставляя гайдлайны
и seed. Агент повторяет правило после Qdrant (`kb.is_visible`) для hash-
профиля и keyword-fallback — defense in depth, как у `exclude_ids`.

## 8. Открытые вопросы
- Объём корпуса (число чанков) — оценка после наполнения; при <10k чанков даже exact-перебор быстр, ANN-индекс не критичен.
- ~~Размер dense (bge-m3 = 1024) и необходимость **второго** реранкера~~ — реранкер (bge-reranker-v2-m3) остаётся опциональным тумблером; бенчмарк закрыл вопрос выбора модели (bge-m3, §5).
- Где хостить модель (onnx/CPU или GPU). - **Закрыто бенчмарком:** CPU достаточно для корпуса демо (<10k чанков; 108 чанков bge-m3 на CPU ≈ 6 мин). GPU — только при прод-наполнении и/или добавлении re-rank.
- ~~Выбор эмбеддера~~ - **пересматривается (TODO-бенчмарк-2).** Текущий вывод (§5) опирается на **малую и не узко-психиатрическую** выборку: 108 чанков (8 PMC мета-анализов + 3 факт-листа ВОЗ) и 55 запросов. Для уверенного выбора нужен **датасет крупнее** — мета-исследования и гайдлайны/рекомендации **ВОЗ именно по психиатрии и лечению тревоги/депрессии** (не только общие помимо тематики). Шаблон расширения уже готов (`bench/expand_queries.py` + `run_bench.py name:all`); после наполнения корпуса повторить бенчмарк и переутвердить bge-m3 либо сменить на лидера. Флаги: `CC_EMBEDDER` + `kb_seed --reset` + guard `ensure_collection` при смене размерности.
- Пересчёт бенчмарка при расширении корпуса: `bench/bin/python bench/run_bench.py --all` (см. bench/README.md).
