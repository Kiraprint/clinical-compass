# 07. Векторная БД для ИИ-агента (ADR)

Статус: v0.1, 2026-10-16. Решение принято; реализация — этап 08 (ИИ-агент).

---

## 1. Контекст

Добавляем ИИ-агента — чатбота **врача-ассистента** на LangChain/LangGraph с **гибридным поиском по базе знаний** (вкладка для врачей в интерфейсе + функционально). БД наполняется открытым медицинским корпусом: клинические рекомендации Минздрава (тревога/депрессия), инструкции препаратов (в т.ч. АВИАНДР/Маритупирдин), протоколы триажа, описания шкал.

Требования к векторной БД:
- **self-host** в РФ (152-ФЗ), разворачивается **отдельным сервисом в docker-compose**;
- **гибридный поиск** (dense + sparse), т.к. корпус на русском и описывается разными терминами (акроним «ГАД», синонимы, названия шкал);
- лёгкая эксплуатация на 1 ноде под демо;
- русскоязычные эмбеддинги.

## 2. Варианты

| БД | Лицензия | Гибрид (dense+sparse) | Эксплуатация | Комментарий |
|---|---|---|---|---|
| **Qdrant** v1.19.2 | Apache-2.0 | **Нативный**: named vectors (dense/sparse/multivector) + Query API `prefetch` + fusion RRF/DBSF | Один контейнер, один бинарник, без координаторов; memory tiers + скалярная/бинарная квантизация | Лучший fit под BGE-M3 (dense+sparse+ColBERT одним моделью) |
| **pgvector** 0.7.0+ | (расширение Postgres, свободный) | Ограничен: есть `sparsevec`, но **без ANN-индекса на sparse** — только точный перебор; «гибрид» = vector + Postgres FTS (`tsvector`), без встроенного RRF | Уже есть Postgres, ничего нового | KB-вектора попадают в ту же БД, что и спец-категории ПДн — размывает поверхность 152-ФЗ |
| **Weaviate** | NOASSERTION (BSD-3 + source-available модули) | Нативный (BM25 + vector + fusion) | Несколько сервисов/модулей | Больше движущихся частей |
| **Milvus** v2 | Apache-2.0 | Нативный | Standalone проще, но в проде тянет etcd + (MinIO/Pulsar) | Избыточен для корпуса такого объёма |
| **Chroma / LanceDB** | Apache-2.0 | Chroma: без production-гибрида; LanceDB: embedded, без сервера | Максимально просто | Не даёт «отдельного docker-сервиса» |

## 3. Решение

**Qdrant v1.19.2** — отдельным контейнером в `infra/docker-compose.yml`. Это совпадает с вариантом пользователя.

### Обоснование

1. **Нативный гибрид** — dense + sparse и multivector как named vectors, слияние по `prefetch` + `RRF`/`DBSF` в Query API (доступно с v1.10.0). Не нужно собирать fusion вручную, как в pgvector.
2. **Оптимален под BGE-M3** (см. §5): одна модель даёт dense, sparse и ColBERT — ровно три типа, которые Qdrant хранит как named vectors. Отпадает отдельный sparse-пайплайн (SPLADE/BM25).
3. **Лёгкий self-host**: один бинарник (Rust), без координаторов/etcd; память регулируется memory tiers + квантизацией. Для корпуса в несколько тысяч чанков — минимальные ресурсы, помещается в RAM.
4. **Apache-2.0**, поддерживается (последний релиз v1.19.2, ~35k звёзд).
5. **Разделение поверхностей — плюс к 152-ФЗ**: база знаний — это **открытый, не персональный** корпус. Размещение векторов в отдельном Qdrant (а не в Postgres с ПДн) не смешивает их со спец-категорией персональных данных и не расширяет аудит/согласие на публичный контент. Это ключевой аргумент против pgvector.
6. **Экосистема**: зрелая интеграция `langchain-qdrant` + `langchain-huggingface`.

### Принятые компромиссы
- **+1 контейнер и +1 датастор** в стеке.
- Qdrant хранит **только публичный корпус**, без связи с пациентом: никаких `patient_id`, `escalation_id` в векторах. Связь с клиникой только через источник (guideline_id) для цитирования.
- Присоединение LLM/реранкера — за SPI, по умолчанию офлайн-мок (см. docs/03 §1.3): без сети и без утечек ПДн.

## 4. Развёртывание (docker-compose)

```yaml
services:
  qdrant:
    image: qdrant/qdrant:v1.19.2
    ports:
      - "6333:6333"     # REST
      - "6334:6334"     # gRPC
    volumes:
      - qdrant-data:/qdrant/storage
    healthcheck:
      test: ["CMD", "bash", "-c", "exec 3<>/dev/tcp/localhost/6333 && echo -e 'GET /healthz HTTP/1.0\r\n\r\n' >&3 && grep -q '200' <&3"]
      interval: 5s
      timeout: 3s
      retries: 10
```

Индекс создаётся при старте сервиса (контейнер инициализации/seed), идемпотентно: `DELETE collection` + `recreate` при изменении схемы.

## 5. Эмбеддинги и спарс-вектора

**Выбор подтверждён эмпирически: bench/run_bench.py на собственном корпусе
(8 мета-анализов PMC + факт-листы ВОЗ, 108 чанков, 14 золотых запросов RU/EN,
вкл. кросс-языковые; метрики R@1/5/10, nDCG@10, MRR; плоскости dense / dense+sparse
RRF / dense+BM25 RRF):**

| Модель | dense | hybrid (RRF) | +BM25 | R@10(dense) | MRR(dense) | Примечание |
|---|---|---|---|---|---|---|
| hash (офлайн-база, baseline) | 0.329 | 0.377 | 0.413 | 0.429 | 0.404 | без модели, детерминирован |
| deepvk/USER-bge-m3 | 0.736 | 0.578 | — | 0.917 | 0.792 | RU-focused, dense 1024 |
| ai-forever/FRIDA | 0.697 | 0.566 | — | 0.810 | 0.798 | dense-only + префиксы |
| **BAAI/bge-m3** | 0.742 | 0.587 | 0.699 | 0.714 | 0.667 | **dense+sparse настоящие** |
| Qwen/Qwen3-Embedding-0.6B | 0.798 | 0.608 | 0.677 | 0.750 | 0.705 | dense-only (sparse=hash) |
| intfloat/multilingual-e5-large | **0.820** | 0.581 | 0.651 | **0.952** | **0.845** | dense-only (sparse=hash) |

**Чтение таблицы (честно):** на этом корпусе **dense-only всюду обгоняет
гибрид** — RRF с любым спарс-каналом (ни настоящие веса bge-m3, ни BM25, ни
хеш) только ухудшает выдачу. На 108 чанках плотный косинус уже достаёт всё
релевантное, а добавленный лексический канал вносит шум. e5-large по dense
лучше всех (0.820 vs bge-m3 0.742; попарно 6 побед, 6 ничьих, 2 поражения из 14).
Пропускная способность e5-multilingual ≥ bge-m3 (dense-only, 1024 dim).

Почему в демо и тестах оставлен **hash**, а прод-вариант **bge-m3** (не e5):
1. **Демо/тесты**: hash — офлайн, детерминирован, без загрузки модели
   (CC_EMBEDDER=hash по умолчанию). На 8-чанковом корпусе демо разница качества
   не видна, а воспроизводимость важнее.
2. **Прод-заявка**: bge-m3 — единственный кандидат с настоящим спарс-каналом
   (и ColBERT) из одной модели. Разрыв e5 по dense (0.078 nDCG) — на выборке из
   14 запросов, дисперсия высока (e5 проигрывает bge на 2 из 14). Для
   масштабного корпуса, где гибрид окупается, bge-m3 не требует второй модели;
   e5 пришлось бы усиливать внешним BM25/FTS.
3. Переключение — одна переменная `CC_EMBEDDER` (фабрика `build_embedder`),
   размерность коллекции Qdrant меняется 512→1024 при переиндексации
   (`kb_seed --reset`), guard в `ensure_collection` это проверяет.

Если качество станет важнее универсальности — `CC_EMBEDDER=e5` (dense-only)
на этом же корпусе даёт лучший nDCG@10=0.820; решение принимается по расширенной
выборке запросов (14 — мало для уверенного вывода).

Детали воспроизведения — bench/README.md; харнесс не входит в docker-образы.

**BAAI/bge-m3** — мультиязычная модель (100+ языков, включая русский), которая **одновременно** даёт:
- **dense** вектор (семантика),
- **sparse** вектор (лексика: точное совпадение терминов),
- **ColBERT** multi-vector (поземельное сопоставление).

Это снимает необходимость связки «dense-модель + отдельный sparse-индекс»: один encoder, три представления — все три ложатся в named vectors Qdrant.

Русскоязычный клинический корпус требует именно dense+sparse одновременно: dense ловит смысл (например, «повышенная тревожность» и «ГАД» близки), sparse ловит точные идентификаторы и акронимы (код шкалы, МНН препарата), которые dense может упустить.

## 6. Схема коллекции

```json
{
  "collection_name": "kb",
  "vectors": {
    "dense":   {"size": 1024, "distance": "Cosine"},
    "colbert": {"size": 1024, "distance": "Cosine", "multivector_config": {"comparator": "max_sim"}}
  },
  "sparse_vectors": {"sparse": {}}
}
```

Каждая точка (чанк) несёт payload: `guideline_id`, `source_title`, `chunk_index`, `text_hash`, `language`, `topic` (ШКАЛЫ | ПРЕПАРАТЫ | ТРИАЖ | РЕКОМЕНДАЦИИ).

## 7. Поиск (гибрид)

Запрос → bge-m3 → dense + sparse + ColBERT → Query API с двумя `prefetch` (dense, sparse) → fusion **RRF** → тумблер: при высоком пороге поднять topN, затем **реранкер** (bge-reranker-v2-m3) → отдать топ-k с обязательным `source_title`+`guideline_id` для цитирования. Агент отвечает **только** по найденным фрагментам, при нехватке — явно говорит «в корпусе нет данных», без клинического вывода (red line docs/01).

## 8. Открытые вопросы
- Объём корпуса (число чанков) — оценка после наполнения; при <10k чанков даже exact-перебор быстр, ANN-индекс не критичен.
- ~~Размер dense (bge-m3 = 1024) и необходимость **второго** реранкера~~ — реранкер (bge-reranker-v2-m3) остаётся опциональным тумблером; бенчмарк закрыл вопрос выбора модели (bge-m3, §5).
- Где хостить модель (onnx/CPU или GPU). - **Закрыто бенчмарком:** CPU достаточно для корпуса демо (<10k чанков; 108 чанков bge-m3 на CPU ≈ 6 мин). GPU — только при прод-наполнении и/или добавлении re-rank.
- Пересчёт бенчмарка при расширении корпуса: `bench/bin/python bench/run_bench.py --all` (см. bench/README.md).
