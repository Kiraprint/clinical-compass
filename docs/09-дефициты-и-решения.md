## 0. Кейс (подтверждённый текст)

**Задача:** инструмент поддержки принятия врачебных решений для ведения пациентов
с тревожно-депрессивной симптоматикой.

**Задачи инструмента (8):** 1) стандартизированные методы оценки; 2) рекомендации/
справка по вариантам терапии; 3) учёт и оценка рисков и нежелательных явлений;
4) мониторинг динамики; 5) пациентский интерфейс самоотчёта и самоконтроля
динамики; 6) каналы коммуникации для сопровождения лечения; 7) оценка
приверженности лечению; 8) выявление ситуаций для направления к психиатру (для
врачей других специальностей) + рекомендации по маршрутизации («обязательно»/
«желательно» по тяжести).

**Обязательные условия (9):** две роли Врач/Пациент; связь врач-пациент без третьих
лиц; никаких клинических действий без подтверждения врачом; **демо-сценарии с
назначением «Авиандр»** (профиль + рекомендации по лечению + маршрутизация);
алертинг (признаки и действия определяет команда); **сигналы направления к
психиатру и предупреждения безопасности терапии визуально выделены, категории
«обязательно»/«желательно» различимы**; КР Минздрава действующие + международные
с источником + **лекарства по действующей инструкции из ГРЛС** + шкалы
валидированные ру-версии с источником валидации; соответствие законодательству РФ;
конфиденциальность.

**Критерии оценки (6):** научная обоснованность; клиническая применимость; удобство
UI; наличие всех обязательных условий; **отдельно каждый пункт «что делает
инструмент»** (т.е. каждая из 8 задач); апробация.

**Технические метрики (13):** 1) быстродействие; 2) обработка входных данных —
извлечение из историй разных шаблонов; 3) надёжность/корректность; 4) эргономика;
5) обоснованность выводов источниками; 6) устойчивость к нагрузкам; 7)
отказоустойчивость/восстановление данных; 8) кроссплатформенность; 9)
масштабируемость; 10) гибкость архитектуры (шкалы/препараты/правила алертинга/
функции — без изменения ядра); 11) гибкость данных; 12) полнота данных; 13)
защищённость.

## 4. Дизайн решений

### P1. Справочный режим вместо отказа на всю терапию

Разделить «назначение/коррекцию» (запрет) и «справку» (разрешено).

- `core/compass/agent.py` `_TREATMENT_PATTERNS` сузить до интента назначения:
  `назначь|подбери|отмени|скорректируй|поменяй|увеличь дозу|уменьши дозу|схему терапии
  (мне|пациенту)` → отказ `TREATMENT_REDLINE` с текстом по P9.
- Справочные запросы (`инструкция|показания|дозировка|противопоказания|побочные|
  взаимодействия|как принимать <препарат>`) не отбиваются → retrieval по KB (после
  P2 там будут чанки препарата).
- Тесты: «Назначь Авиандр» → TREATMENT_REDLINE; «Дозировка Авиандра» → не red
  line, retrieval; «Показания Авиандра» → retrieval.

### P2. Данные по препаратам в KB (АВИАНДР® + резерв)

Структурированный манифест, источник — ГРЛС (публичный гос. реестр).

- `api/app/data/drugs.json`: per-drug {drug_id, trade_name, inn, reg_number
  [TBD из ГРЛС], indications, dosage, contraindications, adverse_events,
  special_notes, instruction_revision}. Факты дозировок/показаний — гос. данные,
  не копирайт; формулировки структурированные, с номером РУ и датой пересмотра в
  цитате. Согласуется с политикой docs/08 (no-third-party-text).
- `kb_seed.py` `_drug_docs()`: чанк на препарат (topic `ЛЕКАРСТВА`,
  `guideline_id = "drug-<id>"`) + отдельный чанк «НЯ препарата» для точного
  retrieval по «побочные эффекты».
- Доступ: CLINICIAN/ADMIN only (как /assistant/ask), аудит ASK_ASSISTANT.
- Проверка: после `kb_seed --reset` есть `drug-aviandr`; live «инструкция
  Авиандра» возвращает чанк с цитатой РУ.
- Демо-сценарии (усл.4): seed пациентов с назначением Авиандра (GAD-7 профиль →
  ГТР, показание Авиандра), в карточке — терапия + routing.

### P3. Реальные КР Минздрава в KB

По образцу `bench/fetch_sources.py` — манифест + загрузка на билде.

- `api/app/data/guidelines.json`: КР «ГТР (F41.1)» код 457 ред. 3 (Российское
  общество психиатров, cr.minzdrav.gov.ru), КР по депрессии (F32/F33) [код —
  подтвердить у медика]. Международные (WHO/NICE) — дополнение с указанием
  источника (усл.7).
- `kb_seed.py --with-guidelines` (нужна сеть): скачивает в gitignored кэш
  (`bench/.cache`-стиль), chunking ~512/64 overlap (docs/08 §3), SHA-256 dedup,
  чанки с guideline_id + source_title + URL рубрикатора.
- Без сети — корпус движок+препараты (§P1/P2) без КР.
- Проверка: «что рекомендуют КР при ГТР» → чанки КР с цитатой «КР ГТР (F41.1),
  код 457, ред. 3».

### P4. Модель нежелательных явлений

- `models.py AdverseEvent`: id, patient_id FK indexed, clinician_id FK, event_text,
  severity CHECK mild\|moderate\|severe, onset_date, suspected_drug nullable,
  action_taken CHECK none\|monitoring\|dose_reduced\|stopped\|referred, created_at.
  Именованные CHECK по конвенции.
- API: POST/GET `/clinician/patients/{id}/adverse-events` (roster-гейт 403
  NO_ROSTER, аудит ADVERSE_EVENT).
- UI: ClinicianView ReportView секция «Нежелательные явления» — список (препарат,
  тяжесть, действие) + форма.
- Alembic autogenerate (цепочка после a1b2c3d4e5f6).
- 152-ФЗ: consent-гейт, append-only аудит. Тесты по паттерну test_clinician.py.

### P5. Оценка приверженности лечению

- `models.py AdherenceRecord`: id, patient_id FK indexed, medication str nullable
  (напр. «Авиандр»), status CHECK taken\|partial\|missed, note nullable, recorded_at.
- Пациентский UI: вопрос в чекине «Принимали назначенный препарат?» → POST
  /me/adherence. Врач: поле «Назначенная терапия» в карточке + GET
  /clinician/patients/{id}/adherence → агрегат «% за 14 дней» (taken×1 +
  partial×0.5)/всего. Прогресс-бар в карточке.
- Препарат — свободная строка (без FK на лекарство; модель назначения появится
  только если кейс потребует). Тесты: запись/чтение/агрегат/roster-гейт.

### P6. Маршрутизация «обязательно/желательно» к психиатру

- `core/compass/routing.py`: RoutingCategory {REQUIRED, DESIRABLE, NONE};
  `routing_for(triage, risk_flags, scale_code) -> Routing(category, target,
  reason)`. Границы [TBD — медик]: SUICIDAL_IDEATION → REQUIRED; SEVERE →
  REQUIRED; MODERATE или MILD с ухудшением (delta_7>0) → DESIRABLE; NONE → NONE.
- Детерминировано из triage+flags (уже в Assessment), колонка не нужна.
- API: GET /clinician/patients/{id}/report добавляет routing последнего assessment.
- UI: ReportView блок «Маршрутизация» — badge красный «Обязательно — психиатр» /
  жёлтый «Желательно» / серый «не требуется». Категории визуально различимы (усл.6).
  Предупреждения безопасности терапии (НЯ, противопоказания) тоже визуально
  выделены (связка с P4).
- Core-тесты: детерминизм, границы (suicidal при низком балле → REQUIRED и т.п.).

### P7. Обработка входных клинических историй

- POST `/clinician/patients/{id}/import-history` (roster-гейт, аудит
  IMPORT_HISTORY): тело {text, template_name?}.
- `services/history_extract.py` — детерминированный экстрактор (без LLM в коре):
  словари заголовков разделов по нескольким шаблонам («Жалобы/Complaints/Анамнез/
  Anamnesis/Диагноз/Diagnosis/Лечение/Therapy/Назначено/Принимает»), извлечение:
  жалобы, анамнез, диагноз (МКБ-10), текущая терапия (препарат+доза), баллы шкал.
- Результат — черновик для **подтверждения врачом**, не авто-запись (красные
  линии не нарушаются: структурирование, не диагноз).
- Бенч `bench/history/`: 5-10 шаблонов историй (gold-поля), метрика «доля
  корректно извлечённых полей на шаблон» — таблица. Закрывает метрику 2.

### P8. Канал врач↔пациент

- `chat_messages.sender` CHECK расширяется на CLINICIAN (миграция + новый CHECK).
- POST `/clinician/patients/{id}/chat` (roster-гейт, аудит), пациент GET
  /chat/thread видит врачебные сообщения.
- UI: ClinicianView панель чата в карточке; PatientView чат — ответы врача.
- 152-ФЗ: consent, append-only аудит. Scope средний; кейс задача 6 → делать.

### P9. Правовая ссылка

- `kb_seed.py` redline-therapy + `agent.py` отказ: «323-ФЗ ст.36.2, приказ
  Минздрава №965н; врач-врач телемед-консультации/консилиумы — без очного приёма».
- Тест: текст отказа содержит «323-ФЗ», не содержит «242-ФЗ».

### P10. Отказоустойчивость/backup демо

- Реализовать pg_dump cron в docker-compose (раз в сутки, 30 дней) + документ
  restore: `pg_restore` в fresh БД через `alembic upgrade head` + пересев.
- Демонстрация: backup→drop→restore→seed, данные целы; «критические данные
  (escalations, audit) не теряются» — audit_log append-only + WAL. Метрика 7.

### P11. Правила алертинга data-driven

- Вынести правила триажа/алертинга в конфиг (`api/app/data/alert_rules.json`):
  {flag, condition, triage, action}. Core `triage()` читает правила из
  dataclass-конфига (как ALL_SCALES), не хардкод.
- Добавление правила (напр. «PHQ-9 q9>=2 → REQUIRED routing») = правка JSON, не
  кода. Метрика 10 (гибкость без ядра). Препараты (P2 drugs.json) и шкалы уже
  data-driven — вместе закрывают метрику 10.

### P12. Апробация

- Валидационный нарратив в docs: 3-5 клинических сценариев (профиль→скрининг→
  триаж→therapy-справка (Авиандр)→routing→мониторинг→НЯ/приверженность),
  результат对照 с КР Минздрава. + таблица «сценарий → ожидаемый триаж/routing →
  факт».
- Не пилот на реальных пациентах (152-ФЗ, demo), а валидация детерминированного
  движка на сценариях. Критерий 6.

### P13. Замеры метрик 1/4/6
