# ТЗ. Техническое задание на разработку программного обеспечения

**Наименование разработки:** «Клинический компас» — цифровой инструмент вспомогательной диагностики и мониторинга пациентов с тревожными и депрессивными расстройствами.

**Обозначение документа:** `ТЗ. Клинический компас. v1.0`

**Документ разработан по:** ГОСТ 19.201-78 (ЕСПД. Техническое задание. Требования к содержанию и оформлению).

**Статус:** проект для кейс-чемпионата «Клинический компас 2026». Дата: 2026-10-13. Редакция: v1.0.

---

## 1. Введение

### 1.1 Полное наименование программы

Полное наименование: **«Клинический компас» (Clinical Compass)** — программное обеспечение веб-приложения для структурированного скрининга, мониторинга и передачи врачу данных о состоянии пациентов с тревогой и депрессией.

Условное обозначение (код разработки): `clinical-compass`.

### 1.2 Краткая характеристика области применения

Область применения — вспомогательная диагностика и динамическое ведение (мониторинг) пациентов (18+) с лёгкой и средней степенью тяжести тревожных и депрессивных симптомов. Программное обеспечение размещается в защищённом терапевтическом и клиническом контуре: интерфейс пациента, интерфейс врача-психиатра/психотерапевта, интерфейс администратора.

Программное обеспечение является **дополняющим (adjunct)** инструментом: оно не заменяет клиническое решение врача, а предоставляет структурированные данные (баллы валидированных шкал, динамика, риск-эскалации) для его обоснования.

### 1.3 Нормативная и методологическая основа

Разработка ведётся в рамках описания продуктового кейса чемпионата «Клинический компас 2026» (индустриальный партнёр — ООО «Авинейро», ГК «ХимРар»; методологическая база — НМИЦ ПН им. В.П. Сербского, Сеченовский Университет).

Разработка учитывает требования следующих нормативных актов и стандартов РФ:

- Федеральный закон №152-ФЗ «О персональных данных» (ст. 9, 10, 11, 22) — согласие, категории ПДн, биометрия, оператор/уведомление.
- Федеральный закон №323-ФЗ «Об основах охраны здоровья граждан в РФ», ст. 36.2 + приказ Минздрава России №965н — телемедицинские технологии, порядок оказания медпомощи.
- Постановление Правительства РФ №1119 «О требованиях к защите ПДн при их обработке в ИСПДн».
- Приказ ФСТЭК России №21 — состав и содержание мер защиты для ИСПДн.
- ГОСТ Р 56939-2016 (защита информации при разработке ПО), ГОСТ Р ИСО/МЭК 12207-2010 (процессы жизненного цикла), ГОСТ Р МЭК 62304-2013 (жизненный цикл ПО медицинского назначения — как путь регистрации), ГОСТ Р ИСО 14971-2011 (менеджмент риска).

> **Примечание (важное допущение):** MVP настоящего прототипа **не является регистрируемым медицинским изделием** (допущение A4 из аналитики). Настоящее ТЗ фиксирует требования к прототипу; конструкторские решения (в первую очередь по ГОСТ Р МЭК 62304 и 14971) проектируют путь к последующей регистрации, но полный файл жизненного цикла медизделия в объём настоящей работы не входит.

## 2. Основания для разработки

### 2.1 Основание

Основание — потребность в демонстрации работающего прототипа на кейс-чемпионате «Клинический компас 2026» (предзащита 28.10.2026, демо-день 30.10.2026), в соответствии с описанием задачи чемпионата: «прототип цифрового ассистента врача для диагностики и ведения пациентов с тревожно-депрессивной симптоматикой — от скрининга до отслеживания динамики лечения».

### 2.2 Организационный контекст

Работа выполняется междисциплинарной командой в составе не менее одного медицинского и не более двух технических специалистов (допущение A5). Команда действует на принципах соревнования: финальное решение врача, клиническая валидность и безопасность (включая эскалацию суицидального риска) имеют приоритет над объёмом функций.

### 2.3 Цель и назначение разработки

Обеспечить между визитами пациента к врачу:

1. структурированный скрининг с расчётом баллов валидированных шкал;
2. расчёт триаж-уровня (зелёный/жёлтый/красный) по клиническим порогам;
3. автоматическую эскалацию при выявлении высокого/суицидального риска;
4. ежедневный мониторинг (чек-ины) и построение трендов;
5. передачу врачу сводных данных (риск, динамика, история, дневник) за один экран.

Разработка ведётся с целью прохождения предзащиты (топ-3) и сильного выступления на демо-дне, а также демонстрации архитектурной ценности (переиспользуемое клиническое ядро / SDK) для индустриального партнёра.

## 3. Назначение разработки

### 3.1 Функциональное назначение

Программное обеспечение предназначено для:

- проведения скрининга по **валидированным** опросникам (PHQ-9, GAD-7, HADS-A, HADS-D) с автоматическим расчётом баллов и интерпретацией;
- определения уровня риска (**триажа**) по клиническим порогам;
- выявления суицидального риска и немедленной эскалации (контакты помощи + уведомление врача);
- ежедневного мониторинга состояния через адаптивные короткие чек-ины и построения трендов;
- ведения дневника самочувствия (заметки, настроение, сон);
- предоставления врачу панели с картой рисков, графиками динамики и историей;
- rule-based чата поддержки (FAQ / горячая линия);
- соблюдения требований 152-ФЗ (согласие, аудит доступа, append-only журнал).

### 3.2 Целевое назначение и пользователи

**Пациент (18+, лёгкая–средняя тяжесть тревоги/депрессии):** самостоятельное прохождение скринингов и чек-инов, ведение дневника, доступ к динамике своего состояния, явная эскалация к помощи при высоком риске.

**Врач (психиатр/психотерапевт/ординатор):** просмотр списка пациентов по уровню риска, графика динамики, истории заполнений, дневника; обоснование решений.

**Администратор:** управление журналом аудита (append-only), подтверждение соблюдения 152-ФЗ.

### 3.3 Эксплуатационное назначение

Программное обеспечение функционирует в контуре, защищённом в соответствии с требованиями к ИСПДн категории 1 (целевой уровень защищённости УЗ-2). Использует TLS 1.2+, хранение данных в зашифрованном виде, обязательную 2FA для клинических/административных ролей, read-only журнал аудита.

## 4. Требования к программе (программному изделию)

### 4.1 Требования к функциональным характеристикам

Реализуемые требования соответствуют MVP-скоупу (F1–F8) из аналитики:

| Код | Требование |
|---|---|
| F1 | Каталог валидированных шкал (PHQ-9, GAD-7, HADS-A, HADS-D) с русскоязычными текстами и идентификацией тревоги/депрессии. |
| F2 | Скрининг: заполнение шкалы → расчёт балла → интерпретация + триаж-уровень (зелёный/жёлтый/красный) по клиническим порогам. |
| F3 | Эскалация безопасности: флаг суицидального риска (п.9 PHQ-9) → немедленное уведомление, контакты горячей линии (8-800-2000-122, 112), уведомление врача. |
| F4 | Мониторинг: ежедневные чек-ины (генерация коротких анкет из заполненной шкалы), тренды баллов во времени. |
| F5 | Врачебная панель: список пациентов по уровню риска, график динамики, история заполнений. |
| F6 | Дневник самочувствия: заметки, настроение, сон. |
| F7 | Чат-поддержка: FAQ / горячая линия, rule-based (LLM опционально). |
| F8 | Согласие на обработку ПДн (152-ФЗ) и аудит доступа. |

Каждое требование покрывается автоматизированным тестом: см. карту соответствия (Приложение Б настоящего ТЗ) и `docs/06-TDD.md`.

### 4.2 Требования к триажу и эскалации (клинические)

Триаж-уровень определяется **детерминированной чистой функцией** от балла шкалы, порога тяжести и риск-флагов:

- GREEN / YELLOW / RED по порогам каждой шкалы;
- флаг **SUICIDAL_IDEATION** — при ответе на суицидальный пункт шкалы ≥ 1;
- флаг **SEVERE_SYMPTOMS** — при достижении баллом порога SEVERE собственной шкалы;
- при триаже RED — создание записи эскалации в той же транзакции, уведомление врача и вывод контактов помощи.

> Клинические пороги и суицидальный пункт помечены в аналитике как **[TBD — подтвердить медиком команды]**: финальные числовые значения уточняются до открытия 15.10.2026. Механизм, пороговые шкалы и правила — инвариантны и не зависят от уточнения чисел.

### 4.3 Количественные характеристики (измеримые в демо)

| Показатель | Значение |
|---|---|
| Время прохождения скрининга 3 шкал | < 3 мин |
| Время срабатывания эскалации красного риска | < 1 с (от ответа до commit) |
| Выдача списка пациентов и отчёта врачу | за 1 экран |
| Доля веток ядра, покрытых тестами | ≥ 95% |

### 4.4 Требования к интерфейсу

- Пациентский интерфейс: адаптивный веб (поддержка мобильных устройств — обязательный horizontal-scroll для таблиц), вкладки «Скрининг / Чек-ин / Дневник / Чат / Мой тренд».
- Врачебный интерфейс: фильтр по триажу (All/GREEN/YELLOW/RED), отчёт пациента с графиком динамики, историей, дневником и эскалациями.
- Админ-интерфейс: журнал аудита (append-only), колонки время/действие/объект/актор/IP.
- Язык интерфейса: русский.

### 4.5 Требования к надёжности

- При недоступности внешних сервисов (LLM-чат, TTS) система остаётся работоспособной: внешние сервисы изолированы через SPI с офлайн-моками.
- Журнал аудита защищён от правки на уровне БД (только append): row-level BEFORE UPDATE OR DELETE триггер + statement-level BEFORE TRUNCATE триггер.
- Перезапуск/ресидинг демо-данных — через контролируемый путь (seed `--reset`), не ломающий инварианты.

### 4.6 Требования к безопасности и конфиденциальности

- TLS 1.2+ с HSTS (терминация — на nginx).
- Шифрование данных в покое (AES-256 через KMS).
- Обязательная 2FA (TOTP) для ролей CLINICIAN и ADMIN.
- RBAC + привязка «врач→пациент» (clinician_roster) на уровне сервисного слоя.
- Append-only аудит доступа к специальным категориям данных.
- Хостинг на территории РФ; TTS/LLM изолированы за прокси с протоколируемой передачей.
- Обязательное согласие на обработку ПДн (152-ФЗ, ст. 9 ч. 4 — письменное с обязательными реквизитами) до работы с данными; отсутствие согласия → отказ в доступе.

### 4.7 Требования к эргономике и эксплуатации

- Время отклика API p95 < 300 мс (измеряемое в нагрузочном тесте).
- Демо-данные генерируются детерминированным симулятором (seed) с реалистичными траекториями (включая RED-пациентов).
- Регистрация и согласие пациента — за один заход без вмешательства администратора.

### 4.8 Требования к составу и параметрам технических средств

Программное обеспечение является веб-приложением (SPA + API). Минимальная конфигурация для развёртывания демо — один сервер/Docker-хост с Docker Compose (postgres + api + ui + seed). Специальных требований к конкретным типам ЭВМ не предъявляется; клиент — любой современный браузер (desktop/mobile).

### 4.9 Требования к информационной и программной совместимости

- Ядро (клинический движок) — Python 3.12, чистые функции, распространяется как пакет `clinical-compass-core` без внешних зависимостей (SDK).
- API — Python 3.12, FastAPI, SQLAlchemy 2, Alembic, Postgres 16.
- UI — React 18 + Vite + TypeScript.
- Взаимодействие — REST (JSON), RFC 7807 problem+json для ошибок.

### 4.10 Специальные требования (научно-клиническая достоверность)

- Шкалы — валидированные русскоязычные версии PHQ-9, GAD-7, HADS-A, HADS-D.
- Ядро не содержит клинических ярлыков (депрессия/тревога): движок оперирует данными шкал, риск-флаги обобщённые (SUICIDAL_IDEATION, SEVERE_SYMPTOMS); маппинг в диагноз — функция врача, вне ядра.
- Отсутствует автоматическая постановка диагноза.

- **Критерий приёмки UI (демо)**: e2e-сценарий питча проходит против поднятого stack; UI работает на мобильной ширине (горизонтальный скролл таблиц).
- **Приёмка у заказчика/жюри**: демонстрация на предзащите (28.10) и демо-дне (30.10) работает без багов; демо-данные правдоподобны.
