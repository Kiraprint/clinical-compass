# 18. Клинические сессии врача: календарь, ИИ-протокол, ЭЦП, передача в ЕМИАС

Версия документа: 0.1 · статус: контракт (реализуется по частям, §11) · 2026-10-26

Документ фиксирует **контракт** четырёх связанных возможностей врача и границы между ними:
календарь приёмов (FR-38), ИИ-ассистент сессии и протокол приёма (FR-39), электронная подпись
и PDF-документ (FR-40), передача подписанного документа в ЕМИАС (FR-41). Контракт написан до
реализации (docs/03 §1 п.7, docs/05): реализация каждого блока идёт отдельным PR по этому тексту.

Порядок PR и зависимость контрактов — §11. Ни один блок не меняет чужие контракты: если
реализация требует отступления, правится этот документ тем же PR.

## 1. Границы и клинические красные линии

1. Протокол сессии — **юридически значимая запись приёма** (дневник наблюдения / протокол
   осмотра врача-психиатра, §5), а не «заметка ИИ». ИИ формирует **черновик**; запись становится
   документом только после подтверждения врачом и УКЭП.
2. ИИ **никогда** не формирует разделы «Диагноз» и «Лечение»: они приходят из данных карточки
   (МКБ-код из последней оценки, назначения из `prescriptions`) и заполняются/подтверждаются
   врачом вручную. Модель, вернувшая эти ключи, игнорируется (тест-инвариант, §5.3).
3. Аудиозапись сессии — **отдельное согласие** (`clinical_sessions.audio_consent`), не покрытое
   общим согласием 152-ФЗ: без него запись/загрузка аудио запрещена (422 `AUDIO_CONSENT_REQUIRED`),
   а ручной протокол остаётся доступен.
4. Аудио и расшифровка — спецкатегория ПДн. В БД и на диске только шифротекст (§4.6), в логи и
   аудит — ids, длительности, категории масок; никогда — текст.
5. Текст расшифровки уходит в LLM **только после деперсонализации** (docs/12): структурные ПДн +
   ML-маскирование + deny-list ротера. В `CC_PROD_MODE` недоступный ML-backend = 503
   `DEPERSONALIZATION_UNAVAILABLE` и **никакой** отправки сырого текста.
6. ИИ-ассистент — **опциональный** блок: `CC_SESSION_AI_ENABLED=false` по умолчанию выключает
   загрузку аудио и черновики; календарь, ручной протокол, подпись и передача работают без него.

## 2. Роли, доступ, аудит

| Действие | CLINICIAN | ADMIN |
|---|---|---|
| Календарь и сессии своих пациентов | да, только roster (`require_roster`) | нет |
| Чужой пациент / чужая сессия | 403 `NO_ROSTER`, 404 `SESSION_NOT_FOUND` | — |
| Просмотр аудита | — | `GET /admin/audit` (как сейчас) |

- Каждый пациентский endpoint дополнительно требует **активное согласие** пациента
  (`require_patient_consent`), как в FR-31/FR-37.
- `patient_id` сессии всегда берётся из БД сессии, а не из тела запроса: IDOR-инвариант (R5).
- Аудит (append-only, `services.audit.record`) — обязательные коды:

| Код | Когда |
|---|---|
| `APPOINTMENT_CREATE` / `APPOINTMENT_UPDATE` | создание / правка записи календаря |
| `SESSION_START` / `SESSION_FINISH` | старт (в т.ч. offline) / завершение сессии |
| `SESSION_CONSENT_UPDATE` | переключение согласия на аудиозапись (`audio_consent`) |
| `SESSION_AUDIO_UPLOAD` | загрузка записи |
| `SESSION_TRANSCRIBE` | расшифровка завершена/упала |
| `SESSION_PROTOCOL_DRAFT` | черновик от LLM |
| `SESSION_PROTOCOL_EDIT` | правка разделов врачом |
| `SESSION_PROTOCOL_APPROVE` | подтверждение врачом |
| `SESSION_PROTOCOL_SIGN` | наложение УКЭП |
| `SESSION_PROTOCOL_PDF` | генерация PDF |
| `EMIAS_SUBMIT` | отправка в ЕМИАС/РЭМД |

Аудит фиксирует только ids (`action`, `object_type`, `object_id`): категории масок, модель и длительности в аудит не пишутся — они в ответах API и логах без текста.

## 3. Модель данных

Все таблицы — в `api/app/models.py`, миграция — одна (`…_sessions_protocol`), `down_revision` =
текущая голова. Свободный текст — только `EncryptedText` (pgcrypto) или шифрованный артефакт (§4.6);
jsonb хранит только структурированные, не свободнотекстовые поля. `sections` (§5) — тоже
`EncryptedText`: шифрование делает СУБД (pgcrypto, `pgp_sym_encrypt` с ключом `CC_DATA_KEY`),
в колонке лежит `bytea`-шифротекст, в приложении plaintext существует только в памяти запроса.

|---|---|---|

### 3.3 `visit` — связь с историей приёма

`visits` получает `session_id uuid NULL UNIQUE FK clinical_sessions` (миграция та же). Завершение
сессии создаёт `Visit` (`source='local'`, `visited_at = started_at`, `duration_min`, `notes` =
сводка подтверждённого протокола ≤ 2000 символов, иначе пусто) — приём появляется в карточке
пациента, как в FR-23. Идемпотентность: повторный `finish` не создаёт вторую запись (по
`session_id`).

### 3.5 `session_transcripts` — метаданные расшифровки

`id`, `session_id` (UNIQUE FK), `language` char(2) default `ru`, `model` varchar(64),
`duration_sec` int, `segments_artifact_id` FK `document_artifacts`, `mask_categories` jsonb
(`{"PER": 4, "LOC": 1, "PHONE": 2}`), `depersonalized` bool, `created_at`.
Текст сегментов — только в артефакте (шифрован), в jsonb его нет.

FR-42 (диаризация, PR P7) добавляет три поля:

| Поле | Тип | Смысл |
|---|---|---|
| `diarized` | bool default `false` | сайдкар реально разделил говорящих; `false` — честная деградация |
| `speaker_roles` | jsonb NULL | `{"A": "clinician", "B": "patient"}`; `NULL` — роли не назначались (кластеров не два) |
| `speaker_roles_assumed` | bool default `false` | `true` — роли проставлены автоматически, врач их не подтверждал |

Артефакт расшифровки хранит на сегмент `{start, end, speaker, role, text}`, где
`speaker` — метка кластера (`A`/`B`), `role` — `clinician | patient | unknown | null`.
`PATCH …/transcript/speakers` перешифровывает артефакт с новыми ролями, чтобы UI и
черновик протокола не разъехались.

### 3.8 `emias_deliveries` — передачи в ЕМИАС

| Поле | Тип | Правила |
|---|---|---|
| `id` | uuid PK | |
| `session_id` | uuid FK `clinical_sessions` | NOT NULL, индекс `(session_id, submitted_at)` |
| `protocol_id` | uuid FK `session_protocols` | NOT NULL, UNIQUE — одна строка на версию протокола |
| `status` | varchar(16) | check `queued \| sending \| registered \| rejected \| failed` |
| `local_document_uid` | uuid | NOT NULL, UUIDv5(`protocol_id:version`) — ключ идемпотентности РЭМД |
| `document_sha256` | char(64) | sha256 отправленных байт СЭМД (не сами байты: они в артефактах) |
| `kind` | int | вид СЭМД, НСИ 1520 (по умолчанию 34) |
| `request_id` | varchar(64) NULL | идентификатор запроса стороны РЭМД; индекс |
| `external_id` | varchar(64) NULL | `emdr_id` из callback |
| `attempts` | int | число **отправок** (ретраи HTTP внутри одной отправки не считаются) |
| `last_error_code`, `last_error_message` | varchar(64/400) NULL | код НСИ-каталога и текст последней ошибки |
| `result` | jsonb NULL | ответ РЭМД как есть (`message_type`, `status`, `emdr_id`, `errors[]`), без СЭМД и ПДн; при протухании `sending` — `{"status": "error", "error_code": "CALLBACK_TIMEOUT"}` |
| `submitted_at`, `updated_at` | timestamptz | `now()` |
| `registered_at` | timestamptz NULL | момент `registered` по callback |

Инварианты: терминальные статусы `registered`/`rejected` не меняются callback'ом и повторным
submit; `failed` — транспортная ошибка после всех ретраев, повторная отправка разрешена тем же
`local_document_uid`; одна строка на протокол (`UNIQUE(protocol_id)`), потому что новый контент —
это новая версия протокола. При `registered` версия протокола переходит в `submitted`. СНИЛС и
ФИО в таблице не хранятся.

### 3.9 `session_chat_messages` — диалог врача по сессии (FR-44, PR P9)

| Поле | Тип | Правила |
|---|---|---|
| `id` | uuid PK | |
| `session_id` | uuid FK `clinical_sessions` | NOT NULL, индекс `(session_id, created_at)` |
| `clinician_id` | uuid FK `users` | NOT NULL — автор реплики-вопроса; у роли `assistant` тот же id: диалог ведёт один врач |
| `role` | varchar(16) | check `clinician \| assistant`; пациента в диалоге нет |
| `content_cipher` | bytea | pgcrypto (`EncryptedText`, ключ `CC_DATA_KEY`): вопрос врача может содержать ПДн. У `assistant` — шифрованный JSON `{answer, citations, proposal}` |
| `created_at` | timestamptz | время реплики задаёт api, а не `now()`: обе реплики одного хода пишутся в одной транзакции и иначе получили бы одинаковую метку — порядок истории стал бы случайным |

Инварианты: в аудит уходят только id сессии (`SESSION_CHAT_ASK`), текста реплик в журнале нет;
в LLM уходит замаскированный текст (маскирование — на каждом вызове, а не при записи: иначе врач
не увидел бы свою реплику); цитаты и `proposal` — часть того же шифрованного сообщения, отдельных
открытых jsonb-колонок нет.


## 4. API (prefix `/api/v1`)

Общие правила: 403 `NO_ROSTER` / 403 `CONSENT_REQUIRED` (существующие), 404 `SESSION_NOT_FOUND`
(чужая сессия неотличима от несуществующей), ошибки — RFC 7807 (`Problem`), пагинация —
`limit`+`offset` с потолком 200.

### 4.1 Календарь

| Метод | Путь | Тело / параметры | Ответ |
|---|---|---|---|
| GET | `/clinician/appointments` | `from`, `to` (обязательны, ≤ 62 дней), `patient_id?` | `{items: [Appointment]}` по `starts_at` |
| POST | `/clinician/appointments` | `{patient_id, starts_at, duration_min?, channel?, location?}` | 201 `Appointment`; 409 `SLOT_CONFLICT` |
| PATCH | `/clinician/appointments/{id}` | `{starts_at?, duration_min?, channel?, status?, location?}` | 200 `Appointment`; 409 `SLOT_CONFLICT`, 409 `APPOINTMENT_NOT_ACTIVE` |
| POST | `/clinician/appointments/{id}/start` | `{}` | 201 `{session_id}` (или 200 существующей) |

`Appointment` = `{id, patient_id, patient_fio, starts_at, duration_min, channel, status, location,
has_session}`.

### 4.2 Сессии

| Метод | Путь | Тело / параметры | Ответ |
|---|---|---|---|
| POST | `/clinician/sessions` | `{patient_id, channel?, appointment_id?, audio_consent?}` — offline/внеплановый приём | 201 `Session` |
| GET | `/clinician/sessions` | `from`, `to`, `patient_id?`, `status?` | `{items: [Session]}` |
| GET | `/clinician/sessions/{id}` | — | `SessionDetail` (сессия + протокол + артефакты + подпись + передача) |
| POST | `/clinician/sessions/{id}/finish` | `{duration_min?}` | 200 `Session` + созданный `visit_id` |
| PATCH | `/clinician/sessions/{id}` | `{audio_consent}` | 200 `Session` |

`Session` = `{id, appointment_id, patient_id, patient_fio, channel, started_at, ended_at, status,
audio_consent, ai_status, protocol: {version,status}|null}`.

В `PATCH /clinician/sessions/{id}` поле `audio_consent` **обязательно** и принимается только как
JSON-`true`/`false`: пустое тело, `null` и lax-строки (`"yes"`, `"on"`) → 422 `VALIDATION`.
`POST /clinician/sessions` принимает `audio_consent` опционально (default `false`), но по той же
строгой схеме.

### 4.3 ИИ-ассистент (FR-39, PR P3)

| Метод | Путь | Тело | Ответ / ошибки |
|---|---|---|---|
| POST | `/clinician/sessions/{id}/audio` | multipart `file` | 201 `{artifact_id, size_bytes}`; 422 `AUDIO_CONSENT_REQUIRED`; 413 `AUDIO_TOO_LARGE`; 415 `AUDIO_UNSUPPORTED`; 409 `SESSION_FINISHED`; 503 `SESSION_AI_DISABLED` |
| POST | `/clinician/sessions/{id}/transcribe` | `{}` | 202 `{ai_status: "transcribing"}`; 409 `AUDIO_MISSING`; 409 `AI_BUSY` (расшифровка этой сессии уже идёт, в т.ч. в другом воркере); 409 `SESSION_FINISHED`; 503 `SESSION_AI_DISABLED` |
| GET | `/clinician/sessions/{id}/transcript` | — | `{segments: [{start,end,speaker,role,text}], model, duration_sec, mask_categories, depersonalized, diarized, speaker_roles, speaker_roles_assumed}`; 404 `TRANSCRIPT_MISSING` |
| PATCH | `/clinician/sessions/{id}/transcript/speakers` | `{roles: {"A": "clinician", "B": "patient"}}` | 200 — расшифровка с ролями; 422 `VALIDATION` (не clinician/patient/unknown), 422 `SPEAKER_ROLE_DUPLICATE` (две одинаковые роли), 422 `SPEAKER_UNKNOWN` (метки нет в расшифровке); 404 `TRANSCRIPT_MISSING`/`SESSION_NOT_FOUND`; 403 `NO_ROSTER`/`CONSENT_REQUIRED`; 503 `SESSION_AI_DISABLED` |
| POST | `/clinician/sessions/{id}/protocol/draft` | `{}` | 201 `Protocol` (`source='llm'`, `needs_review`, `sections.sources`); 409 `TRANSCRIPT_MISSING`; 409 `PROTOCOL_LOCKED`; 503 `MODEL_NOT_CONFIGURED`, 503 `DEPERSONALIZATION_UNAVAILABLE`, 503 `DRAFT_FAILED` (модель дважды не вернула валидный JSON). Недоступность KB — **не** ошибка: черновик без источников + `needs_review sources_unavailable` (§5.3); роли реплик (`Врач:`/`Пациент:` или метка кластера) уходят в промпт вместе с текстом |

Реализация (PR P3) уточняет контракт:

- расшифровка идёт **фоновой задачей процесса API** (`asyncio` + `anyio.to_thread`,
  без Celery): 202 возвращается сразу, `clinical_sessions.ai_status` меняется
  `transcribing → transcribed | failed`, код сбоя — в `ai_error` (detail сессии):
  `AUDIO_MISSING`, `TRANSCRIPT_TOO_LARGE`, `ML_UNAVAILABLE`,
  `DEPERSONALIZATION_UNAVAILABLE`, `TRANSCRIBE_FAILED`. Текста и диагностики
  сайдкара в `ai_error` нет;
- **сырой (до маскирования) текст расшифровки не сохраняется вообще** — маска
  применяется до записи артефакта, поэтому «показать врачу исходную речь» этим
  API нельзя (осознанное ограничение: спецкатегория ПДн в БД не нужна, а
  правки врач вносит в протокол, а не в расшифровку);
- черновик LLM правит **активный draft** на месте (как `PUT …/protocol`), версии
  не плодятся; подтверждённая/подписанная/переданная запись не перезаписывается —
  `409 PROTOCOL_LOCKED`;
- `needs_review` черновика (§5.3): `{section:'mental_status.suicidal_risk',
  reason:'clinical_risk'}` — всегда; `{section:'llm_output',
  reason:'unexpected_section', key}` — модель вернула ключ вне §5.1;
  `{section, reason:'source_missing' | 'drug_not_in_source' |
  'dosage_not_in_source' | 'icd10_unverified' | 'sources_unavailable'}` — grounding
  диагноза/лечения (FR-43, §5.3); `{section, reason:'dosage_in_draft'}` — дозировка
  прозой в нарративе; `{section, reason:'invalid_item' | 'too_many_items'}` —
  элемент модели не по схеме / позиций лечения больше 20;
- перед вызовом LLM сервис ищет обоснования в KB (`services.agent.AgentFactory.search_kb`,
  темы `ЛЕКАРСТВА`, `РЕКОМЕНДАЦИИ`, `ШКАЛЫ`, `ТРИАЖ`, лимит `CC_SESSION_AI_SOURCES`):
  чанки уходят в промпт нумерованным списком, а их id — в модель ответа как
  `sources` (§5.4). Red-line гейт поиска обходится ЯВНЫМ параметром
  `allow_redline=True` только здесь: в чате врача/пациента гейт остаётся;
- `passport` заполняет сервис (время приёма, канал, активное ИДС пациента), модель
  его не заполняет. `diagnosis`/`treatment` модель МОЖЕТ предложить — но только со
  ссылками на полученные источники, иначе элементы отбрасываются (§5.3);
- `depersonalized` — **не константа**: `true` только если маскировал ML-детектор
  (`CC_DEPERSONALIZE_NER≠off`) и он не деградировал до regex/deny-list в этом
  процессе; иначе `false`, и врач видит, что расшифровка защищена слабее. В
  `CC_PROD_MODE` при `CC_SESSION_AI_ENABLED=true` выключенный NER — **ошибка
  старта** (`CC_DEPERSONALIZE_NER=off` несовместим с продом: аудио и расшифровка
  — тот же egress ПДн, что и чат);
- `AI_BUSY` держится **в БД** (`pg_try_advisory_lock` по id сессии, отдельное
  соединение на время расшифровки), поэтому несколько uvicorn-воркеров не
  запускают два прогона ASR; in-process реестр остаётся быстрой отсечкой.
  Если `engine` не сконфигурирован (сборка без БД как арбитра), «занято»
  решает только in-process реестр — это осознанный фолбэк, а не вечный 409;
- зависшие расшифровки снимаются реапером: `ai_started_at` + порог
  `CC_SESSION_AI_TIMEOUT × 2` → `ai_status='failed'`, `ai_error='TRANSCRIBE_INTERRUPTED'`
  (при старте приложения и перед каждым запуском расшифровки). Отмена задачи
  (остановка процесса) тоже не оставляет `transcribing`: захват освобождает
  `add_done_callback`;
- новая загрузка аудио заменяет прежнюю запись: старые артефакты `audio` и
  `transcript` удаляются, `GET …/transcript` снова 404; повторная расшифровка
  удаляет артефакт прошлой расшифровки (не остаётся сиротой в списке сессии);
- загрузка аудио и расшифровка на завершённой сессии (`status='finished'`) —
  409 `SESSION_FINISHED` (статус не откатывается в `recording`);
- битый `multipart` (нет boundary, обрезанное тело) и прочие `HTTPException`
  Starlette отдаются тем же Problem-конвертом (`code: VALIDATION_ERROR` /
  `NOT_FOUND` / …), а не `{"detail": …}`.

#### Диаризация: как реплики делятся на врача и пациента (FR-42, PR P7)

Сайдкар размечает спикеров по запросу `diarize=true`; api просит его всегда, гейт
один — `CC_ML_DIARIZE` на стороне сайдкара.

**Бэкенды** (`CC_ML_DIARIZE_BACKEND`; обе реализации — за одним интерфейсом,
метки кластеров нумеруются одинаково):

| Бэкенд | Лицензия / вес | Замер (50.6 с русского диалога) | Статус |
|---|---|---|---|
| `sherpa` (дефолт) | ONNX из релизов k2-fsa: segmentation MIT + CAM++ Apache-2.0, 33 МБ; `sherpa-onnx` 2.0, CPU | 12/12 реплик верно, RTF 0.08–0.12 при load ≈6/16, до 0.16 на загруженном хосте (2 потока CPU), VRAM 0, RSS ~1.3 ГБ | в образе `ml`, качает `ml-warmup` |
| `sortformer` | `nvidia/diar_streaming_sortformer_4spk-v2.1`, NVIDIA Open Model License (коммерческое использование разрешено); `nemo_toolkit[asr]` — свой torch 2.14.1+cu130, venv 6.3 ГБ | 12/12 реплик верно, RTF 0.33 (GPU), 918 МБ VRAM, RAM-пик 2.5 ГБ, до 4 спикеров | проверен вживую, но нужен отдельный образ (конфликт с пином torch 2.11) |

`pyannote/speaker-diarization-community-1` и `pyannote/segmentation-3.0` на HF
**gated** (ручное принятие условий, веса не перераздаваемы) — поэтому используем
свободный ONNX-порт k2-fsa. `BUT-FIT/diarizen-wavlm-large-s80-md` и
`nvidia/diar_sortformer_4spk-v1` — **CC-BY-NC-4.0**, исключены как некоммерческие.
Если бэкенд не поднялся (нет `nemo_toolkit`, нет весов, опечатка в имени), ответ
остаётся 200 с `diarized=false`, а в лог один раз идёт код
`diarize_backend_unavailable`.

- **Модели** (ONNX, CPU, без HF-гейта и без pyannote.audio): pyannote
  segmentation 3.0 (MIT, 6 МБ) для границ реплик + 3D-Speaker CAM++ zh/en
  advanced (Apache-2.0, 28 МБ) для эмбеддингов голоса, кластеризация AHC в
  sherpa-onnx. Веса качает `ml-warmup` из релизов k2-fsa в том же томе
  `ml-models` (`/models/diarize`), sha256 зафиксирован в `ml/models.py`.
- **Число кластеров фиксировано (2)**: приём ведёт врач с пациентом; автопорог давал
  третий «спикер» из шума VAD. Одинокую запись модель тоже делит на два кластера —
  поэтому роли по умолчанию помечены `speaker_roles_assumed=true`, а UI просит
  врача их подтвердить.
- **Сшивка с ASR**: каждый сегмент faster-whisper получает кластер с максимальным
  перекрытием по времени; сегмент без перекрытия (тишина/шум) остаётся `speaker: null`.
- **Точность** (замер на 50.6 с синтетического русского диалога, две голосовые
  модели piper, 12 чередующихся реплик): 12/12 реплик размечены верно, RTF 0.08–0.12
  при load ≈6/16 (2 потока CPU), на загруженном хосте — до 0.16 (VRAM
  не используется). На реальном двухголосом английском
  тесте k2-fsa кластеры чистые, но речевые пересечения там редкие — реальную
  клиническую запись этот замер не заменяет.
- **Ограничения (реализованы явно)**: ровно два участника; пересекающаяся речь
  относится к говорящему с большим перекрытием, а не делится; реплики короче
  ~0.3 с отбрасываются (`min_duration_on`); качество падает при одном микрофоне в
  шумном кабинете и при схожих голосах; диаризация — подсказка, роли подтверждает врач.
- **Деградация честная**: нет весов, `CC_ML_DIARIZE=0` или сбой — ответ 200,
  `diarized=false`, `speaker: null`, `degraded=true` (причина в логах сайдкара);
  api сохраняет такую расшифровку, UI показывает «говорящие не разделены».
- **Роли**: кластер, заговоривший первым, — врач (`assumed=true`); кластеров не два
  или диаризации нет — роли пустые, `assumed=false`. Врач переставляет роли
  `PATCH …/transcript/speakers`, после чего `assumed=false` и аудит
  `SESSION_TRANSCRIPT_SPEAKERS`. В LLM уходят подписи «Врач:/Пациент:», а не латиница.

### 4.6 Артефакты: хранение и шифрование

- Каталог — `CC_ARTIFACTS_DIR` (default `/var/lib/compass/artifacts`, в compose — volume);
  в тестах — `tmp_path`.
- Файл = AES-256-GCM (`cryptography`), ключ — HKDF от `CC_DATA_KEY` (тот же секрет, что pgcrypto),
  nonce в заголовке файла (`CCART1` + 12 байт nonce + ciphertext). `sha256` считается по шифротексту.
- Чтение — только через сервис `app/services/artifacts.py` (`put_bytes`/`get_bytes`), не напрямую.
- Аудио сессии **не проходит через `UploadFile`**: Starlette спулил бы загрузку >1 МиБ
  открытым текстом в `/tmp`. Роутер отдаёт `request.stream()`, сервис разбирает
  multipart на лету, шифрует порциями (`put_stream`) и рвёт соединение на
  `CC_SESSION_AUDIO_MAX_MB` — недописанный `.tmp` удаляется.
- Файл и строка `document_artifacts` пишутся разными шагами: отмена между
  `os.replace` и коммитом оставила бы шифротекст без ссылки, вне ретенции.
  На старте приложения свип удаляет файлы `CC_ARTIFACTS_DIR/<kind>/*.bin`, для
  которых нет строки в `document_artifacts` (в этот момент живых загрузок нет;
  `tmp/` разбирается отдельно по возрасту).
- Для ASR артефакт расшифровывается в файл `0600` под `CC_ARTIFACTS_DIR/tmp`
  (`iter_plaintext`/`decrypt_to_temp`) и уходит в сайдкар потоком (тело multipart
  не собирается в память); файл удаляется в `finally` — и при успехе, и при сбое.
  Это единственное окно открытого текста на диске, оно ограничено одним запросом
  к сайдкару и не переживает процесс: на старте из `tmp` удаляются файлы старше
  `CC_SESSION_AI_TIMEOUT × 2` (свежие не трогаем — при `WEB_CONCURRENCY>1` их
  может держать соседний воркер).
- Тело загрузки, разобранное на части, проверяется целиком: пустая файловая часть
  и вторая часть с `name="file"` — 422 `VALIDATION_ERROR` (тихо записать 0 байт
  или проигнорировать присланное аудио нельзя). Разделителем считается только
  `--boundary`, за которым идёт `\r\n` или `--`; иначе это байты записи.
- Потолки: аудио ≤ `CC_SESSION_AUDIO_MAX_MB` (default 200), расшифровка ≤ 5 МБ JSON, PDF ≤ 10 МБ.
- Удаление при отзыве согласия (`DELETE` спецкатегории) удаляет и артефакты сессий пациента.

## 5. Структура протокола приёма

### 5.1 Разделы

Соответствует требованиям к дневниковой записи / протоколу осмотра врача-психиатра
(Приказ Минздрава № 274н; Закон РФ № 3185-1; форма № 025/у и внутренние бланки МИС):

```json
{
  "passport": {
    "visit_at": "2026-10-26T10:00:00+03:00",
    "channel": "in_person",
    "legal_basis": "ИДС № 12 от 2026-05-04"
  },
  "complaints": "…",
  "anamnesis_morbi": "…",
  "mental_status": {
    "appearance_behavior": "…",
    "consciousness_orientation": "…",
    "perception": "…",
    "thinking_speech": "…",
    "emotions_volition": "…",
    "criticism": "…",
    "suicidal_risk": "…"
  },
  "somatic_status": "…",
  "diagnosis": { "syndrome": "…", "icd10": "F41.1", "rationale": "…", "sources": ["S1"] },
  "treatment": [ { "drug": "…", "dose": "…", "schedule": "…", "duration": "…",
                   "sources": ["S1"] } ],
  "recommendations": "…"
}
```

Нарративные разделы (`complaints`, `anamnesis_morbi`, `mental_status.*`, `somatic_status`,
`recommendations`) ИИ заполняет **черновиком** из расшифровки. `diagnosis` и `treatment`
ИИ тоже может предложить — но только со ссылками на чанки KB (FR-43, §5.3–5.4), и врач
их правит и утверждает сам. `passport` заполняет сервис (время приёма, канал, ИДС);
`diagnosis.icd10`/`treatment` врач может взять из карточки (`prescriptions`, последняя
оценка), но подписывает то, что видит в протоколе.

### 5.2 Валидация

- Потолки: `complaints` ≤ 4000, `anamnesis_morbi` ≤ 8000, каждый `mental_status.*` ≤ 2000,
  `somatic_status` ≤ 2000, `recommendations` ≤ 4000, `diagnosis.rationale` ≤ 2000,
  `treatment` ≤ 20 позиций, строка ≤ 500.
- Обязательны для `approve`: `passport.visit_at`, `passport.legal_basis`, `complaints`,
  `mental_status.suicidal_risk`, `diagnosis.icd10` (непустые). Пусто → 409 `PROTOCOL_NOT_READY`
  со списком разделов в `detail`.
- `diagnosis.icd10` — формат `^[A-Z]\d{2}(\.\d{1,2})?$` (МКБ-10), иначе 422.
- Канонический JSON: `json.dumps(sections, ensure_ascii=False, sort_keys=True, separators=(",",":"))`
  — именно эти байты хэшируются в `content_sha256` и подписываются. `sections.sources`
  (§5.4) входят в хэш: подписывается документ **вместе с обоснованием**.
- `sections.sources` (если есть): массив ≤ 50 записей, строковое поле ≤ 500,
  `quote` ≤ 2000, `used_by` — массив строк; иначе 422.
- `diagnosis.sources` и `treatment[i].sources` (если заданы) — массив строк, и каждый
  id обязан быть в `sections.sources` этого же документа; иначе 422
  `PROTOCOL_SOURCE_UNKNOWN` (UI мог склеить старый черновик с новой выдачей — тогда
  ссылка указывает в пустоту и подписанный документ врёт о своём обосновании).

### 5.3 Черновик ИИ: диагноз и лечение с обоснованием (FR-43)

Прежний запрет «ИИ не заполняет диагноз и лечение» снят **не полностью**, а заменён
контрактом с источниками. Модель МОЖЕТ предложить:

```json
{"diagnosis": {"syndrome": "…", "icd10": "F41.1", "rationale": "…", "sources": ["S1"]},
 "treatment": [{"drug": "…", "dose": "50 мг", "schedule": "…", "duration": "…",
                "sources": ["S1"]}]}
```

Что проверяется автоматически (`services.session_ai._sanitize`):

1. **Источник обязателен и только из выдачи.** `sources` — метки `S1…Sn` из промпта
   (допустим и id чанка). Пустой список или ссылка на несуществующий чанк → элемент
   отбрасывается, в `needs_review` добавляется `{"section": <раздел>,
   "reason": "source_missing"}`. Индекс у лечения — **сохранённый**:
   `treatment.<i>` считается по `sections.treatment` после уплотнения, а причина
   отброшенного элемента вешается на раздел `treatment` целиком (иначе бейдж
   приезжает к чужому препарату). Тот же reason ставится разделу, где модель
   сослалась в тексте на `[S9]`, которого в выдаче нет: текст остаётся, но
   утверждение не подтверждено.
2. **Препарат подтверждается источником.** Название препарата должно встречаться в
   тексте хотя бы одного указанного чанка: подстрокой либо как та же лексема (общий
   корень ≥ 5 букв, окончание расходится не больше чем на 2 буквы; для коротких
   названий ≤ 6 букв корень ≥ 4 — «литий» ↔ «литием»). «сертралин» ↔ «сертралина»
   — подтверждено, «пароксетин» ↔ «пароксизм» — нет. Название без слов ≥ 4 букв
   («АСК», «Mg», «Li») источником не подтверждается никогда. Иначе
   `{"reason": "drug_not_in_source"}`, но позиция остаётся — врач может знать больше
   модели.
3. **Доза — в том же чанке.** Токен дозы (`\d+([.,]\d+)?\s*(мг|мл|г|мкг|МЕ)`) должен
   встречаться в том же чанке, где найден препарат, с границей числа слева («50 мг»
   не подтверждается чанком «150 мг»); десятичный разделитель сравнивается в обе
   стороны (`0,5 мг` = `0.5 мг`). Иначе `{"reason": "dosage_not_in_source"}`,
   позиция остаётся.
4. **МКБ-10.** Формат `^[A-Z]\d{2}(\.\d{1,2})?$` проверяет `protocols.validate_sections`
   (422 `PROTOCOL_ICD10_INVALID`). Дополнительно код должен встречаться в тексте
   указанных чанков; справочника МКБ в МВП нет, поэтому неподтверждённый код даёт
   `{"reason": "icd10_unverified"}`, а код неверного формата выбрасывается (диагноз
   остаётся без кода — врач выбирает сам).
5. **`suicidal_risk`** из ИИ — ВСЕГДА `needs_review` (`reason: "clinical_risk"`).
6. **Никакой автоматической подписи.** Черновик никогда не переводит протокол в
   `approved`: утверждает врач через `POST …/protocol/approve`, и только при
   заполненных обязательных полях §5.2 (иначе 409 `PROTOCOL_NOT_READY`; `PUT` с
   невалидными разделами — 422).

Прочее:

- дозировка прозой в нарративных разделах (`recommendations` и др.) помечается
  `{"reason": "dosage_in_draft"}`: лечение живёт в `treatment`, где его проверяет
  grounding;
- ключ вне §5.1 → `{"section": "llm_output", "reason": "unexpected_section", "key": …}`,
  ключ отброшен;
- элемент не по схеме (не объект, пустой препарат, строка > 500) → `invalid_item`
  (отброшен); позиций лечения > 20 → `too_many_items` (лишние отброшены);
- **KB недоступна** (Qdrant/эмбеддер лежит, `CC_SESSION_AI_SOURCES=0`) — не 502 и не
  выдумка: черновик формируется без `sources`, плюс `{"section": "treatment",
  "reason": "sources_unavailable"}`; диагноз и лечение без источников при этом тоже
  отбрасываются (п. 1).

Промпт (`PROMPT_VERSION = "v2"`) содержит только деперсонализированный транскрипт и
блок `<<ИСТОЧНИКИ>>` с чанками KB (открытый корпус, ПДн пациента в нём нет); оба
блока объявлены данными, а не инструкциями.

### 5.4 `sections.sources` — формат обоснований

Черновик складывает полученные чанки в `sections.sources` (шифрованный канонический
JSON, входит в `content_sha256`):

```json
[{"id": "8f14e45f-…", "ref": "S1", "section": "ЛЕКАРСТВА",
  "title": "Сертралин: дозирование", "url": "https://…",
  "quote": "Сертралин назначают внутрь, стартовая доза 25–50 мг/сут…",
  "used_by": ["diagnosis", "treatment.0", "recommendations"]}]
```

- `id` — id точки Qdrant (стабилен для чанка); по нему ссылаются
  `diagnosis.sources` и `treatment[i].sources`;
- `ref` — метка из промпта (`S1`), она же на чипе в UI;
- `section` — раздел корпуса (`topic`), `title` — `source_title`, `url` — провенанс
  гайдлайна/статьи (у seed-чанков пусто);
- `quote` — короткий (~320 символов) фрагмент чанка: только открытый текст KB;
- `used_by` — что на источник опирается: `diagnosis`, `treatment.<i>`,
  `recommendations` и другие разделы, где модель поставила `[S1]`;
- текст разделов сохраняется как есть (со ссылками `[S1]`), чтобы врач видел связь
  «фраза ↔ источник».

## 6. Календарь: границы UX

- Вид «Месяц» (сетка 7×6) + список дня; без внешних библиотек дат — `Date`/`Intl` (`ru-RU`).
- Клик по дню → форма «Новый приём»: пациент (только roster), время, длительность (30/45/50/60/90),
  канал, кабинет. Перетаскивания и повторяющихся приёмов нет (вне MVP).
- Кнопка «Начать приём» в записи → `POST …/start`; кнопка «Начать приём без записи» → выбор
  пациента → `POST /clinician/sessions`.
- Сессия открывается в панели: таймер, «Завершить», редактор протокола (разделы §5.1) и две
  сворачиваемые карточки — «ИИ-ассистент» и «Документ».

Финальный UI-поток приёма (PR P6 `feat/session-docs-ui`) — сверху вниз по панели:

- **ИИ-ассистент** (§4.3): доступность определяет сервер (ответ `GET …/transcript`); при
  `503 SESSION_AI_DISABLED` карточка показывает «ИИ-ассистент выключен администратором» без
  кнопок. Дальше — согласие на аудиозапись (`PATCH …` c `audio_consent`, отдельное основание
  §1.3), запись через `MediaRecorder` (`audio/webm`, таймер, `track.stop()` на стопе и
  размонтировании) или файл, загрузка `POST …/audio`, «Расшифровать» → 202 и опрос детали
  сессии каждые 2 с (до 15 минут, стоп на `transcribed|failed`), просмотр деперсонализированной
  расшифровки (`mm:ss`, бейдж спикера, пометка о маскировании) и «Сформировать черновик
  протокола». Черновик только заполняет пустые разделы: введённый врачом текст не
  перезаписывается — расхождения выносятся блоком выбора, а разделы из `needs_review`
  помечаются бейджем с причиной. Коды `MODEL_NOT_CONFIGURED`, `DEPERSONALIZATION_UNAVAILABLE`,
  `AI_BUSY`, `TRANSCRIPT_MISSING`, `SESSION_FINISHED` показываются человеческим текстом.
- **Документ** (§7, §8): шаги «черновик → подтверждён → подписан → передан» с объяснением,
  чего не хватает, вместо мёртвых кнопок. «Подписать» — две подписи (врач + МО) с реквизитами
  сертификатов и примечанием о демонстрационном УЦ (§7.6); «Проверить подпись» — чип
  `valid|invalid|unknown_ca|expired|digest_mismatch` с причиной; «Скачать PDF» — blob с именем
  из `Content-Disposition` (`protocol-<version>.pdf`); «Передать в ЕМИАС» — 202 и опрос
  `GET …/delivery` до `registered|rejected|failed` (попытки, код и текст ошибки РЭМД, повтор
  только для `failed`). Подпись и доставка перечитываются из `SessionDetail` после каждой
  мутации; сбой опроса оставляет ручное «Обновить статус», а не вечный спиннер.

## 7. ЭЦП и электронный документ

Реализовано в PR P4 (`feat/ecp-pdf`). Подписывается **документ**, а не JSON протокола:
канонический JSON `sections` фиксируется хэшем `content_sha256` при approve (§5.2), но подпись
ставится над байтами СЭМД (CDA R2 XML), потому что именно они уйдут в РЭМД (§8).

### 7.1 Что подписывается и чем

| Слой | Значение |
|---|---|
| Объект подписи | СЭМД протокола — CDA R2 XML в кодировке UTF-8 (`document_artifacts.kind='protocol_cda'`) |
| Хэш | ГОСТ Р 34.11-2012, Стрибог-256 (OID `1.2.643.7.1.1.2.2`) |
| Подпись | ГОСТ Р 34.10-2012, 256 бит (OID `1.2.643.7.1.1.3.2`) |
| Ключи | ГОСТ Р 34.10-2012-256, кривая `id-tc26-gost-3410-2012-256-paramSetB` (`1.2.643.7.1.2.1.1.2`) |
| Контейнер | Отсоединённый CMS `SignedData` (CAdES-BES-структура): `eContent` **отсутствует**, подписанные атрибуты `content-type=data`, `message-digest`, `signing-time`; подписываются SET OF-байты атрибутов (`0x31`), в контейнере они `[0] IMPLICIT` (`0xA0`) |
| Библиотеки | `gostcrypto` (примитивы), `asn1crypto` (X.509 + CMS). `pygost` не используется (снят с PyPI), `endesive` — не подходит: встраивает содержимое в контейнер |

Две подписи на документ: `role='clinician'` — врач, ведущий сессию (п. 9 приказа Минздрава
России № 209н от 25.03.2026 — «ЭМД подписывается УКЭП лица, подписавшего документ»), и
`role='mo'` — уполномоченное лицо МО (п. 11 — вторая подпись нужна, когда документ требует
печати/штампа МО). Обе подписи ставятся над одними и теми же байтами СЭМД: `content_sha256`
у обеих строк `protocol_signatures` совпадает.

### 7.2 Формат сертификата (X.509 с ГОСТ-ключами)

Стандартный X.509 по RFC 9215, **без** двухслойной схемы (RSA-сертификат + привязка ГОСТ-ключа
внутри CMS): обходной путь не понадобился, потому что `asn1crypto` позволяет собрать
`SubjectPublicKeyInfo` с ГОСТ-алгоритмом.

- `SubjectPublicKeyInfo`: `algorithm = 1.2.643.7.1.1.1.1`, параметры — SEQUENCE с OID кривой
  `paramSetB`; `subjectPublicKey` — BIT STRING, содержащий DER `OCTET STRING(64)` координат
  `X‖Y` **little-endian** (RFC 9215 §4.3);
- `signatureAlgorithm` = `1.2.643.7.1.1.3.2` без параметров, `signatureValue` — 64 байта
  **`s‖r`** big-endian (RFC 9215 §3);
- `subject`: `CN=ФИО`, `O=<МО>`, `T=<должность>`, `C=RU`; СНИЛС — `subjectAltName`/`otherName`
  с OID `1.2.643.100.3` (тот же OID, что в квалифицированных сертификатах УЦ); если СНИЛС
  подписанта не сконфигурирован, расширение не добавляется и в PDF печатается «не указан» —
  значение не выдумывается;
- расширения: `basicConstraints`, `keyUsage` (лист — `digitalSignature + nonRepudiation`,
  УЦ — `keyCertSign + cRLSign`), `subjectKeyIdentifier`.

Демо-УЦ: `CN=Compass Demo CA`, самоподписанный, срок 10 лет. Хранится под
`CC_ARTIFACTS_DIR/_ca/`, права **0600**, каталоги — 0700. Сертификат и ключ лежат **одним**
файлом (`_ca/ca.pem`, `_ca/leaves/<hash>.pem`; прежние `_ca/ca.crt.pem`/`ca.key.pem` не
читаются — такие файлы удаляются вручную):
файл собирается во временном имени и появляется под итоговым через `os.link`, поэтому ни гонка
на холодном старте (`WEB_CONCURRENCY>1`), ни крах посреди записи не оставляют «смешанной пары»
или усечённого PEM; проигравший гонку читает готовую пару целиком. Осиротевшие `.<name>.<hex>.tmp` (обрыв процесса
между записью и `os.link`) вычищаются при инициализации каталога.
Ключ кэша листа — sha256(отпечаток УЦ, ФИО, должность, организация, СНИЛС, срок): поэтому
подпись, поставленная до рестарта, проверяется после него, а смена УЦ не оставляет листов,
выданных старым (иначе `sign` проходил бы, а `verify` навсегда отдавал `unknown_ca`). Внешний стенд подключается через
`CC_SIGNING_CA_CERT`/`CC_SIGNING_CA_KEY` (PEM-файлы). Закрытые ключи не попадают в git, БД,
логи и ответы API; наружу отдаются только серийный номер, издатель, срок действия и отпечаток.

### 7.3 Хранение артефактов

| Артефакт | `kind` | MIME | Когда создаётся |
|---|---|---|---|
| СЭМД | `protocol_cda` | `application/xml` | `POST …/protocol/sign`, один на версию |
| CMS-подпись | `signature` | `application/pkcs7-signature` | две на версию (врач + МО), ссылки в `protocol_signatures.cms_artifact_id` |
| PDF | `protocol_pdf` | `application/pdf` | первый `GET …/protocol/pdf`, повторный отдаёт те же байты (sha256 не меняется) |

Все три — шифрованные файлы по §4.6 (AES-256-GCM, sha256 по шифротексту), в имени файла нет ПДн.

### 7.4 Проверка подписи (`POST …/protocol/verify`)

Для каждой подписи: пересчёт Стрибог-256 сохранённых байт СЭМД и сравнение с
`protocol_signatures.content_sha256` → разбор CMS (хвостовые байты после `SignedData` →
`cms_malformed`) и проверка подписи по сертификату из контейнера → **сверка сертификата
контейнера со строкой подписи**: вложенный в CMS сертификат обязан совпасть с
`protocol_signatures.cert_der` (иначе подпись чужого УЦ или чужая CMS роли принималась бы как
наша → `invalid`); принимается только канонический DER-контейнер с `content-type = id-data` —
PEM/BER, неопределённая длина и хвостовые байты после `SignedData` → `cms_malformed`, а подмена
`content-type` в подписанных атрибутах → `content_type_invalid` → цепочка до демо-УЦ (имя издателя + подпись листа) и срок действия по
`cert_der` строки → привязка подписанта (врач = врач сессии, МО = настроенное лицо). Ответ:

| `status` | Причина |
|---|---|
| `valid` | обе подписи верны |
| `digest_mismatch` | байты СЭМД подменены (или `message-digest` в CMS не совпадает) |
| `unknown_ca` | сертификат выдан не нашим УЦ |
| `expired` | срок действия сертификата истёк/ещё не начался |
| `invalid` | нет подписи, битый контейнер/сертификат, контейнер не соответствует строке подписи, несовпадение подписанта |

Порядок итогового статуса — как в таблице (первое сработавшее); в `signatures[]` — статус
каждой подписи отдельно. Хэш в ответе — `document.digest` с явным `digest_algorithm =
GOST3411-2012-256` (это не SHA-256). Ошибки никогда не превращаются в 500: испорченный документ — это
результат проверки.

### 7.5 Печатная форма (`GET …/protocol/pdf`)

WeasyPrint (HTML/CSS → PDF, системные зависимости — Pango/HarfBuzz/Fontconfig и шрифты с
кириллицей в `api/Dockerfile`). Заголовок: МО, название документа, дата, id и версия
документа. Далее все заполненные разделы §5.1 (психический статус — 7 подразделов, лечение —
таблицей), затем блок на каждого подписанта: **«ПОДПИСАНО»**, роль, ФИО, должность, СНИЛС
(или «не указан»), издатель сертификата, серийный номер, срок действия, первые 16 hex
отпечатка, дата и время подписи. В подвале — «Страница X из Y» и `документ/версия`;
под блоками подписи — примечание «Демонстрационная подпись: УКЭП аккредитованного УЦ не
выдавалась». Доступен только после подписи (409 `PROTOCOL_NOT_SIGNED`).

### 7.6 Легальность: что настоящее, а что демонстрация

- **Настоящее**: алгоритмы и форматы (ГОСТ Р 34.10-2012 / 34.11-2012, X.509 по RFC 9215,
  отсоединённый CMS, CDA R2), проверяемость подписи независимыми средствами, неизменность
  подписанных байт, аудит.
- **Демонстрация**: УЦ. УКЭП по ФЗ-63 ст. 5 требует сертификата **аккредитованного** УЦ и
  СКЗИ класса КС1 и выше (приказ ФСБ № 796); без КриптоПро CSP/JaCarta валидную УКЭП выпустить
  нельзя. Наш «Compass Demo CA» — тестовый: своей юридической силы подпись не имеет, поэтому
  PDF прямо это печатает, а `verify` подтверждает только целостность и цепочку до демо-УЦ.
- **Отметка о подписи** соответствует п. 9 приказа Минздрава России № 209н от 25.03.2026
  («ПОДПИСАНО» вместо прежнего «ДОКУМЕНТ ПОДПИСАН ЭЛЕКТРОННОЙ ПОДПИСЬЮ»; приказ 947н
  недействующий). Вторая подпись МО — п. 11 того же приказа.
- **РЭМД**: с 01.01.2024 принимает только структурированные СЭМД (CDA), PDF не принимается;
  PDF — внутренний/печатный контур. Реальная передача — PR P5 (§8), `templateId` вида СЭМД
  задаётся профилем передачи, а не выдумывается здесь.
- **Чего нет**: CRL/OCSP и отзыв сертификатов, метки доверенного времени (CAdES-T), политики
  УЦ и квалифицированные расширения RFC 9215 §5. Для демо-контура и внутреннего аудита этого
  достаточно; для юридически значимого ЭДО нужен аккредитованный УЦ и СКЗИ.

## 8. Передача в ЕМИАС/ЕГИСЗ РЭМД (FR-41)

Направление — **исходящее**: подписанный СЭМД (CDA R2, `document_artifacts.kind='protocol_cda'`)
вместе с отсоединённой CMS (`kind='signature'`) уходит в REST-фасад РЭМД ЕГИСЗ. PDF/PNG не
передаются: с 01.01.2024 РЭМД принимает только структурированные документы. Пакет
`api/app/remd/` повторяет структуру inbound-интеграции `api/app/emias/`
(config → auth → client → mock), плюс `service.py` (статусная машина и БД) и `mapping.py`
(конверт, СНИЛС, GUID идемпотентности).

### 8.1 Мок РЭМД (`api/app/remd/mock.py`)

Самостоятельное FastAPI-приложение: `uvicorn app.remd.mock:app --port 8091` (в compose —
профиль `emias`, сервис `remd-mock`). Состояние — в памяти процесса, `reset_state()` для тестов.

| Метод | Путь | Поведение |
|---|---|---|
| POST | `/oauth/token` | `client_credentials` + Basic → `{access_token, token_type:"Bearer", expires_in:3600}`; `/remd/v1/*` требует Bearer |
| POST | `/remd/v1/register-document/` | конверт §8.2 → **202 `{request_id}`**; ошибки — 4xx с `{request_id, status:"error", errors:[{code,message}]}` |
| POST | `/remd/v1/get-metadata/` | 202 → callback `getMetadataResult` |
| POST | `/remd/v1/search-registry-item/` | 202 → callback `searchRegistryItemResult` с `items[]` |
| GET | `/remd/v1/registry/{emdr_id}` | 200 `{emdr_id, status, errors, created_at, updated_at}` — только для отладки (реального метода нет) |
| POST | `/remd/v1/_test/callback-retry/{request_id}` | повторная доставка последнего callback (тестовый хук) |
| GET | `/health` | `{status:"ok"}` |

Callback (`CC_REMD_MOCK_CALLBACK_URL`, иначе `callback_url` конверта) — настоящий HTTP POST:
`{from_system_id, lpu_uid, response_to_request_id, message_type:"registerDocumentResult",
status:"success", data:{emdr_id, registration_date, retention_period:"25y", status:"REGISTERED"}}`.
Доставка at-least-once: до `CC_REMD_MOCK_CALLBACK_ATTEMPTS` попыток (default 5) с backoff
`CC_REMD_MOCK_CALLBACK_BACKOFF_S`; недоставленный callback повторяется хуком.
Инъекция сбоев: `?simulate=500|429|timeout`, `CC_REMD_MOCK_FORCE_STATUS=429|500|503`,
`CC_REMD_MOCK_FAIL_FIRST=N`.

**Подпись проверяется по-настоящему**: `app.signing.cms.verify_cms` над байтами CDA (Стрибог-256 +
ГОСТ 34.10-2012), затем срок сертификата (`CERTIFICATE_EXPIRED`) и цепочка до демо-УЦ
(`CERTIFICATE_NOT_FOUND`). Проверка «непустой base64» — не проверка. Сам документ обязан быть
`ClinicalDocument` в пространстве имён `urn:hl7-org:v3`.

### 8.3 Статусная машина

```
submit → queued → sending → registered   (callback: success + emdr_id)
                          → rejected     (callback: error не из «повтор: да» / синхронный 4xx)
                          → failed       (транспорт, 403/scope, «повтор: да»)
                                         (тоже: callback не пришёл за CC_REMD_SENDING_STALE_SEC
                                          → failed/CALLBACK_TIMEOUT, повтор — следующим submit)
failed → sending → …                    (повтор тем же local_document_uid)
```

`registered` и `rejected` терминальны: callback-реплей и повторный submit их не меняют.
`registered` переводит версию протокола в `submitted`. `failed` повторяется тем же
`local_document_uid` (новая запись реестра не создаётся, РЭМД вернёт тот же `request_id`).

Выход из `sending` (потерянный callback) — только по времени: пока `submitted_at` моложе
`CC_REMD_SENDING_STALE_SEC` (900 с), повторный submit возвращает 202 без второй отправки. После
порога доставка становится `failed` с `CALLBACK_TIMEOUT` (ответ 202 с этим статусом) — РЭМД ничего
не подтвердил, поэтому отправка не считается состоявшейся. Следующий submit повторяет регистрацию
тем же `local_document_uid` с полным конвертом (`attempts += 1`); новая запись в реестре РЭМД не
создаётся. Отдельной сверки по реестру нет: `emdr_id` узнаётся только из callback'а, а
`GET /remd/v1/registry/{emdr_id}` — диагностический эндпоинт мока, не продовый контракт.

Сериализация submit: блокировка строки `session_protocols` держится только на выбор состояния
(создать/взять доставку) и снимается коммитом **до** сетевого вызова; результат пишется коротким
`FOR UPDATE` по строке доставки. Поэтому долгий ответ РЭМД не блокирует сессию и пул потоков.

Повторный submit по свежему `sending` (`submitted_at` моложе `CC_REMD_SENDING_STALE_SEC`) документ
не отправляет, а отдаёт `request_id` уже идущей отправки: **ответ может задержаться до 5 с, пока
лидер не сохранит `request_id`** (опрос строки доставки каждые 20 мс). Ожидание идёт **вне
транзакции** — транзакция чтения закрывается перед каждым `sleep`, поэтому соединение из пула не
занято и соседние запросы не ждут. Если за 5 с `request_id` не появился, ответ — тот же 202 со
`status="sending"` и `request_id=null` (клиент может перезапросить доставку). Покрыто тестами
`test_request_id_wait_does_not_hold_connection` и `test_request_id_wait_deadline_returns_null_request_id`
(`api/tests/test_remd_delivery.py`).

| `VALIDATION_ERROR` | 400 | битый конверт/не CDA R2 | нет |
| `INVALID_SNILS` | 400 | контрольная сумма СНИЛС | нет |
| `INVALID_SIGNATURE` | 400 | подпись не сходится с байтами CDA | нет |
| `CERTIFICATE_EXPIRED` | 400 | сертификат вне срока | нет |

| `ORGANIZATION_NOT_FOUND` | 400 | `lpu_uid` не зарегистрирован | нет |
| `NOT_UNIQUE_PROVIDED_ID` | 409 | тот же `local_document_uid`, другой контент | нет |
| `DUPLICATE_DOCUMENT` | 409 | тот же номер+вид+пациент | нет |

`PATIENT_NOT_FOUND` объявлен в каталоге, но мок его не воспроизводит: справочника пациентов
(ФРМР/ЕГИСЗ) в контуре нет, проверяется только формат/сумма СНИЛС. Транспортные ошибки,
таймауты и 5xx клиент отдаёт как `502 EMIAS_UNAVAILABLE` (Problem), 4xx — как `rejected`
с кодом каталога. Исключения: коды «повтор: да» (`RATE_LIMITED`, `MIS_NOT_AVAILABLE`,
`INTERNAL_ERROR`) и 403 дают `failed`, а не терминальный `rejected`, — их лечит повтор тем же
`local_document_uid`.

Мок выдаёт токен с запрошенным `scope`; без `remd.write` регистрация отвечает
`403 INSUFFICIENT_SCOPE`. Клиент всегда запрашивает `scope=remd.write`.

### 8.5 Идемпотентность и повторные отправки

- Ключ — `local_document_uid = UUIDv5(protocol_id:version)`: повтор той же версии даёт тот же
  `request_id` и не создаёт записи реестра; тот же UID с другими байтами → 409
  `NOT_UNIQUE_PROVIDED_ID`.
- `request_id` приходит от РЭМД; callback сопоставляется по `response_to_request_id`
  (at-least-once, upsert; терминальные статусы не перезаписываются).
- Клиент: до `CC_REMD_MAX_ATTEMPTS` попыток только на 429/5xx/таймаут, экспоненциальный backoff
  с jitter, `Retry-After` соблюдается, но обрезается `CC_REMD_RETRY_AFTER_CAP` (60 с), 4xx не
  ретраятся; белый список хостов; кап тела ответа. 403 (`INSUFFICIENT_SCOPE`) — конфигурационный
  сбой: доставка уходит в `failed`, API отвечает `502 EMIAS_UNAVAILABLE`.
- Callback обязан совпадать по `lpu_uid` с `CC_REMD_LPU_UID` (иначе 400, доставка не меняется).
- Callback, пришедший раньше, чем API сохранил `request_id` (окно между 202 РЭМД и коротким
  коммитом), получает `404` в обычном конверте ошибок RFC 7807 (`type`, `title`, `status=404`,
  `code`, `detail`, `instance`), где `title` = `code` = `UNKNOWN_REQUEST`, `detail` = «Запрос с
  таким request_id не найден». Строка доставки при этом не меняется (`status`, `request_id`,
  `attempts`, `updated_at` те же): РЭМД шлёт callback at-least-once, поэтому `404` для него —
  сигнал «повтори», и повтор с известным `response_to_request_id` регистрирует документ
  (`registered` + `external_id`). Страховка от потерянного callback'а — `CC_REMD_SENDING_STALE_SEC`
  → `failed`. Покрыто тестом `test_unknown_request_id_callback_is_404_and_keeps_delivery`
  (`api/tests/test_remd_delivery.py`).
- Callback аутентифицируется общим секретом `CC_REMD_CALLBACK_TOKEN` в заголовке `X-Remd-Token`
  (`hmac.compare_digest`, до чтения тела; `Content-Length` и поток режутся по
  `CC_REMD_CALLBACK_MAX_KB`, default 256 → `413 PAYLOAD_TOO_LARGE`) и принимает только
  `message_type="registerDocumentResult"`; клиническая сессия не нужна. Аудит: `EMIAS_SUBMIT`,
  `EMIAS_CALLBACK`.
- Гонка «первый callback пришёл раньше commit со `request_id`» в этом контуре не воспроизводится:
  callback мока отправляется только после ответа 202, а `request_id` коммитится до ответа. В
  живом контуре она закрывается неизвестным `request_id` → повторной доставкой РЭМД (at-least-once).
- Повтор после `failed` — это новая попытка (`attempts += 1`): сохранённый `result` прошлой попытки
  стирается (`NULL`) вместе с `last_error_*`, поэтому старый ответ не выглядит ответом новой
  попытки. Дальше `result` заполняется только исходом этой попытки (callback, синхронный отказ
  или протухание `sending` → `CALLBACK_TIMEOUT`). Покрыто тестом
  `test_retry_clears_previous_result` (`api/tests/test_remd_delivery.py`).

### 8.6 Чего мок не воспроизводит (сознательно)

СМЭВ 3.x (SOAP 1.x/XML) и шлюз ЕГИСЗ с ГОСТ-TLS; КриптоПро DSS/валидацию квалифицированной
подписи и CRL/OCSP; живые НСИ/ФРМО/ФРМР (врачи, МО, виды СЭМД — фикстуры и один код 34);
ИЭМК/Госуслуги и уведомления пациента; квоты/SLA и `retention`-джобы (поле `retention_period`
в callback — декоративное); московский ЕМИАС-специфичный обмен; обратный `getDocumentFile`
(выдача файла из РЭМД); подпись всего конверта (в реальном контуре — транспорт СМЭВ).
Формат СЭМД — упрощённый CDA R2 без `templateId` профиля: шаблон вида задаёт интегратор, здесь
его нет. Демо-УЦ не аккредитован, подпись юридической силы не имеет (§7.6).

## 10. Диалог по сессии и тул протокола (FR-44, PR P9)

### 10.1 Автопайплайн приёма

Конвейер доводит приём до черновика без участия врача: `recording → transcribing →
transcribed` → **автодрафт**. После успешного коммита расшифровки (сессия `transcribed`)
фоновый шаг вызывает **тот же** `session_ai.draft()`, что и ручная кнопка, в новой сессии БД;
соединение advisory-лока расшифровки при этом ещё удерживается (повторный «расшифровать» во
время автодрафта — 409 `AI_BUSY`, это осознанно: два прогона по одному аудио не нужны).

Свойства автодрафта:

- управляется `CC_SESSION_AI_AUTODRAFT` (по умолчанию `true`), читается там же, где остальные
  `CC_SESSION_AI_*`; `false` — черновик только вручную (`POST …/protocol/draft`);
- **сбой не ломает расшифровку**: `ai_status` остаётся `transcribed`, код уходит в `ai_error`
  (`DRAFT_FAILED` — модель не вернула валидный черновик; `AUTODRAFT_FAILED` — неожиданный сбой;
  коды гейтов `MODEL_NOT_CONFIGURED`/`SESSION_AI_DISABLED` — как у ручного вызова), ручной вызов
  остаётся доступен;
- подтверждённый/подписанный протокол автодрафт не трогает: `PROTOCOL_LOCKED` здесь штатный —
  пропуск, а не ошибка;
- аудит — только ids, но **отличим по коду действия** (`audit.record` не принимает metadata):
  `SESSION_PROTOCOL_DRAFT` (кнопка/POST), `SESSION_PROTOCOL_AUTODRAFT` (конвейер),
  `SESSION_PROTOCOL_CHAT_DRAFT` (тул из диалога).
- **несколько писателей черновика не конфликтуют**: врач может нажать «Сформировать черновик»
  или попросить его в чате, пока автодрафт после расшифровки ещё идёт. Все входы идут через
  `protocols._create_draft`, где гонка за `UNIQUE(session_id, version)` разбирается повтором
  (взять следующий номер) **внутри SAVEPOINT** — транзакция вызывающего не откатывается
  (в чате в ней уже лежит реплика врача); автодрафт такую коллизию трактует как «черновик уже
  создан» и **не** пишет `ai_error`, а тул диалога возвращает модели `error`, не роняя ответ.

### 10.2 Тул `draft_session_protocol`

Инструмент агента (`api/app/services/session_agent.py`): аргумент — `session_id`, но **доступ
ограничен открытой сессией**. Тул сравнивает id с сессией, которую врач открыл (bound session),
и при расхождении отвечает 404 `SESSION_NOT_FOUND` (чужой id неотличим от несуществующего);
сама работа — существующий `session_ai.draft()` со всеми его гейтами (роутер/согласие,
`PROTOCOL_LOCKED`).

Возврат — **компактная сводка без текста протокола** (иначе контекст модели раздувается):

```json
{"protocol_id": "...", "version": 2, "filled_sections": ["complaints", "mental_status"],
 "needs_review_count": 3, "sources_count": 4}
```

Отказы тула не роняют диалог: `404 SESSION_NOT_FOUND` и `409 PROTOCOL_LOCKED` возвращаются
модели как результат вызова (`{"error": "<CODE>"}`), она продолжает ответ, а врач получает
обычный 200 без нового черновика. Для ручного/скриптового вызова сервис поднимает `Problem`
с теми же кодами.

### 10.3 Диалог: `POST` / `GET …/sessions/{id}/chat`

| Метод | Путь | Тело / параметры | Ответ |
|---|---|---|---|
| POST | `/clinician/sessions/{id}/chat` | `{message}` (1…`CC_SESSION_CHAT_MESSAGE_CHARS`) | 200 `SessionChatMessage` (роль `assistant`) |
| GET | `/clinician/sessions/{id}/chat` | `limit` (1…200, по умолчанию 50) | `{items: [SessionChatMessage]}` — **последние** `limit` реплик, старые → новые |

`SessionChatMessage` = `{id, role: clinician|assistant, content, citations[], proposal|null,
created_at}`. `citations[]` — `{source_title, guideline_id, topic, score}`, те же цитаты, что у
ассистента врача (docs/07); в тексте ответа маркеры `[n]` соответствуют позициям в `citations`.

Коды: 403 `NO_ROSTER` / `CONSENT_REQUIRED` (карта пациента), 404 `SESSION_NOT_FOUND` (чужая
сессия), 503 `SESSION_AI_DISABLED` / `MODEL_NOT_CONFIGURED`, 422 `MESSAGE_EMPTY` /
`MESSAGE_TOO_LONG`, 409 `CHAT_LIMIT_REACHED`. **409 `SESSION_FINISHED` чат не блокирует**:
разбор приёма и проверка протокола после «Завершить приём» — штатный сценарий; документ при
этом не меняется до явной правки врачом.

Контекст одного шага: обезличенная карточка пациента (`clinician.patient_context` — roster-гейт,
согласие, аудит `ASK_ASSISTANT_WITH_PATIENT`), текущий **черновик** протокола (если есть) и
последние `CC_SESSION_CHAT_HISTORY` реплик. Инструменты в tool-loop (не более **2 раундов**,
`tool_choice: auto`, `temperature: 0`, `chat_template_kwargs {enable_thinking: false}`):
`search_kb` (существующий гибридный поиск; red line остаётся включённой — в отличие от черновика
§5.3) и `draft_session_protocol` (§10.2).

**Ответ собирается детерминированно**: текст берётся из `agent.compose_grounded_answer` по
найденным чанкам (проверка ссылок `[n]`, FR-17), при её отказе — `build_rag_answer` (карта
пациента как опора). Модель не пишет клинических утверждений от себя — инвариант docs/07 §5
действует и здесь.

**Мутации протокола из чата запрещены.** Если врач просит поменять раздел, агент возвращает
`proposal: {section, before, after, reason, sources}`: `before` берётся из сохранённого черновика
на сервере (не из ответа модели), `section` — только из разрешённого списка (нарративные разделы,
поля `mental_status`, `diagnosis.rationale`; лечение и МКБ не предлагаются — там нужны источники
по каждому элементу §5.3), `sources` — найденные чанки, на которые опирается правка. Применяет
врач явным `PUT …/protocol` (кнопка «Применить в раздел» в UI); правка подтверждённого протокола
кнопкой не предлагается.

**ПДн**: в LLM уходит только замаскированный текст — текст расшифровки замаскирован при
расшифровке, карточка пациента и черновик проходят `scrub_for_llm`/`scrub_text`, реплики врача
маскируются на каждом вызове (это же повторно проверяется в тестах: исходных ФИО/телефона в
запросе к модели нет). В БД реплики — только шифротекстом (§3.9), в аудите — только id
(`SESSION_CHAT_ASK`).

Потолок реплик проверяется перед вставкой без блокировки сессии: два одновременных POST с
одним и тем же счётчиком могут дать пару реплик сверх лимита. Это бюджетная страховка от
зацикливания, а не инвариант — перебор ограничен степенью параллельности, поэтому advisory-lock
на время ответа модели здесь не берётся (он держал бы соединение все секунды LLM-вызова).
