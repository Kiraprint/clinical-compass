# 08. База знаний ИИ-агента (дизайн)

Статус: v0.2, 2026-10-21. Этап 08, item 2. Векторная БД — Qdrant (см. docs/07). Изменение v0.2: корпус пополняется внешними источниками через подсистему обогащения (docs/15), реестр `kb_works` — источник истины, Qdrant — производный индекс.

---

## 1. Назначение

База знаний (КБ) — корпус, по которому ИИ-агент **врача-ассистента** ведёт гибридный поиск (dense + sparse) и отвечает с обязательным указанием источника. Агент **не диагностирует** и **не назначает лечение** — только извлечение справочной информации по найденным фрагментам (red line docs/01).

Ключевое ограничение: КБ, которую агент цитирует, агент **не должен** использовать для клинического вывода сверх источника. Ответ формируется перефразированием найденных фрагментов + явная ссылка `source_title`/`guideline_id`.

### 2.1 Внешние источники: реестр и производный индекс

Часть топиков собирается не сидом, а подсистемой обогащения (`api/app/enrichment/`,
док. docs/15):

| Топик | Кто попадает | Источник | Условие попадания в индекс |
|---|---|---|---|
| `НАУЧНЫЕ-СТАТЬИ` | систематические обзоры и метаанализы по тревоге/депрессии, БАР, ТРД, суицидальному риску | PubMed E-utilities (абстракт + метаданные) | approve ADMIN (`kb_works.status='approved'`) |
| `РЕКОМЕНДАЦИИ` (внешние) | гайдлайны ВОЗ из белого списка IRIS (7 handle) | `iris.who.int/server/api` (текст из бандла TEXT) | автопубликация только при найденной в тексте лицензии CC BY-NC-SA 3.0 IGO |
| `РЕКОМЕНДАЦИИ`, `ЛЕКАРСТВА`, `ШКАЛЫ`, `ТРИАЖ`, `ЧЕК-ИН`, `СОРС-ПРАВИЛА` | собственный и РФ-контент | seed-корпус `kb_seed.py`, клинреки Минздрава, ГРЛС | ручная курация (docs/13 §2) |

Разделение ответственности: Postgres-таблицы `kb_works`/`kb_runs`/`kb_exclusions`
— **источник истины** (провенанс, вердикты критериев, статус, история ревизий);
Qdrant — **производный индекс**, где чанки существуют только для `approved`
записей. Неодобренный материал агенту физически недоступен.

Провенанс внешнего источника (`kb_works`): `source` (pubmed|who), `external_id`
(PMID | IRIS handle), `guideline_id` (`pmid-<PMID>` / `who-10665-374250`),
`revision` + `content_hash` (версия документа), `title`, `meta` (journal, year,
authors, doi, pmid, pmcid, url, fulltext_url, license, language,
publication_types, abstract, results, retraction_note, fetched_at), `design`,
`criteria` (вердикты с цитатами), `appraisal`, `retraction`, `revision_history`,
`approved_by/at`, `reject_reason`, `chunk_count`, `indexed_hash`.

Payload чанка внешнего источника: `guideline_id`, `source_title`, `topic`,
`text`, `chunk_index`, `work_id`, `source`, `kind`, `year`, `source_url`,
`license`, `revision`, `text_hash`. Чанк статьи начинается с заголовка и
включает журнал/год/дизайн/PMID/DOI, абстракт, раздел результатов, сводку оценки
методологии и ссылку; чанк гайдлайна несёт шапку с редакцией, лицензией и URL.

> **Копирайт/152-ФЗ.** Полные тексты КР Минздрава — сторонний контент. В репозиторий их **не заливаем**; индексация идёт во время сбора корпуса, а в демо-офлайн корпусе для `РЕКОМЕНДАЦИИ`/`ЛЕКАРСТВА` используем **собственные** пересказы/выдержки с явным `source_title` и `guideline_id`-ссылкой. Векторная БД хранит только публичный (не-ПДн) контент — поверхность 152-ФЗ не расширяется (docs/07 §3.5).

## 3. Chunking

- **Источник**: собираем корпус как список `Document` (title, topic, text, url/citation).
- **Размер**: целевой чанк **~512 токенов** (~3000 символов), перекрытие **~64 токена** между соседними — баланс целостности куска и перекрытия при поиске. [TBD — подтвердить на реальном корпусе, но стартовые значения такие.]
- **Структурный** (не наивный посимвольный): режем по заголовкам/абзацам (model.md-разметка, markdown-заголовки), сохраняя `source_title`. Таблицы (шкалы) — чанк целиком, но с мини-аннотацией топика, чтобы не разрывать строки.
- **Метаданные в payload** каждой точки: `guideline_id`, `source_title`, `chunk_index`, `topic`, `lang="ru"`, `text_hash` (SHA-256 для дедупликации и трассировки).

### Индексные точки Qdrant (коллекция `kb`)

## 4. Эмбеддинги — bge-m3 (SPI)

Retrieval-стек БЗ настраивается пятью env-ручками (дефолты — `Settings`):

| Ручка | Значение | Смысл |
|---|---|---|
| `CC_EMBEDDER` | `hash` \| `bge-m3` \| `qwen3-0.6b` \| `e5-large-instruct` \| `user-bge-m3` | профиль эмбеддера: dense-размерность + стратегия поиска |
| `CC_RETRIEVAL_CANDIDATES` | int, `0` → `max(limit*3, 10)` | глубина пула до реранка/отсечки |
| `CC_RRF_K` | int, `60` | константа RRF-слияния каналов (`qm.RrfQuery(qm.Rrf(k=…))`) |
| `CC_RERANKER` | `off` \| `<hf-model-id>` | кросс-энкодерный реранк пула |
| `CC_KB_MIN_SCORE` | float \| пусто | порог «релевантного ответа нет»; пусто → дефолт профиля |

### 4.1 Профили эмбеддера

Профиль — единственный источник истины для dense-размерности, стратегии поиска
и дефолтного порога (`PROFILES`, `api/app/services/embeddings.py`):

| профиль | модель | dense | стратегия | extra | порог по умолчанию |
|---|---|---|---|---|---|
| `hash` (**дефолт**) | feature hashing, офлайн | 512 | dense+sparse RRF | — | 0.45 |
| `bge-m3` | BAAI/bge-m3 | 1024 | dense-only | `embeddings` | 0.45 |
| `qwen3-0.6b` | Qwen/Qwen3-Embedding-0.6B | 1024 | dense-only (instruct-префикс) | `embeddings` | перемеряется, см. отчёт |
| `e5-large-instruct` | intfloat/multilingual-e5-large-instruct | 1024 | dense-only (instruct-префикс) | `embeddings` | перемеряется, см. отчёт |
| `user-bge-m3` | deepvk/USER-bge-m3 | 1024 | dense-only | `embeddings` | перемеряется, см. отчёт |

SPI — `Embedder` (`dense`/`sparse` + опциональный `query_dense`): асимметричные
модели (e5, Qwen3) кодируют запрос с `query_prefix`, пассаж — с
`passage_prefix`; `kb.hybrid_search` берёт
`getattr(embedder, "query_dense", embedder.dense)`. Sparse-вектор пишется
всегда (схема коллекции неизменна), но нейросетевые профили в ранжировании его
не используют: на RU→EN перефразах RRF с лексическим каналом опускает
семантически верные чанки (`bench/REPORT-retrieval.md`).

### 4.2 Форма выдачи: пул → реранк → порог

dense-поиск оптимизирован на recall большого пула (top-C), а порядок внутри
пула для ответа с цитатами решает кросс-энкодер: он видит пару
(запрос, чанк) целиком. Схема:

```
CC_EMBEDDER → Qdrant: dense (или dense+sparse → RRF(k)) top-C
            → CC_RERANKER: кросс-энкодер по C кандидатам → top-5
            → порог профиля по СКОРУ ПЕРВИЧНОГО ПОИСКА → цитаты
```

Реранк (`api/app/services/reranker.py`) — опциональная зависимость
(`extra rerank`, sentence-transformers+torch). Модель грузится лениво,
процессный синглтон `get_reranker()`; при отсутствии пакета/весов/GPU пишется
warning, порядок остаётся RRF — запрос не падает. Реранк включается только для
нейросетевых профилей: у `hash` порядок чинит лексический гейт
(`_hash_rerank`), реранк поверх него не применяется.

Инвариант приватности: `exclude_ids` (исключённые врачом источники)
фильтруются в Qdrant, повторно — в реранкере и ещё раз в `kb.hybrid_search`
после реранка: воскресить исключённый источник нельзя.

Порог «нет ответа» сравнивается с `retrieval_score` (скор первичного поиска),
а не со скором реранкера: logit-шкала кросс-энкодера с косинусом несравнима.
`CC_KB_MIN_SCORE` перекрывает дефолт профиля; дефолт нужен потому, что шкала
косинуса у моделей разная (у e5-instruct систематически ниже).

подробно — `bench/REPORT-retrieval.md` §6.1. Воспроизведение —
`bench/run_retrieval_suite.sh` или `bench/eval_retrieval.py`.

### 4.4 Коллекция и переиндексация (жизненный цикл)

- **Имя коллекции привязано к профилю.** Дефолт `CC_QDRANT_COLLECTION=kb`
  соответствует `hash`. Нейросетевому профилю нужна своя коллекция:
  `CC_QDRANT_COLLECTION=kb_bge_m3` (dense 1024). Одна коллекция не может
  обслуживать два профиля: dense-вектора несравнимы, размерности разные.
- **Миграция (однократная, офлайн):**
  ```bash
  # 1) новая коллекция под профиль; старая `kb` остаётся рабочей — откат мгновенный
  export CC_EMBEDDER=bge-m3 CC_QDRANT_COLLECTION=kb_bge_m3
  export CC_EMBEDDER_DEVICE=cuda          # или cpu (≈ 3 с/запрос, docs/07)
  cd api && uv run --extra embeddings python -m app.kb_seed --reset
  # 2) обогащённая KB (КР/статьи) — повторный индекс enrichment-процессом
  #    с тем же CC_QDRANT_COLLECTION
  # 3) переключение API: те же env + перезапуск; старт валидирует пару
  #    «эмбеддер ↔ коллекция» (kb.check_embedder_compatibility) и падает с
  #    инструкцией при несовпадении dense-размерности
  ```
- **Откат:** вернуть `CC_EMBEDDER=hash CC_QDRANT_COLLECTION=kb` и перезапустить —
  данные прежней коллекции не трогались.
- **Реранк коллекцию не меняет** (`CC_RERANKER` + extra `rerank`), но добавляет
  VRAM и латентность (§4.3); при недоступности модели деградирует к RRF без
  переиндексации.

### 4.5 Стоимость на CPU (почему нейросетевой профиль требует GPU)

Прод-образ API — **без torch** (`api:latest` ≈ 876 МБ, только CPU). Замер на
хосте с `OMP_NUM_THREADS=4` (как в контейнере при `cpus: 4`), 20 запросов,
`bench/cpu_latency.py`:

| модель | embed запроса, p50 | p95 | rerank 20 канд., p50 | rerank 50 канд., p50 |
|---|---|---|---|---|
| bge-m3 | 75 мс | 130 мс | — | — |
| e5-large-instruct | 87 мс | 125 мс | — | — |
| user-bge-m3 | 90 мс | 127 мс | — | — |
| qwen3-0.6b | 111 мс | 152 мс | — | — |
| FRIDA | 419 мс | 528 мс | — | — |
| bge-reranker-v2-m3 | — | — | **11.9 с** | **28–31 с** |

Вывод прямой: даже **эмбеддинг запроса на CPU** съедает весь бюджет
`/assistant/ask` (p95 ≈ 120 мс) ещё до похода в Qdrant, а один проход
кросс-энкодера по 20 кандидатам — ~12 с (в 100 раз больше бюджета). Поэтому
профиль с реранком в CPU-контейнере **непригоден**, а dense-эмбеддер на CPU
пригоден только при смягчённом бюджете (p95 ≥ 250 мс на поиск).

Стоимость образа (если всё же ставить torch в API): CPU-wheel `torch` —
176 МБ сжатого / **682 МБ распакованного**, `transformers` ~40 МБ,
`sentence-transformers` ~5 МБ, tokenizers/safetensors/huggingface-hub ~20 МБ
→ **≈ +0.9 ГБ к распакованному образу** (≈ +0.25 ГБ к слоям). CUDA-wheels в
образ не попадают никогда: для CPU нужен индекс `download.pytorch.org/whl/cpu`.
Отдельно: веса bge-m3 (2.3 ГБ) и реранкера (2.3 ГБ) — ещё +4.6 ГБ, если
класть их в образ, а не тянуть на старте.

### 4.6 Форма деплоя: GPU только на хосте

GPU (RTX 5090) есть только на хосте приложения, в контейнере — нет. Варианты:

| вариант | как | цена | когда выбирать |
|---|---|---|---|
| **A. hash (сейчас)** | всё в API-контейнере | 0 | пока качество hash приемлемо |
| **B. ML-сайдкар на GPU (принято)** | сервис `ml` (эмбеддинг + реранк + mask) за `CC_ML_URL`, API-образ без torch | +1 сетевой хоп и +1 сервис в эксплуатации | выбран пользователем: нейросетевой профиль без раздувания образа |
| **C. CPU-эмбеддер в образе** | extra `embeddings` в API | +0.9 ГБ образа, p95 поиска ≥ 130 мс, реранк невозможен | только dense-эмбеддер без реранка |
| **D. GPU-sidecar в compose** | контейнер с `--gpus all` рядом с API | требует NVIDIA Container Toolkit на хосте | если хост — выделенный сервер с GPU |

Вариант **B** и есть принятая форма (решение пользователя): один ML-сайдкар
на GPU, API-образ остаётся без torch. Контракт — §4.7.

### 4.7 ML-сайдкар (GPU)

Сервис `ml` в compose (`nvidia` runtime) держит все тяжёлые модели и отдаёт
их по HTTP. API ходит в него через общий клиент
`api/app/services/ml_client.py` (`urllib`, без новых зависимостей) — тот же
клиент используют другие потребители (NER-mask), второго клиента быть не
должно.

Контракт (заморожен, общий для всех потребителей):

| метод | запрос | ответ |
|---|---|---|
| `POST /v1/embeddings` | `{"texts":[…], "kind":"query"\|"passage", "profile":"<id>"}` | `{"profile":…, "dense_size":N, "vectors":[[float,…],…]}` (порядок сохраняется) |
| `POST /v1/rerank` | `{"query":str, "documents":[str], "top_k":int}` | `{"scores":[float,…]}` (выровнено с `documents`, больше — лучше) |
| `POST /v1/mask` | `{"text":str, "names":[str]}` | `{"text":str, "spans":[{"category","start","end"}], "model":str}` |
| `GET /health` | — | `{"status":"ok", "device":…, "models":{…}}` |

Необязательная авторизация — заголовок `X-CC-ML-Token` из `CC_ML_TOKEN`.

**Профили.** `CC_EMBEDDER` получает семейство `remote-<profile>`:
`remote-bge-m3`, `remote-qwen3-0.6b`, `remote-user-bge-m3`,
`remote-e5-large-instruct`. `profile` — id профиля в сайдкаре, dense-размерность
берётся из `/health` (или из первого ответа) и **сверяется с профилем**:
несовпадение — `EmbedderConfigError` на старте, молчаливой обрезки вектора нет
(коллекция Qdrant создаётся под одну размерность, §3). Стратегия поиска —
dense-only; sparse-вектор пишется лексическим hash-каналом только для схемы
коллекции. `CC_RERANKER=remote` включает реранк через `/v1/rerank`.

**Таймауты и деградация.** `CC_ML_TIMEOUT_S` (по умолчанию 5 с) — на запрос;
реранк делает один ретрай на транспортной ошибке, после чего
`kb.hybrid_search` пишет WARNING и отдаёт выдачу в порядке RRF: `/assistant/ask`
продолжает отвечать без реранка. Эмбеддер деградировать не может (без вектора
поиска нет) — его недоступность на старте даёт громкую ошибку с инструкцией.

**Порог и приватность.** Порог «нет релевантного ответа» (`CC_KB_MIN_SCORE`,
иначе дефолт профиля) сравнивается с `retrieval_score` — скором первичного
поиска; `score` после реранка — скор сайдкара. Исключённые врачом источники
фильтруются до и после реранка (§4.2), в том числе для remote-режима.

**Переключение прода** (после приёмки; дефолты в compose не меняются):

```bash
# 1) поднять сайдкар и проверить контракт
docker compose -f infra/docker-compose.yml up -d ml
curl -s $CC_ML_URL/health

# 2) собрать коллекцию под размерность профиля (старая `kb` остаётся рабочей)
export CC_EMBEDDER=remote-qwen3-0.6b CC_QDRANT_COLLECTION=kb_qwen3 CC_ML_URL=http://ml:8080
(cd api && uv run python -m app.kb_seed --reset)
# enrichment: повторный reindex статей/КР с тем же CC_QDRANT_COLLECTION

# 3) включить в API
#    CC_EMBEDDER=remote-qwen3-0.6b, CC_RERANKER=remote,
#    CC_RETRIEVAL_CANDIDATES=50, CC_QDRANT_COLLECTION=kb_qwen3
# откат: CC_EMBEDDER=hash CC_QDRANT_COLLECTION=kb CC_RERANKER=off + перезапуск
```

Тесты (`api/tests/test_ml_remote.py`) идут без GPU и сайдкара: фейковый клиент
проверяет несовпадение размерности, недоступность сайдкара (порядок RRF,
ответ без 500), фильтр `exclude_ids` после remote-реранка и порог по
`retrieval_score`.

## 5. Пайплайн индексации (офлайн)

```
сбор корпуса → нормализация (md) → chunk → SHA256(text_hash) → дедупликация
   → bge-m3: dense/sparse/colbert → upsert в Qdrant (источник: guideline_id)
```

- **Идемпотентность**: при изменении схемы/корпуса — `DELETE collection` + `recreate` (контейнер-сидер, один раз).
- **Сид**: офлайн-демо корпус строится из **собственного** контента (`core/compass.*`, docs/01) — без сети; `РЕКОМЕНДАЦИИ`/`ЛЕКАРСТВА` — пересказы с citation. (Полный корпус КР — отдельный сбор вне репозитория.)
- **Дедупликация**: один `text_hash` на чанк; повторный сид не плодит дубли.

**Второй путь наполнения — обогащение (внешние источники, docs/15):**
`api/app/enrichment/index.py` режет текст абзацно-осознанно (1800 символов / 120
перекрытие, `CC_ENRICH_CHUNK_CHARS`/`CC_ENRICH_CHUNK_OVERLAP`), отсекает точные
дубли по `text_hash` и обеспечивает идемпотентность на уровне работы, а не
коллекции: `index_work` удаляет точки прежней версии по payload `work_id` и
вставляет новые чанки. Коллекция при этом не пересоздаётся; сид и обогащение
пишут в одну коллекцию, но разными `topic`.

**Кеш корпуса в процессе API.** `kb_seed.build_corpus()` вызывается на запрос
агента (лексический fallback в `search_kb`, docs/07 §7) и читает препараты из
таблицы `drugs`. Готовый корпус кешируется в процессе на
`CC_KB_CORPUS_TTL_SECONDS` (по умолчанию 60 с, `0` — кеш выключен): промах кеша
стоит одного похода в БД даже при параллельных запросах, ошибки не кешируются.
Снимок неизменяем (`MappingProxyType`), поэтому вызывающий не может испортить
кеш. Runtime-писателей `drugs`/КР в API нет (сид — отдельный CLI), поэтому TTL —
единственная инвалидация на запросном пути; писатели (`seed._seed_drugs`,
`python -m app.kb_seed`, тестовые фикстуры) зовут `clear_corpus_cache()`.

## 6. Поиск (гибрид) — ссылка на docs/07 §7

Запрос → bge-m3 → dense + sparse + colbert → Query API c `prefetch` (dense, sparse) → fusion **RRF** → тумблер topN → **реранкер** (bge-reranker-v2-m3) → top-k с `source_title`+`guideline_id`. Ответ — только по найденным фрагментам, при пустоте — «в корпусе нет данных», без клинического вывода.
