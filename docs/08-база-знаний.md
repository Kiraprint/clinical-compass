# 08. База знаний ИИ-агента (дизайн)

Статус: v0.2, 2026-10-21. Этап 08, item 2. Векторная БД — Qdrant (см. docs/07). Изменение v0.2: корпус пополняется внешними источниками через подсистему обогащения (docs/15), реестр `kb_works` — источник истины, Qdrant — производный индекс.

---

## 1. Назначение

База знаний (КБ) — корпус, по которому ИИ-агент **врача-ассистента** ведёт гибридный поиск (dense + sparse) и отвечает с обязательным указанием источника. Агент **не диагностирует** и **не назначает лечение** — только извлечение справочной информации по найденным фрагментам (red line docs/01).

Ключевое ограничение: КБ, которую агент цитирует, агент **не должен** использовать для клинического вывода сверх источника. Ответ формируется перефразированием найденных фрагментов + явная ссылка `source_title`/`guideline_id`.

### 2.1 Внешние источники: реестр и производный индекс

Часть топиков собирается не сидом, а подсистемой обогащения (`api/app/enrichment/`,
док. docs/15):

| Топик | Кто попадает | Источник | Условие попадания в индекс |
|---|---|---|---|
| `НАУЧНЫЕ-СТАТЬИ` | систематические обзоры и метаанализы по тревоге/депрессии, БАР, ТРД, суицидальному риску | PubMed E-utilities (абстракт + метаданные) | approve ADMIN (`kb_works.status='approved'`) |
| `РЕКОМЕНДАЦИИ` (внешние) | гайдлайны ВОЗ из белого списка IRIS (7 handle) | `iris.who.int/server/api` (текст из бандла TEXT) | автопубликация только при найденной в тексте лицензии CC BY-NC-SA 3.0 IGO |
| `РЕКОМЕНДАЦИИ`, `ЛЕКАРСТВА`, `ШКАЛЫ`, `ТРИАЖ`, `ЧЕК-ИН`, `СОРС-ПРАВИЛА` | собственный и РФ-контент | seed-корпус `kb_seed.py`, клинреки Минздрава, ГРЛС | ручная курация (docs/13 §2) |

Разделение ответственности: Postgres-таблицы `kb_works`/`kb_runs`/`kb_exclusions`
— **источник истины** (провенанс, вердикты критериев, статус, история ревизий);
Qdrant — **производный индекс**, где чанки существуют только для `approved`
записей. Неодобренный материал агенту физически недоступен.

Провенанс внешнего источника (`kb_works`): `source` (pubmed|who), `external_id`
(PMID | IRIS handle), `guideline_id` (`pmid-<PMID>` / `who-10665-374250`),
`revision` + `content_hash` (версия документа), `title`, `meta` (journal, year,
authors, doi, pmid, pmcid, url, fulltext_url, license, language,
publication_types, abstract, results, retraction_note, fetched_at), `design`,
`criteria` (вердикты с цитатами), `appraisal`, `retraction`, `revision_history`,
`approved_by/at`, `reject_reason`, `chunk_count`, `indexed_hash`.

Payload чанка внешнего источника: `guideline_id`, `source_title`, `topic`,
`text`, `chunk_index`, `work_id`, `source`, `kind`, `year`, `source_url`,
`license`, `revision`, `text_hash`. Чанк статьи начинается с заголовка и
включает журнал/год/дизайн/PMID/DOI, абстракт, раздел результатов, сводку оценки
методологии и ссылку; чанк гайдлайна несёт шапку с редакцией, лицензией и URL.

> **Копирайт/152-ФЗ.** Полные тексты КР Минздрава — сторонний контент. В репозиторий их **не заливаем**; индексация идёт во время сбора корпуса, а в демо-офлайн корпусе для `РЕКОМЕНДАЦИИ`/`ЛЕКАРСТВА` используем **собственные** пересказы/выдержки с явным `source_title` и `guideline_id`-ссылкой. Векторная БД хранит только публичный (не-ПДн) контент — поверхность 152-ФЗ не расширяется (docs/07 §3.5).

## 3. Chunking

- **Источник**: собираем корпус как список `Document` (title, topic, text, url/citation).
- **Размер**: целевой чанк **~512 токенов** (~3000 символов), перекрытие **~64 токена** между соседними — баланс целостности куска и перекрытия при поиске. [TBD — подтвердить на реальном корпусе, но стартовые значения такие.]
- **Структурный** (не наивный посимвольный): режем по заголовкам/абзацам (model.md-разметка, markdown-заголовки), сохраняя `source_title`. Таблицы (шкалы) — чанк целиком, но с мини-аннотацией топика, чтобы не разрывать строки.
- **Метаданные в payload** каждой точки: `guideline_id`, `source_title`, `chunk_index`, `topic`, `lang="ru"`, `text_hash` (SHA-256 для дедупликации и трассировки).

### Индексные точки Qdrant (коллекция `kb`)

```json
{
  "vectors": {
    "dense":   {"size": 1024, "distance": "Cosine"},
    "colbert": {"size": 1024, "distance": "Cosine", "multivector_config": {"comparator": "max_sim"}}
  },
  "sparse_vectors": {"sparse": {}}
}
```

## 4. Эмбеддинги — bge-m3 (SPI)

Единая мультиязычная модель (100+ языков, включая русский) даёт **три** представления, каждое ложится в свой named vector:
- **dense** (1024) — семантика/смысл;
- **sparse** — лексика: точное совпадение терминов, акронимов (МНН препарата, код шкалы), которые dense может упустить;
- **colbert** — многопозиционное сопоставление для тонкого ранжирования.

Стало быть, **не нужен** отдельный sparse-пайплайн (SPLADE/BM25): один encoder → 3 вектора → фьюжн в Qdrant (для hash-профиля; прод bge-m3 ищет dense-only, см. ниже). Модель запускается **офлайн** (CPU + onnx, см. docs/03 §1.3 — SPI-изоляция внешних подсистем).

**Выбор модели обоснован бенчмарком** (`bench/`, docs/07 §5): bge-m3 — лучший
мультиязычный кандидат (RU nDCG@3 0.776 против 0.616 у e5 и 0.635 у FRIDA на
прикладном пути); альтернативы (Qwen3-Embedding, multilingual-e5, FRIDA,
USER-bge-m3) — dense-only. Реализация SPI — `api/app/services/embeddings.py`:
интерфейс `Embedder` (dense/sparse), офлайн `HashEmbedder` (демо/тесты, без
модели) и `BgeM3Embedder` (прод). Выбор профиля — `CC_EMBEDDER=hash|bge-m3`
(по умолчанию `hash`), фабрика `build_embedder()` и процессный синглтон
`get_embedder()` (модель грузится один раз на процесс).

Профиль bge-m3 настраивается env-переменными (дефолты в `Settings`):
`CC_EMBEDDER_MODEL` (id модели/fine-tune, дефолт `BAAI/bge-m3`),
`CC_EMBEDDER_DEVICE` (`auto`|`cpu`|`cuda[:N]`), `CC_EMBEDDER_BATCH_SIZE`,
`CC_EMBEDDER_MAX_LENGTH` (токенов на текст).

**Стратегия выдачи зависит от профиля** (`kb.hybrid_search`, флаг
`Embedder.use_sparse`): hash — dense+sparse prefetch → RRF (лексика —
единственный точный сигнал feature-hashing); bge-m3 — **dense-only**, т.к. на
золотом наборе из 55 запросов RRF с лексическим каналом роняет RU nDCG@3 с
0.78 до 0.49 (ранг-слияние уравнивает сильный мультиязычный dense и слабый
лексический). Sparse-вектора bge-m3 при индексации пишутся, но в ранжировании
не участвуют.

**Зависимости и переиндексация**:
- torch/FlagEmbedding — опциональный extra `embeddings`
  (`uv sync --extra embeddings`); базовый образ API остаётся без torch, а
  `CC_EMBEDDER=bge-m3` без extra падает на старте с инструкцией;
- dense-вектора разных моделей несравнимы → смена `CC_EMBEDDER` требует
  переиндексации (`python -m app.kb_seed --reset` для демо-корпуса, повторный
  enrichment-индекс для обогащённой KB);
- старт валидирует пару «эмбеддер ↔ коллекция» (`kb.check_embedder_compatibility`
  в lifespan приложения): несовпадение dense-размерности — падение с
  инструкцией, а не 500 на запросе. Воспроизводимый замер —
  `bench/eval_app_path.py` (тот же путь `kb.upsert_documents`/`hybrid_search`).

### 4.1 ML-сайдкар (GPU)

Модели, которые не помещаются в torch-free образ `api`, вынесены в отдельный
GPU-сервис `ml` (`ml/`, профиль compose `gpu`, docs/03 §7). api общается с ним
по одному внутреннему HTTP-контракту (`api/app/services/ml_client.py`), второго
клиента быть не должно:

- `POST /v1/embeddings` `{texts, kind: "query"|"passage", profile}` →
  `{profile, dense_size, vectors}` — dense-векторы БЗ, L2-норма;
- `POST /v1/rerank` `{query, documents, top_k}` → `{scores}` — cross-encoder,
  порядок = порядок `documents`, больше — лучше;
- `POST /v1/mask` `{text, names}` → `{text, spans, model: "hybrid"}` —
  маскирование ПДн (docs/12);
- `GET /health` → `{status, device, models}`.

**Профили эмбеддингов** (таблица `ml/models.py`, размерность 1024 у обоих):

| Профиль | Модель | Префиксы |
|---|---|---|
| `qwen3-0.6b` (дефолт) | `Qwen/Qwen3-Embedding-0.6B` | запрос: `Instruct: …\nQuery: `, пассаж: без префикса |
| `e5-large-instruct` | `intfloat/multilingual-e5-large-instruct` | запрос: `Instruct: …\nQuery: `, пассаж: без префикса |

Дефолт меняется **одной переменной** `CC_ML_DEFAULT_PROFILE` (без правки кода);
новые профили/переопределения — `CC_ML_PROFILES` (JSON). Асимметрия
query/passage обязательна: instruct-модели обучены на инструкции только в
запросе. Векторы разных моделей несравнимы → смена профиля требует
**переиндексации** коллекции, как и смена `CC_EMBEDDER` (размерность совпадает,
но геометрия пространства — нет).

**Таймауты и деградация.** `CC_ML_TIMEOUT` (по умолчанию 5 с) — на один вызов;
клиент повторяет ровно один раз только на сетевой сбой/5xx (операции
идемпотентны), бизнес-ошибки (4xx) не ретраятся. Недоступность сайдкара —
`MlUnavailable`; решение принимает вызывающий: эмбеддинги/реранк деградируют
к текущему пути (hash/bge-m3 в api), маскирование ПДн в прод-режиме —
fail-closed (docs/12). Пока модели грузятся, эндпоинты отдают 503
`model_loading` (с `Retry-After`), упавшая загрузка — 503 `model_unavailable`;
`restart: unless-stopped` перезапускает контейнер.

**Кеш моделей.** Веса (~4 ГБ: эмбеддер 0.6B, реранкер m3, rubert NER) лежат в
томе `ml-models` (`HF_HOME=/models`). Первый старт скачивает их из Hugging Face
— разовый egress; дальше сервис работает офлайн, интернет ему не нужен.

**Порядок переключения.**
1. `docker compose -f infra/docker-compose.yml --profile gpu up -d ml`, дождаться
   `/health` → `status: ready` (холодная загрузка ≈ 20 с при прогретом кеше).
2. Прописать `CC_ML_URL=http://ml:8080`, `CC_ML_TOKEN`, `CC_ML_TIMEOUT` в api
   (в compose уже есть; `.env`).
3. При смене профиля эмбеддингов — переиндексировать коллекцию и только потом
   переключать `CC_ML_DEFAULT_PROFILE` у потребителя.
4. Откат — убрать `CC_ML_URL` (api возвращается к локальным hash/bge-m3 и
   regex-NER); сам сервис можно остановить, профиль `gpu` не влияет на
   остальной стек.

Без GPU профиль `gpu` не поднимается: демо/CI работают на `CC_EMBEDDER=hash` и
`CC_DEPERSONALIZE_NER=off`.

## 5. Пайплайн индексации (офлайн)

```
сбор корпуса → нормализация (md) → chunk → SHA256(text_hash) → дедупликация
   → bge-m3: dense/sparse/colbert → upsert в Qdrant (источник: guideline_id)
```

- **Идемпотентность**: при изменении схемы/корпуса — `DELETE collection` + `recreate` (контейнер-сидер, один раз).
- **Сид**: офлайн-демо корпус строится из **собственного** контента (`core/compass.*`, docs/01) — без сети; `РЕКОМЕНДАЦИИ`/`ЛЕКАРСТВА` — пересказы с citation. (Полный корпус КР — отдельный сбор вне репозитория.)
- **Дедупликация**: один `text_hash` на чанк; повторный сид не плодит дубли.

**Второй путь наполнения — обогащение (внешние источники, docs/15):**
`api/app/enrichment/index.py` режет текст абзацно-осознанно (1800 символов / 120
перекрытие, `CC_ENRICH_CHUNK_CHARS`/`CC_ENRICH_CHUNK_OVERLAP`), отсекает точные
дубли по `text_hash` и обеспечивает идемпотентность на уровне работы, а не
коллекции: `index_work` удаляет точки прежней версии по payload `work_id` и
вставляет новые чанки. Коллекция при этом не пересоздаётся; сид и обогащение
пишут в одну коллекцию, но разными `topic`.

**Кеш корпуса в процессе API.** `kb_seed.build_corpus()` вызывается на запрос
агента (лексический fallback в `search_kb`, docs/07 §7) и читает препараты из
таблицы `drugs`. Готовый корпус кешируется в процессе на
`CC_KB_CORPUS_TTL_SECONDS` (по умолчанию 60 с, `0` — кеш выключен): промах кеша
стоит одного похода в БД даже при параллельных запросах, ошибки не кешируются.
Снимок неизменяем (`MappingProxyType`), поэтому вызывающий не может испортить
кеш. Runtime-писателей `drugs`/КР в API нет (сид — отдельный CLI), поэтому TTL —
единственная инвалидация на запросном пути; писатели (`seed._seed_drugs`,
`python -m app.kb_seed`, тестовые фикстуры) зовут `clear_corpus_cache()`.

## 6. Поиск (гибрид) — ссылка на docs/07 §7

Запрос → bge-m3 → dense + sparse + colbert → Query API c `prefetch` (dense, sparse) → fusion **RRF** → тумблер topN → **реранкер** (bge-reranker-v2-m3) → top-k с `source_title`+`guideline_id`. Ответ — только по найденным фрагментам, при пустоте — «в корпусе нет данных», без клинического вывода.
