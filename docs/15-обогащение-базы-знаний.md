# 15. Обогащение базы знаний: реестр источников, критерии, ревью, индекс

Статус: v0.1, 2026-10-21. Реализация: `api/app/enrichment/`, compose-сервис `kb-enrichment`,
миграция `api/alembic/versions/c1d2e3f4a5b6_kb_enrichment.py`. Документ дополняет
docs/08 (дизайн КБ) и docs/13 (критерии отбора): здесь — как критерии исполняются
кодом, откуда берутся источники и почему неодобренный материал физически недоступен агенту.

---

## 1. Назначение и границы

КБ ассистента врача (docs/08) пополняется из двух внешних источников: PubMed
(систематические обзоры и метаанализы) и ВОЗ/IRIS (гайдлайны по психическому
здоровью). Задача подсистемы обогащения — превратить внешнюю публикацию в
**запись реестра с проверяемым провенансом** и, только после гейтов, в чанки
Qdrant.

Что подсистема делает:

- опрашивает источники по зафиксированному плану запроса и сохраняет план прогона;
- дедуплицирует публикации и отслеживает версии (revision/content hash);
- применяет детерминированные критерии (docs/13) и оценку методологии;
- публикует гайдлайны ВОЗ автоматически при подтверждённой лицензии;
- ставит статьи в очередь человеческого ревью (approve/reject ADMIN);
- индексирует в Qdrant только `approved` и снимает с индекса всё остальное.

Чего подсистема **не** делает:

- не хранит персональные данные: в процессах обогащения нет доступа к ПДн,
  вход — только внешние публикации;
- не выполняет сетевых запросов из API: у `api` нет исходящего трафика в
  PubMed/IRIS, всё сетевое поведение изолировано в процессе `kb-enrichment`;
- не оценивает качество статьи «одним баллом» и не принимает клинических
  решений: вердикты критериев хранятся раздельно, а приёмка в корпус — за человеком
  (кроме гейтованной автопубликации гайдлайнов).

## 2. Владение данными: реестр и производный индекс

| Хранилище | Роль | Что лежит |
|---|---|---|
| Postgres `kb_works` | **источник истины** | карточка источника: кто/откуда/какая редакция, метаданные, вердикты, оценка, статус, история ревизий |
| Postgres `kb_runs` | журнал прогонов | план запроса, версии алгоритмов, статистика, ошибки |
| Postgres `kb_exclusions` | персональные исключения врача | `(user_id, guideline_id)` |
| Qdrant (коллекция КБ) | **производный индекс** | чанки только из `kb_works.status='approved'`; payload несёт `work_id`, `guideline_id`, `source_url` |

Инварианты (закреплены в `api/app/enrichment/index.py`):

1. Чанк существует только для `approved`-работы. `candidate`, `rejected`,
   `excluded` в Qdrant отсутствуют — агент не может процитировать неодобренное.
2. Переиндексация работы удаляет прежние точки по payload `work_id`: старая и
   новая редакции не сосуществуют.
3. Текст чанка несёт ссылку на первоисточник, поэтому цитата проверяема из
   ответа агента без отдельного поля контракта RAG.
4. Порядок записи — **сначала реестр, потом индекс** (и в прогоне, и в
   `review.approve`): статус `approved` фиксируется в Postgres отдельным
   коммитом до записи в Qdrant, поэтому сбой коммита не оставляет в индексе
   точки без одобренной `kb_works`. После индексации статус перепроверяется под
   блокировкой строки (параллельный `reject`/новая версия отменяют публикацию и
   точки снимаются). Обратная ошибка тоже закрыта: `index_work` снимает прежние
   точки в память, удаляет частично записанные новые и возвращает снимок, если
   upsert упал; сбой индексации при approve возвращает работу в `candidate`.
5. Запись реестра возможна только для `candidate`; `excluded`/`rejected`,
   `approved` и `superseded` получают 409 `REVIEW_CONFLICT`. Решение по одной
   работе сериализуется блокировкой строки (`SELECT … FOR UPDATE`).

Статусы `kb_works.status`: `candidate` (ждёт врача), `approved` (в индексе),
`rejected` (отклонён с причиной), `excluded` (не прошёл жёсткий критерий, в
очереди кандидатов не показывается), `superseded` (зарезервирован в схеме под
замещение новой редакцией; кодом пока не выставляется).

Поля провенанса `kb_works`: `kind` (article|guideline), `source` (pubmed|who),
`external_id` (PMID | IRIS handle), `guideline_id` (идентификатор чанков:
`pmid-<PMID>` / `who-10665-374250`), `revision`, `content_hash`, `title`,
`meta` (journal, year, authors, doi, pmid, pmcid, url, fulltext_url, license,
language, publication_types, abstract, results, retraction_note, fetched_at),
`full_text` (только гайдлайны ВОЗ), `design`, `criteria`, `appraisal`,
`retraction`, `revision_history`, `first_seen_at`, `last_seen_at`,
`published_at`, `indexed_hash`, `chunk_count`, `approved_by`, `approved_at`,
`reject_reason`.

Payload чанка Qdrant: `guideline_id`, `source_title`, `topic`,
`text`, `chunk_index`, `work_id`, `source`, `kind`, `year`, `source_url`,
`license`, `revision`, `text_hash`. Топик: `НАУЧНЫЕ-СТАТЬИ` для статей,
`РЕКОМЕНДАЦИИ` для гайдлайнов ВОЗ.

## 3. Архитектура и развёртывание

```
kb-enrichment (тот же образ, что api; команда python -m app.enrichment serve)
   ├── pubmed.py   → eutils.ncbi.nlm.nih.gov (esearch + efetch)
   ├── who.py      → iris.who.int/server/api (DSpace 7 REST, белый список)
   ├── dedupe.py   → ключи DOI/PMID/нормализованный заголовок+год
   ├── design.py   → детерминированный классификатор дизайна
   ├── criteria.py → вердикты критериев + решение include/exclude
   ├── appraisal.py→ AMSTAR 2 / RoB 2 / ROBINS-I / AGREE II (по дизайну)
   ├── pipeline.py → оркестрация прогона, запись kb_runs/kb_works
   ├── index.py    → чанки и точки Qdrant (delete by work_id → upsert)
   └── review.py   → approve/reject, персональные исключения
```

Процесс использует общий образ `api/Dockerfile`, поэтому код и зависимости
совпадают с API, но запускается отдельным контейнером
(`infra/docker-compose.yml`, сервис `kb-enrichment`) и зависит от здоровья `api`
(схема обновляется миграциями в lifespan API) и завершения `kb-seed`.
CLI `python -m app.enrichment` доступен и внутри контейнера
(`docker compose exec kb-enrichment ...`), и локально из `api/`.

## 4. Источники

### 4.1 PubMed E-utilities

Базовый URL: `https://eutils.ncbi.nlm.nih.gov/entrez/eutils` (`CC_ENRICH_PUBMED_BASE_URL`).

Шаги: `esearch.fcgi` (JSON) → `efetch.fcgi` (XML, батчами по `MAX_BATCH` PMID) →
построчный разбор XML (`parse_pubmed_xml`, чистая функция).

Параметры `esearch` формируются в `pubmed.search_params`:

| Параметр | Значение |
|---|---|
| `db` | `pubmed` |
| `term` | `CC_ENRICH_PUBMED_QUERY` (по умолчанию — запрос из `config.DEFAULT_QUERY`, см. §13.2) |
| `datetype` | `pdat` |
| `mindate` / `maxdate` | `today - CC_ENRICH_PUBMED_DAYS` … `today`, формат `YYYY/MM/DD` |
| `retmax` | `CC_ENRICH_PUBMED_RETMAX`, ограничение 500 |
| `sort` | `pub_date` |
| `retmode` | `json` |
| `tool` | `clinical-compass-kb-enrichment` |
| `email`, `api_key` | из env, если заданы (правила NCBI: без ключа 3 запроса/с) |

Из `efetch` берутся: структурированный абстракт (разделы BACKGROUND/METHODS/
RESULTS/CONCLUSIONS), journal, год, авторы, DOI, PMCID, язык, PublicationType,
`CommentsCorrectionsList` (ретракции/исправления). Хранится **только абстракт**:
полный текст у издателя не скачивается (лицензия), `fulltext_url` ведёт на PMC/DOI.
`url` — страница PubMed.

Автоматического поиска вне PubMed нет; Europe PMC не подключён (см. §14).

### 4.2 ВОЗ: IRIS (DSpace 7 REST)

Базовый URL: `https://iris.who.int/server/api` (`CC_ENRICH_WHO_BASE_URL`).
Поиск по сайту ВОЗ **не используется**: релевантность IRIS ненадёжна для
тематического фильтра, поэтому список курируется людьми — белый список
`WHO_HANDLES` в `api/app/enrichment/who.py`.

Загрузка одного документа: `GET /core/items/{uuid}` → `_links.bundles` →
bitstream бандла `TEXT` с именем `*.pdf.txt` (готовый текст IRIS, PDF не
парсится, разбивка на разделы сохраняется) → текст документа. Ограничение
размера — `CC_ENRICH_WHO_MAX_TEXT_CHARS` (по умолчанию 4 000 000 символов):
превышение — ошибка документа (`SourceError` попадает в `kb_runs.errors`), текст

## 5. Конвейер прогона

`pipeline.execute` выполняет стадии последовательно и пишет каждый шаг в `kb_runs`:

1. **План и опрос источников** (`collect_documents`). Ошибка одной базы не
   отменяет другую: она попадает в `errors`, вторая база продолжает работу.
2. **Дедупликация** (`dedupe`): внутри пакета — по набору ключей (DOI, PMID,
   нормализованный заголовок + год, `source:external_id`, совпадение любого =
   дубликат); против БД — `source + external_id` → DOI → `title_key`.
3. **Классификация дизайна** (`design.classify`): по PublicationType и заголовку —
   `network_meta_analysis`, `umbrella_review`, `systematic_review_meta_analysis`,
   `systematic_review`, `meta_analysis`, `rct`, `cohort`, `guideline` (семейство
   SR/MA — `SR_FAMILY`).
4. **Критерии** (`criteria.evaluate`): набор вердиктов по виду источника
   (статья/гайдлайн), решение `include`/`exclude`.
5. **Оценка методологии** (`appraisal.appraise`): инструмент по дизайну.
6. **Решение о статусе** (`pipeline._decide`): `excluded` | `approved` (только
   гайдлайн с подтверждённой лицензией при `CC_ENRICH_AUTO_PUBLISH_GUIDELINES`)
   | `candidate`.
7. **Запись реестра** (`_apply_work`): создать или обновить запись, обновить
   `revision`, `content_hash`, `revision_history`, `last_seen_at`.
8. **Индексация**: `approved` и `indexed_hash != content_hash` → `index.index_work`;
   `approved` с прежним хешем → чанки не пересобираются; снят с публикации —
   точки удаляются по `work_id`.

Ошибка обработки одного документа инкрементит `stats["failed_documents"]` и не
валит прогон. Итоговый статус прогона: `failed` (есть ошибки и ничего не
загружено), `partial` (есть ошибки, часть данных получена), `ok` (без ошибок).
Результаты не считаются «пустыми» при отказе источника: отказ — это ошибка
прогона, а не отсутствие публикаций.

## 6. Критерии и семантика вердиктов

Критерии — детерминированный модуль `criteria.py` (версия `CRITERIA_VERSION`),
а не суждение LLM. Базовые пороги — docs/13; здесь фиксируется исполнение.

Статья (PubMed), жёсткие критерии — `ARTICLE_HARD`:

| Ключ | Жёсткий | Как проверяется |
|---|---|---|
| `psychiatry_relevance` | да | 12 кластеров терминов по заголовку + абстракту; `relevance_score = min(1, найдено/3)` |
| `freshness` | да | `current_year - year <= 5` (`FRESHNESS_YEARS = 5`); нет года → `insufficient_info` |
| `design` | да | дизайн ∈ `SR_FAMILY` |
| `language` | да | en/ru по метаданным; не указан → `insufficient_info` |
| `retraction` | да | `none` → `met`; `retracted` → `not_met` (+ ручная проверка); `correction` → `met` + ручная проверка; нет данных → `not_checked` |
| `reporting_completeness` | нет | абстракт с разделом результатов → `met`; абстракт без результатов → `insufficient_info`; абстракта нет → `insufficient_info` |

Гайдлайн (ВОЗ), жёсткие критерии — `GUIDELINE_HARD`:

| Ключ | Жёсткий | Как проверяется |
|---|---|---|
| `psychiatry_relevance` | да | заголовок + первые 4000 символов текста |
| `license` | да | в первых 20 000 символах: `CC BY-NC-SA 3.0 IGO` → `met`; «All rights reserved»/`© WHO` → `not_met` (публикация запрещена, approve блокируется); другая CC → `insufficient_info` (ручная проверка); не найдена → `insufficient_info` |
| `text_available` | да | текст ≥ 5000 символов |
| `recency` | нет | редакция старше 5 лет → `not_met`, но это **предупреждение**, не исключение |
| `source_authority` | нет | документ из белого списка IRIS → `met` |

Семантика вердиктов (единая для критериев и оценки):

| Статус | Значение | Влияет на исключение |
|---|---|---|
| `met` | критерий подтверждён | нет |
| `not_met` | подтверждённое нарушение | **да**, но только для жёсткого критерия |
| `insufficient_info` | данных для проверки нет | нет (неизвестное ≠ недостаток) |
| `not_checked` | проверка не выполнялась/невозможна | нет |

Решение: `exclude`, если хотя бы один **жёсткий** критерий имеет `not_met`;
иначе `include`. Причины исключения сохраняются списком строк
`"<label>: <explanation>"` в `kb_works.criteria.reasons`. Для гайдлайнов
`exclude` не означает потерю: спорный гейт (лицензия/текст) переводит документ в
`candidate` для человеческого решения, а не выбрасывает его молча.

Контракт доказательства (`types.Evidence`): каждый вердикт, где это возможно,
несёт `quote` — **точную подстроку** сохранённого текста (абстракта или полного
текста гайдлайна), `locator` (раздел абстракта / диапазон символов; номер
страницы не выдумывается — IRIS отдаёт текст без разметки страниц),
`source_url`, `confidence` (high/medium/low), `manual_review` и
`manual_review_reason`. Цитата не пересказывается «по смыслу».

## 7. Оценка методологии

Инструмент выбирается по дизайну (`appraisal.appraise`):

| Дизайн | Инструмент | Ограничение |
|---|---|---|
| SR/MA (семейство `SR_FAMILY`) | AMSTAR 2 | по абстракту: пункты, требующие полного текста, получают `insufficient_info`; каждый подтверждённый пункт несёт точную цитату из абстракта |
| РКИ | RoB 2 | не автоматизирован |
| нерандомизированное | ROBINS-I | не автоматизировано |
| гайдлайн | AGREE II | для гайдлайнов ВОЗ не применялся |

Все автоматические оценки помечены `experimental=True` и **не являются
валидированной оценкой качества**: это структурированная подсказка ревьюеру.
Импакт-фактор и число цитирований не используются.

## 8. Ревью и публикация

| Вид | Автопубликация | Условие |
|---|---|---|
| Статья PubMed | нет, всегда `candidate` | approve врача/админа (роль ADMIN) |
| Гайдлайн ВОЗ | да, `approved` | вердикт критерия `license` = `met` **и** `CC_ENRICH_AUTO_PUBLISH_GUIDELINES=true`; иначе `candidate` |

Переходы статусов:

- `candidate` → `approved`: `review.approve` — индексация, `published_at`,
  `indexed_hash`, `approved_by/at`, аудит `KB_SOURCE_APPROVE`. Approve запрещён,
  если хотя бы один **жёсткий** критерий имеет `not_met` (ретракция, проприетарная
  лицензия, не психиатрическая тема, устаревший дизайн/язык): 409
  `REVIEW_CONFLICT`. Это не обход методологии — нужна исправленная версия источника.
- `excluded` → `approved` невозможен (у таких записей всегда есть `not_met`);
  `approved`/`rejected` → approve запрещён (409).
- любой → `rejected`: нужна причина ≥ 3 символов (≤ 2000), причина хранится в
  `reject_reason`, точки удаляются из Qdrant, аудит `KB_SOURCE_REJECT`.
  Отклонение не удаляет запись реестра.
- повторный прогон при неизменившемся `content_hash` сохраняет решение человека;
  при изменившемся содержимом статья возвращается в `candidate` с обновлёнными
  вердиктами (новая версия — новое решение).

Ревью доступно двумя путями (оба — ADMIN): CLI `review` и HTTP
`/api/v1/admin/kb/*`:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/admin/kb/runs?limit=` | последние прогоны (статус, статистика, ошибки, план, версии) |
| GET | `/admin/kb/runs/{run_id}` | детали прогона |
| GET | `/admin/kb/works?status=&kind=&limit=&offset=` | очередь ревью (по умолчанию `candidate`) + счётчики по статусам |
| GET | `/admin/kb/works/{work_id}` | карточка: провенанс, вердикты с цитатами, оценка, индекс |
| POST | `/admin/kb/works/{work_id}/approve` | приёмка в индекс |
| POST | `/admin/kb/works/{work_id}/reject` | `{reason}` → отклонение с причиной |
| GET | `/admin/kb/health` | `{last_run, counts}` — последний прогон + число работ по каждому статусу (`GROUP BY status`) |

Полный текст гайдлайна через API не отдаётся (объём и лицензия): `serialize`
возвращает метаданные, абстракт, вердикты, оценку, `chunk_count`, `indexed`.

## 9. Персональные исключения врача

CLINICIAN может скрыть опубликованный источник **для себя**:

| Метод | Путь | Контракт |
|---|---|---|
| GET | `/assistant/sources` | `{sources: [...], excluded_guideline_ids: [...]}` — опубликованные источники + личные исключения |
| POST | `/assistant/sources/{guideline_id}/exclude` | `{excluded: true|false}` → `{excluded_guideline_ids}` |

Исключение — запись в `kb_exclusions`, а не удаление: источник остаётся в общей
КБ и у других врачей. Фильтр применяется в retrieval как Qdrant `must_not` по
payload `guideline_id` (включая keyword-fallback), поэтому скрытый источник не
попадает ни в поиск, ни в цитаты этого врача.

## 10. Воспроизводимость

`kb_runs` фиксирует всё, что нужно для повторного/объяснимого прогона:

- `trigger` (`cli` | `schedule`), `started_at`, `finished_at`, `status`;
- `query_plan` — фактические запросы: для PubMed — endpoint и все параметры
  `esearch` (term, окно дат, retmax, sort; `api_key` не пишется), `count` и
  `returned`; для ВОЗ — endpoint и список handle;
- `versions` — `enrichment`, `criteria`, `design`, `appraisal`, параметры
  чанкера, имя и размерность эмбеддера, текст PubMed-запроса, список handle;
- `stats` — `fetched`, `duplicates`, `new`, `updated`, `unchanged`, `candidates`,
  `excluded`, `published`, `failed_documents`; `errors` — список текстовых ошибок.

`kb_works.revision_history` хранит для каждой версии `revision`, `content_hash`,
`fetched_at`. `revision` гайдлайна — `<issued>#<12 символов sha256 текста>`,
поэтому изменение текста документа на стороне IRIS обнаруживается как новая
версия.

Граница воспроизводимости: прогон с теми же параметрами и версиями даёт тот же
результат **настолько, насколько стабильны внешние базы** — PubMed и IRIS живые,
их выдача и тексты меняются, а внешние ответы не архивируются. Воспроизводимо
то, что у нас: план запроса, версии алгоритмов, хеши содержимого и принятые
решения.

## 11. Эксплуатация

**Расписание.** `serve` делает прогон сразу при старте и далее каждые
`CC_ENRICH_INTERVAL_HOURS` часов (по умолчанию 24). Параллельность исключена
блокировкой Postgres: `pg_try_advisory_lock(hashtext('kb-enrichment'))` — если
блокировка занята, прогон пропускается с сообщением, а не запускается вторым
процессом. Ошибка одного прогона логируется и не роняет сервис.

**Переменные окружения** (`EnrichmentConfig.from_env`, только для `kb-enrichment`):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `CC_ENRICH_PUBMED_ENABLED` | `true` | опрашивать PubMed |
| `CC_ENRICH_PUBMED_QUERY` | `config.DEFAULT_QUERY` | запрос `esearch` |
| `CC_ENRICH_PUBMED_DAYS` | `30` | окно дат публикации |
| `CC_ENRICH_PUBMED_RETMAX` | `100` | лимит PMID за прогон (не более 500) |
| `CC_ENRICH_PUBMED_EMAIL` | пусто | контакт для NCBI (желателен) |
| `CC_ENRICH_PUBMED_API_KEY` | пусто | ключ NCBI (иначе 3 запроса/с) |
| `CC_ENRICH_PUBMED_BASE_URL` | `https://eutils.ncbi.nlm.nih.gov/entrez/eutils` | endpoint |
| `CC_ENRICH_WHO_ENABLED` | `true` | опрашивать IRIS |
| `CC_ENRICH_WHO_BASE_URL` | `https://iris.who.int/server/api` | endpoint |
| `CC_ENRICH_WHO_MAX_TEXT_CHARS` | `4000000` | отсечка размера текста |
| `CC_ENRICH_AUTO_PUBLISH_GUIDELINES` | `true` | автопубликация гайдлайнов с подтверждённой лицензией |
| `CC_ENRICH_OFFLINE` | `false` | не ходить в сеть (прогон вернёт `failed` с пояснением в `errors`) |
| `CC_ENRICH_TIMEOUT` | `60` | таймаут HTTP, секунды |
| `CC_ENRICH_INTERVAL_HOURS` | `24` | интервал `serve` |
| `CC_ENRICH_RUN_ON_START` | `true` | `false` — первый прогон `serve` только через интервал, не при старте |
| `CC_ENRICH_CHUNK_CHARS` | `1800` | размер чанка |
| `CC_ENRICH_CHUNK_OVERLAP` | `120` | перекрытие чанков |

`CC_DATABASE_URL` и `CC_QDRANT_URL` — общие с API (compose задаёт их сервису).

**CLI** (`python -m app.enrichment <команда>`, запуск из `api/` или через
`docker compose exec kb-enrichment`):

| Команда | Что делает |
|---|---|
| `run [--dry-run] [--source all|pubmed|who] [--json]` | один прогон; `--dry-run` ничего не пишет в БД/Qdrant |
| `serve` | цикл по интервалу с advisory-lock |
| `review list [--status candidate] [--kind article|guideline] [--limit N]` | очередь ревью |
| `review show <id>` | карточка источника |
| `review approve <id>` | приёмка (CLI-актор без `approved_by`) |
| `review reject <id> --reason "..."` | отклонение с причиной |
| `runs [--limit N] [--json]` | история прогонов |

Код возврата `run`: 0 при `ok`/`partial`, 1 при `failed`; `review show` — 2,
если источник не найден.

## 12. Тестирование

Подход: в тестах нет обращений в сеть — ответы внешних баз заменены фикстурами;
интеграционные тесты работают с локальными Postgres и Qdrant.

- `api/tests/test_enrichment_domain.py` — дедупликация, классификатор дизайна,
  критерии, AMSTAR 2, сборка чанков: чистые функции, без сети и БД.
- `api/tests/test_enrichment_pubmed.py` — разбор `efetch` XML, план `esearch`,
  обработка ошибок источника; `api/tests/test_enrichment_who.py` — определение
  лицензии, выбор TEXT-bitstream, уникальность белого списка.
- Фикстуры (`api/tests/enrichment_fixtures.py`) собраны по фактическим схемам
  PubMed и IRIS, но тексты в них собственные: сторонние лицензионные материалы
  в тесты не попадают.
- `api/tests/test_enrichment_pipeline.py` — интеграционный: реестр, гейты,
  индексация и воспроизводимость на реальных Postgres и Qdrant (как остальные
  интеграционные тесты API).
- `api/tests/test_kb_admin_api.py` — HTTP-контракты ревью: RBAC, approve/reject,
  фильтр персональных исключений.
- Сеть в тестах не используется; для прогонов без сети есть `CC_ENRICH_OFFLINE=1`
  — источники отключаются, прогон завершается `failed` с явной ошибкой в
  `kb_runs.errors`.

## 13. Разобранные примеры

Значения ниже — фактические константы и параметры реализации (не результаты
прогонов); результат живого запроса зависит от выдачи внешней базы.

### 13.1 Гайдлайн ВОЗ `10665/374250` (mhGAP, 2023)

1. `who.fetch_documents` берёт из белого списка handle `10665/374250`, item UUID
   `d7727881-07ec-485f-95a8-6f2864aee9a9` и запрашивает
   `https://iris.who.int/server/api/core/items/d7727881-07ec-485f-95a8-6f2864aee9a9`.
2. Из `_links.bundles` выбирается бандл `TEXT`, из него — bitstream
   `*.pdf.txt`; если текст больше 4 000 000 символов, документ считается ошибкой
   прогона (без усечения).
3. `detect_license` ищет `CC BY-NC-SA 3.0 IGO` в первых 20 000 символах →
   вердикт `license = met`.
4. `guideline_id = who-10665-374250`, `revision = 2023-11-20#<sha256[:12] текста>`,
   `kind = guideline`, `source = who`, топик чанков `РЕКОМЕНДАЦИИ`.
5. Критерии: `psychiatry_relevance` (заголовок mhGAP + первые 4000 символов),
   `license`, `text_available` (≥ 5000 символов), `recency` (2023 → в пределах
   5 лет), `source_authority = met`. При `CC_ENRICH_AUTO_PUBLISH_GUIDELINES=true`
   и `license = met` документ получает `approved` и индексируется без человека.
6. Если IRIS отдал документ без строки лицензии — `insufficient_info`, автопубликация
   не срабатывает, документ уходит в `candidate` на ревью. Если в тексте
   «All rights reserved»/`© WHO` — `not_met`: документ не индексируется, а
   `approve` возвращает ошибку (нужно письменное разрешение правообладателя).

### 13.2 Запрос PubMed (значения по умолчанию)

`config.DEFAULT_QUERY` (сокращённо, полный текст — в коде):

```
("Depressive Disorder"[MeSH] OR "Depression"[MeSH] OR "Anxiety Disorders"[MeSH]
 OR "Bipolar Disorder"[MeSH] OR "Suicide"[MeSH]
 OR depression[tiab] OR anxiety[tiab] OR bipolar[tiab]
 OR "treatment-resistant depression"[tiab])
AND ("Systematic Review"[pt] OR "Meta-Analysis"[pt])
AND (english[la] OR russian[la]) AND hasabstract
```

При `CC_ENRICH_PUBMED_DAYS=30` и дате прогона `2026-10-21` параметры `esearch`
будут: `db=pubmed`, `datetype=pdat`, `mindate=2026/09/21`, `maxdate=2026/10/21`,
`retmax=100`, `sort=pub_date`, `retmode=json`, `tool=clinical-compass-kb-enrichment`,
`term=<DEFAULT_QUERY>`. Этот план целиком попадает в `kb_runs.query_plan`.

Дальше каждая публикация проходит §5–§7 и, если критерии не нарушены, попадает
в `kb_works` со статусом `candidate` — до approve врача её нет в Qdrant.

## 14. Ограничения

- **Только абстракты PubMed.** Полный текст у издателя не хранится (лицензия),
  поэтому AMSTAR 2 частичен, а `reporting_completeness` оценивает абстракт.
- **Белый список ВОЗ ручной.** Автопоиска по IRIS нет; новый гайдлайн
  добавляется правкой `WHO_HANDLES` и проверкой темы/редакции/лицензии.
- **IRIS без номеров страниц.** Текст приходит без разметки страниц: `locator`
  указывает раздел или диапазон символов, номер страницы не указывается.
- **Ретракции — только из метаданных PubMed.** Внешние источники о ретракции не
  опрашиваются; `retraction = not_checked` не блокирует статью, а требует
  ручной проверки.
- **Нет автоматического обнаружения замещения обзора** более новым SR/MA:
  решение принимает ревьюер. Статус `superseded` в схеме зарезервирован, но
  кодом не выставляется.
- **Один планировщик.** `serve` — один процесс с advisory-lock, не Celery:
  горизонтального масштабирования прогонов нет.
- **`CC_ENRICH_RUN_ON_START=false`** откладывает первый прогон на интервал
  (полезно при рестартах контейнера).
- **Русскоязычная литература не покрыта** отдельным источником: PubMed-фильтр
  допускает `russian[la]`, но eLibrary/РИНЦ не подключены.
- **Europe PMC не интегрирован** (отложено).
- **Лицензия ВОЗ CC BY-NC-SA 3.0 IGO** — некоммерческое использование; продукт
  заявлен как некоммерческий кейс, коммерческое использование потребует
  пересмотра корпуса.
- **Лимиты NCBI**: без API-ключа 3 запроса/с; при исчерпании — ошибки в
  `kb_runs.errors` и статус `partial`.
