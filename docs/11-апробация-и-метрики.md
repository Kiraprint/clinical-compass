## 2. Метрика 1 — быстродействие

Замеры на живом Docker-стеке (`http://127.0.0.1:8090`, hash-эмбеддер, 16 CPU), 2026-10-19.

| Операция | p50, мс | p95, мс | n | NFR-1 (p95 < 300 мс) |
|----------|---------|---------|---|----------------------|
| Старт скрининга + abandon | 28.3 | 31.5 | 15 | ✅ |
| Ответ ИИ-ассистента (`/assistant/ask`, гибридный поиск) | 17.9 | 22.0 | 15 | ✅ |
| Запись дневника | 14.5 | 15.9 | 15 | ✅ |
| Карта пациента (врач, полный отчёт) | 19.8 | 22.9 | 10 | ✅ |
| Журнал аудита (500 записей) | 17.7 | 19.5 | 10 | ✅ |

**Доставка алерта при RED-эскалации:** строки `Escalation` + `Notification` создаются **в той же транзакции**, что и `Assessment`; время от POST `/runs/{id}/finish` до commit измерено в API-тесте `< 1 с` (docs/04 §NFR-2). Push/Web Push — best-effort **после** commit, вне критического пути.

**Оговорка:** замеры с `CC_EMBEDDER=hash` (демо). С bge-m3 на CPU кодирование одного запроса ≈ 2.97 с p50 (docs/07 §5) — для прод-профиля нужен GPU (на RTX 5090 Laptop: 15 мс p50, 779 q/s при batch 32).

## 7. Метрики обогащения КБ (FR-20, docs/15)

Источник данных — `kb_runs`/`kb_works` (GET `/admin/kb/health`, `/admin/kb/runs`),
замеры не требуют отдельного стенда.

| Метрика | Формула / откуда | Ориентир |
|---|---|---|
| Полнота источников | `approved` по `kind`: гайдлайны ВОЗ / статьи | все гайдлайны белого списка с подтверждённой лицензией — `approved` |
| Очередь ревью | `counts.candidate` | не растёт от прогона к прогону (иначе ревьюеры — узкое место) |
| Время до approve | `published_at − created_at` по `kb_works` | ≤ 7 дней |
| Доля автоблокировок | `status=excluded` / `fetched` за прогон | справочно; резкий рост = деградация запроса или критериев |
| Лицензионный гейт | число гайдлайнов `candidate` из-за `license not_met` | 0 после получения разрешений ВОЗ |
| Персональные исключения | `kb_exclusions` / (врачи × approved-источники) | справочно; рост = сигнал о качестве источника |
| Здоровье прогонов | `kb_runs.status` (`ok/partial/failed`), длительность | ≥ 1 успешный прогон в сутки при `CC_ENRICH_INTERVAL_HOURS=24` |

Базовый замер (21.10, smoke): PubMed — `count=198`, забрано 15, 0 ошибок;
ВОЗ — 7 гайдлайнов, 5 автоопубликованы (1297 чанков), 2 заблокированы
лицензией; повторный прогон — `unchanged=22`, `published=0`.


## 8. Метрика «своевременность напоминаний» (FR-24)

Источник — `clinician_reminders` + `notifications` (дедуп по `reminder_id`),
отдельный стенд не нужен: запрос ниже считается на любой инсталляции.

```sql
SELECT
  count(*) FILTER (WHERE status = 'done' AND done_at <= due_at)::float
    / nullif(count(*) FILTER (WHERE status = 'done'), 0) AS on_time_share,
  count(*) FILTER (WHERE status = 'open' AND due_at < now()) AS overdue_open,
  avg(extract(epoch FROM notified_at - due_at))
    FILTER (WHERE notified_at IS NOT NULL) AS delivery_lag_seconds
FROM clinician_reminders;
```

| Метрика | Формула / откуда | Ориентир |
|---|---|---|
| Своевременность | `done_at <= due_at` / все `done` | ≥ 80% — напоминания работают как рабочий список, а не как архив |
| Просроченные открытые | `open` и `due_at < now()` (он же бейдж в UI) | не растёт между неделями |
| Лаг доставки | `notified_at − due_at` (сек) | ≤ `CC_REMINDER_TICK_SECONDS` + время тика; рост = воркер не запущен |
