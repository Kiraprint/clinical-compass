## 2. Метрика 1 — быстродействие

Замеры на живом Docker-стеке (`http://127.0.0.1:8090`, hash-эмбеддер, 16 CPU), 2026-10-19.

| Операция | p50, мс | p95, мс | n | NFR-1 (p95 < 300 мс) |
|----------|---------|---------|---|----------------------|
| Старт скрининга + abandon | 28.3 | 31.5 | 15 | ✅ |
| Ответ ИИ-ассистента (`/assistant/ask`, гибридный поиск) | 17.9 | 22.0 | 15 | ✅ |
| Запись дневника | 14.5 | 15.9 | 15 | ✅ |
| Карта пациента (врач, полный отчёт) | 19.8 | 22.9 | 10 | ✅ |
| Журнал аудита (500 записей) | 17.7 | 19.5 | 10 | ✅ |

**Доставка алерта при RED-эскалации:** строки `Escalation` + `Notification` создаются **в той же транзакции**, что и `Assessment`; время от POST `/runs/{id}/finish` до commit измерено в API-тесте `< 1 с` (docs/04 §NFR-2). Push/Web Push — best-effort **после** commit, вне критического пути.

**Оговорка:** замеры с `CC_EMBEDDER=hash` (демо). С bge-m3 на CPU кодирование одного запроса ≈ 2.97 с p50 (docs/07 §5) — для прод-профиля нужен GPU (на RTX 5090 Laptop: 15 мс p50, 779 q/s при batch 32).

## 3. Метрика 4 — эргономика (число действий)

| Сценарий | Действия пользователя | Примечание |
|----------|----------------------|------------|
| Пациент: регистрация → согласие → первый скрининг | 1 форма (3 поля) + 1 чекбокс-согласие + 1 «Начать» + N ответов + 1 «Завершить» | шкала назначается врачом, выбора нет |
| Пациент: ежедневный чек-ин | 1 вкладка + 3–5 ответов + 1 «Отправить» | вопросы генерируются детерминированно |
| Пациент: запись дневника | 1 вкладка + 1 текст + опц. настроение/сон + 1 «Сохранить» | |
| Врач: вход → RED-пациенты | 1 форма (3 поля, включая 2FA) + 1 фильтр «RED» | фильтр — одна кнопка |
| Врач: карточка → маршрутизация | 1 клик по пациенту → блок «Маршрутизация» в карточке | badge «Обязательно/Желательно» |
| Врач: справка по препарату | 1 вкладка «Ассистент» + 1 вопрос | ответ с цитатами |

Подтверждено e2e-тестами (`e2e/tests/*.spec.ts`, 14 сценариев), которые проходят те же пути через UI.

## 4. Метрика 6 — нагрузка

| Показатель | Значение | Условия |
|------------|----------|---------|
| `/assistant/ask` RPS | 37.7 | hash-эмбеддер, 60 запросов, p50 26 мс / p95 39 мс |
| Qdrant hybrid query | p50 2.1 мс / p95 11.8 мс | 12 чанков (демо-корпус) |
| Узкое место под bge-m3 (CPU) | 0.34 запроса/с на воркер | энкодер запроса, не Qdrant и не API |
| GPU (RTX 5090 Laptop, fp16) | 65.8 q/s (1 запрос), 779 q/s (batch 32) | снимает узкое место |

Вывод: API-слой и Qdrant держат нагрузку с запасом; при переходе на bge-m3 требуется GPU-воркер эмбеддингов (масштабируется горизонтально, stateless).

## 5. Воспроизведение

```sh
# Сценарии §1 (детерминированный движок, без БД)
.venv/bin/python - <<'PY'
import sys; sys.path.insert(0, "core")
from compass.scales import ALL_SCALES
from compass.scoring import score, risk_flags
from compass.triage import triage
from compass.routing import routing_for
scale = ALL_SCALES["PHQ-9"]
answers = {f"q{i}": 0 for i in range(1, 9)} | {"q9": 1}
r = score(scale, answers); fl = risk_flags(scale, answers)
t = triage(r, fl)
print(r.total_score, r.severity, t, routing_for(t, fl, r.severity).category)  # 1 NONE RED REQUIRED
PY

# Замеры §2 — живой стек
docker compose -f infra/docker-compose.yml up -d
# (скрипт замера: см. историю коммита; p50/p95 по 10-15 вызовам на эндпоинт)
```
