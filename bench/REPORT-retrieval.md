## 1. Что измеряется

Путь `AgentFactory.search_kb` — тот же, что обслуживает `/assistant/ask` и
сообщения тредов:

```
запрос (+ LLM-переформулировка уточнения, FR-21)
  → эмбеддер профиля (CC_EMBEDDER)
  → Qdrant: dense / dense+sparse → RrfQuery(k)     [CC_RRF_K, CC_RETRIEVAL_CANDIDATES]
  → кросс-энкодерный реранк пула                    [CC_RERANKER, CC_RERANK_WINDOW]
  → порог «нет релевантного ответа» по профилю      [CC_KB_MIN_SCORE / default]
  → top-5 чанков с цитатами
```

Метрики: **strict Hit@3** (доля запросов, у которых в top-3 есть чанк grade = 2 —
продуктовый смысл цели 90 %), nDCG@3/5/10 (gains 2^g−1), Recall@3/5/10
(relevant = grade ≥ 1), Recall2@3 (по grade = 2), MRR@10; латентность
p50/p95/p99 на запрос (поиск + реранк, без LLM-ответа) и VRAM процесса.

## 2. Данные и золотой набор

**Запросы** — 158 (92 RU + 66 EN): 38 ручных по «хрупким» разделам (устройство
шкал, дозирование и противопоказания, триаж/red line, коморбидность, check-in,
статьи) + 120 сгенерированных по случайным чанкам руководств (детерминизм:
`random.Random(20261024)` в `bench/build_kb_bench.py`).

**Две нарезки одного и того же корпуса** (A/B по размеру чанка, тот же набор
запросов и тот же судья):

| снапшот | чанкер | точек | точек/запрос в пуле | как получен |
|---|---|---|---|---|
| `bench/data/kb_corpus.jsonl` (**before**) | 1800/120 (дефолт кода) | 998 | 20 | выгрузка прод-коллекции `kb` |
| `bench/data/kb_corpus_600.jsonl` (**after**) | **600/120** | **3362 (×3.4)** | 30 | `bench/rechunk_corpus.py --chars 600` |

Снапшот 600 собран **тем же кодом, что прод** (`app.enrichment.index.build_documents`
+ сид `kb_seed`), а не «пересборкой в бенче»: 3342 чанка руководств ВОЗ + 24
чанка сида (7 шкал, 6 препаратов, 2 триажа, 5 статей, 4 карточки КР) —
переносятся как есть, чанкер их не режет.

**Разметка** — градуированная 0/1/2, локальный судья
`Qwen/Qwen3-4B-Instruct-2507` на GPU (`bench/grade_local.py`,
`do_sample=False`, дозапись по запросу — прогон возобновляем). Рубрика:

- **2** — фрагмент прямо отвечает: содержит нужный факт (число пунктов шкалы,
  дозу, критерий, правило red line, рекомендацию);
- **1** — по теме, полезный контекст, без прямого ответа;
- **0** — не по теме. Язык не важен (EN-фрагмент может отвечать на RU-вопрос).

**Исправленный дефект разметки (важно для сравнения с прошлой версией отчёта).**
Судья теперь видит **тело чанка без метаданного заголовка источника** и **целиком**
(`--chunk-chars 2000`, без обрезки). В первой разметке (2026-10-24) заголовок
(«…ВОЗ, редакция… Лицензия… Источник…», ~230 знаков, одинаков у всех чанков
работы) не срезался, а `--chunk-chars 280` обрезал текст: у 1800-знаковых чанков
судья видел ~50 знаков тела и оценивал почти одинаковые заголовки. Это
**завышало** grade-2 (1661 из 11 695) и давало «красивый» Hit@3 0.753 у стека,
который на честной разметке даёт 0.430. Прошлые числа в этом отчёте заменены;
золотой набор пересобран (`bench/data/qrels_1800_full.jsonl`,
`bench/data/qrels_600_full.jsonl`).

Проверка, что новый судья не «не любит длинные чанки»: для 69 пар
«дочерний чанк 600 (grade 2) → родительский чанк 1800» родитель получил
**2 в 59 случаях (86 %)**, 1 — в 7, 0 — в 3. То есть разница между нарезками —
свойство ранжирования, а не артефакт судьи.

**Анти-предвзятость** (`bench/qa_qrels.py`, детерминированные проверки, оба
набора PASS): у каждого запроса есть чанк grade = 2 и grade ≥ 1; дословного
зеркалирования нет (максимальная общая последовательность слов 5 < 8, средний
Jaccard 0.026); у RU-запросов grade-2 чанки на 97 % латиница (поиск проверяет
перевод смысла); доля нулей в пуле 0.49 (1800) / 0.31 (600) — порог 0.25.

## 3. Методика замера

1. `bench/eval_retrieval.py` — матрица in-memory: корпус векторизуется один раз
   на модель (кэш `bench/data/cache/`, ключ — модель + отпечаток снапшота), далее
   по стекам ранжирования, метрики, латентность, VRAM. Один процесс на группу
   моделей (веса не выгружаются).
2. `bench/rechunk_corpus.py` — снапшот другой нарезки **продовым кодом**.
3. `--dump-pools` + `bench/merge_pools.py` — пул кандидатов: объединение top-30
   (600) / top-20 (1800) четырёх стеков по запросу, кап 30. Top-3 любого стека
   всегда внутри пула, поэтому Hit@3 не зависит от глубины пула.
4. `bench/grade_local.py` — разметка пула судьёй (см. §2 о заголовке).
5. `bench/report_table.py` — пересчёт таблицы по сохранённым ранжированиям: после
   переразметки матрицу не нужно перезапускать.
6. `bench/eval_prod_path.py` — валидация победителя на реальном пути
   (`kb.upsert_documents` пачками по 256 + `kb.hybrid_search` с реранкером и
   порогом профиля) в отдельной коллекции Qdrant.
7. GPU: RTX 5090 Laptop 24 ГБ, bf16 (fp16 для Qwen3-Reranker).

| стек | Hit@3 1800 | Hit@3 600 | Δ | nDCG@3 1800 | nDCG@3 600 | Δ |
|---|---|---|---|---|---|---|
| bge-m3 dense | 0.430 | 0.968 | **+0.538** | 0.186 | 0.789 | **+0.603** |
| user-bge-m3 dense | 0.494 | 0.956 | +0.462 | 0.216 | 0.777 | +0.561 |
| bge-m3 dense+sparse | 0.494 | 0.842 | +0.348 | 0.259 | 0.584 | +0.325 |
| qwen3-0.6b dense | 0.424 | 0.848 | +0.424 | 0.197 | 0.612 | +0.415 |
| bge-m3 + rerank-bge d20 | 0.519 | 0.981 | +0.462 | 0.219 | 0.828 | +0.609 |
| hash dense+sparse | 0.177 | 0.222 | +0.045 | 0.100 | 0.141 | +0.041 |

Чанк 600 знаков ≈ 150–250 токенов: он целиком влезает в контекст эмбеддера и в
512 токенов кросс-энкодера, и в top-3 помещаются три **разных** фрагмента, а не
три куска одного раздела. Цена — индекс ×3.4 (998 → 3362 точки; dense 1024 float
≈ 14 МБ + sparse), время полной переиндексации 75 с на GPU, и рост числа
кандидатов на запрос (пул 30).

### 5.4 Окно чанка для реранка (`CC_RERANK_WINDOW`)

На чанках 600 знаков тело почти целиком влезает в 512 токенов CE, поэтому окно
ожидаемо не даёт устойчивого выигрыша:

| стек | Hit@3 голова | Hit@3 окно 700 | nDCG@3 голова | nDCG@3 окно |
|---|---|---|---|---|
| bge-m3 + rerank-bge d20 | 0.968 | **0.981** | 0.825 | **0.828** |
| bge-m3 + rerank-bge d50 | 0.949 | 0.968 | 0.789 | 0.785 |
| qwen3-0.6b + rerank-bge d20 | 0.962 | 0.962 | **0.782** | 0.771 |

Разница ±0.013 (1–2 запроса из 158) — в пределах шума. Правило: **при чанках
≤ 700 знаков `CC_RERANK_WINDOW=0`** (тело и так влезает в 512 токенов CE).
Окно остаётся в коде для длинных чанков; на 1800-знаковых чанках оно **не
замерялось** — при возврате к крупной нарезке его нужно перемерить этим же
прогоном (`--rerank-window 700`).

### 5.5 Реранк: оправдан ли он

На 600-чанках реранк bge d20 даёт **+0.013 Hit@3 и +0.039 nDCG@3** за
+265 мс (33 → 297 мс p50) и +2.5 ГБ VRAM. Решение: **включать только если
nDCG@3 важен**; для продуктовой цели (Hit@3 ≥ 0.90) достаточно `bge-m3 dense`
без реранка — он даёт 0.968 при p50 46 мс. В комбинации «цель + качество
ранжирования» победитель — `bge-m3 + rerank-bge d20` (0.981/0.828).

## 6. Победившая конфигурация и целевые пороги

### 6.1 Конфигурация

```bash
CC_KB_CHUNK_CHARS=600 CC_KB_CHUNK_OVERLAP=120   # переиндексация обязательна
CC_EMBEDDER=bge-m3                              # dense-only, коллекция kb_bge_m3
CC_QDRANT_COLLECTION=kb_bge_m3
CC_RERANKER=BAAI/bge-reranker-v2-m3             # extra `rerank`
CC_RERANK_WINDOW=0                              # окно не нужно при чанках 600
CC_RETRIEVAL_CANDIDATES=20
```

Включение без GPU — через ML-сайдкар: `CC_EMBEDDER=remote-bge-m3`,
`CC_RERANKER=remote` (docs/08 §4.7). Локальные профили (`bge-m3`,
`user-bge-m3`, `qwen3-0.6b`) требуют GPU в процессе API или сайдкара.

### 6.2 Проверка на продовом пути (Qdrant + `kb.hybrid_search`)

Коллекция `kb_eval_600` (3362 точки, 75 с индексации), 158 запросов:

| конфигурация | Hit@3 | Hit@5 | nDCG@3 | MRR@10 | p50, мс | p95, мс |
|---|---|---|---|---|---|---|
| `bge-m3`, реранк off, gate 0.45 | 0.968 | 0.987 | 0.789 | 0.973 | **29** | 47 |
| `bge-m3` + rerank-bge d20 (окно 700), gate 0.45 | **0.981** | **0.987** | **0.827** | **0.987** | 287 | 331 |

Порог «нет релевантного ответа» включён так же, как в проде: `hybrid_search`
применяет дефолт профиля (bge-m3 — 0.45) ко всему пулу ДО реранка и отсечки;
ложных отказов 0 из 158.

Метрики совпали с in-memory матрицей (0.968/0.789 и 0.981/0.828) — матрица не
расходится с кодом прода.

Латентности сняты после прогрева: один warmup-запрос, затем
`torch.cuda.synchronize()` + сброс CUDA peak (`bench/eval_prod_path.py`); время —
`perf_counter` вокруг `hybrid_search`. Холодный первый запрос (загрузка весов)
не измерен; p50/p95 прошлого прогона (33/51 и 297/359) отличаются в пределах
шума нагрузки при идентичных метриках качества.

### 6.3 Что мешает nDCG@3 ≥ 0.90

nDCG@3 = 0.828 при Hit@3 = 0.981: «ответ в тройке» есть почти всегда, но не
всегда на первом месте и не всегда grade-2 вместо grade-1. Остаток —
чувствительность к порядку внутри top-3 (nDCG@3 падает вдвое сильнее за grade-1
на позиции 1, чем за grade-2 на позиции 3). Что осталось непроверенным:

- **мельче 600 знаков** (450/300 с бóльшим overlap) — вероятно, ещё поднимет
  nDCG@3, но удорожает индекс и размывает контекст (фрагмент без окружения);
- **реранкер, обученный на длинных клинических фрагментах** (все проверенные —
  общего домена; DiTy на RU показал 0.404 nDCG@3 на 1800 и не мерился на 600);
- **query expansion** по клиническим синонимам (СДВГ/ADHD, дозы) — не проверялось;
- **гибрид с лексическим каналом** на этой нарезке только вредит (0.842 против
  0.968): sparse-канал тянет вверх дословные совпадения RU→EN-перефраз.

| модель | query-эмбеддинг p50 / p95 | rerank |
|---|---|---|
| bge-m3 (ST dense) | 75 / 130 мс | 11.9 с на 20 кандидатов, 28–31 с на 50 |
| e5-large-instruct | 87 / 125 мс | — |
| user-bge-m3 | 90 / 127 мс | — |
| qwen3-0.6b | 111 / 152 мс | — |
| FRIDA | 419 / 528 мс | — |

Вывод: нейросетевой профиль и реранк на CPU не укладываются в бюджет запроса;
деплой — **ML-сайдкар на GPU** (`CC_ML_URL`, docs/08 §4.7), API остаётся
torch-free. `hash` в контейнере продолжает работать как раньше: без
`CC_RRF_K` запрос в Qdrant — та же форма `FusionQuery(Fusion.RRF)`, что на main
(`test_off_path_is_byte_identical` в `api/tests/test_retrieval_rerank.py`), то
есть выдача hash-профиля не менялась; `k=60` — только явный retrieval-профиль.

## 8. Ограничения

- Pooled-разметка: чанк вне пула считается нерелевантным; все замеряемые стеки
  в пуле своего снапшота. Для Hit@3 глубина пула не важна (top-3 всегда в пуле).
- Судья — LLM (Qwen3-4B-Instruct), не человек: выгрузка для выборочной проверки
  есть (`bench/data/kb_qrels_review.tsv` для набора 1800); согласованность на
  парах «ребёнок/родитель» 86 %.
- Латентности реранк-стеков в таблице 5.1 частично сняты под нагрузкой; чистые
  числа — §6.2 (продовый путь).
- `hash` в in-memory матрице не использует GPU: VRAM 3623 МБ в строке — остаток
  резидентных моделей предыдущих стеков, не его собственный.
- jina-reranker-v2 не замерен (несовместим с transformers 5.x).
- `CC_KB_MIN_SCORE` в продовом замере (§6.2) включён и на золотом наборе дал
  0 отказов из 158 — проверено отсутствие **ложных** отказов, а не точность
  самих отказов. Заведомо нерелевантных запросов (negative set) в наборе нет;
  отдельный negative-набор — следующий шаг для тюнинга порога.

## 9. Как перемерить

```bash
# всё одной командой (снапшот 1800: экспорт → пул → разметка → QA → матрица → таблица)
bash bench/run_retrieval_suite.sh

# A/B по размеру чанка на снапшоте 600
CC_ALLOW_DEMO_SECRETS=true .venv/bin/python bench/rechunk_corpus.py \
    --chars 600 --overlap 120 --out bench/data/kb_corpus_600.jsonl
.venv/bin/python bench/eval_retrieval.py --corpus bench/data/kb_corpus_600.jsonl \
    --stacks bge-m3-dense,qwen3-0.6b-dense,user-bge-m3-dense,bge-m3-dense+sparse \
    --candidates 30 --dump-pools bench/data/pool600_bge.jsonl   # на каждый стек свой файл
.venv/bin/python bench/merge_pools.py bench/data/pool600_*.jsonl --cap 30 \
    --out bench/data/kb_pool_600.jsonl
.venv/bin/python bench/grade_local.py --pool bench/data/kb_pool_600.jsonl \
    --corpus bench/data/kb_corpus_600.jsonl --out bench/data/qrels_600_full.jsonl \
    --per-prompt 15 --batch 6 --chunk-chars 2000
.venv/bin/python bench/qa_qrels.py --qrels bench/data/qrels_600_full.jsonl \
    --corpus bench/data/kb_corpus_600.jsonl
.venv/bin/python bench/eval_retrieval.py --corpus bench/data/kb_corpus_600.jsonl \
    --stacks bge-m3-dense,bge-m3-dense+rerank-bge-d20 --rerank-window 700 \
    --json-out bench/data/eval_600.json
.venv/bin/python bench/report_table.py bench/data/eval_600.json \
    --qrels bench/data/qrels_600_full.jsonl

# продовый путь победителя
CC_ALLOW_DEMO_SECRETS=true CC_EMBEDDER=bge-m3 CC_QDRANT_COLLECTION=kb_eval_600 \
CC_RERANKER=BAAI/bge-reranker-v2-m3 CC_RERANK_WINDOW=700 CC_RETRIEVAL_CANDIDATES=20 \
  .venv/bin/python bench/eval_prod_path.py --profile bge-m3 \
    --corpus bench/data/kb_corpus_600.jsonl --qrels bench/data/qrels_600_full.jsonl \
    --collection kb_eval_600 --json-out bench/data/prod_path_600.json
```
