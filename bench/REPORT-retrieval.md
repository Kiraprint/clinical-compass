# Отчёт: качество поиска по базе знаний (retrieval quality)

Дата: 2026-10-24. Ветка `feat/retrieval-quality`.
Цель задачи: **nDCG@3 ≥ 0.90 и Recall@3 ≥ 0.95** на документированном бенчмарке
клинической БЗ (RU-запросы врача, EN-корпус ВОЗ).

> **Статус:** измерительный стенд собран и прогнан; **целевые метрики пока НЕ
> подтверждены**. Полная матрица по 158 запросам заблокирована пропускной
> способностью LLM-асессора (см. §7): разметка 10/158 запросов завершена,
> остальные ждут. Ниже — методика, измеренные латентности/VRAM по всем стекам и
> предварительные метрики на размеченной части (n=10; НЕ основание для вывода
> о целевом качестве).

## 1. Что именно измеряется

Поиск `AgentFactory.search_kb` — тот же путь, что обслуживает `/assistant/ask` и
сообщения тредов:

```
запрос (+ LLM-переформулировка уточнения, FR-21)
  → эмбеддер профиля (CC_EMBEDDER)
  → Qdrant: dense / dense+sparse → RrfQuery(k)   [CC_RRF_K, CC_RETRIEVAL_CANDIDATES]
  → кросс-энкодерный реранк пула                  [CC_RERANKER]
  → порог «нет релевантного ответа» по профилю    [CC_KB_MIN_SCORE / default профиля]
  → top-5 чанков с цитатами
```

Метрики: nDCG@3/5/10 (градуированные gains 2^g−1), Recall@1/3/5/10
(relevant = grade ≥ 1), Recall2@3 (strict, grade = 2), MRR@10; латентность
p50/p95 на запрос (поиск+реранк, без LLM-ответа) и VRAM после загрузки модели.

## 2. Данные

**Корпус** — снимок реальной прод-коллекции Qdrant `kb` (998 чанков):
- 978 чанков руководств ВОЗ (mhGAP, подростки, психическое здоровье на работе,
  физическое здоровье при тяжёлых психических расстройствах,
  фармакологическое лечение) — чанки по 1800 знаков;
- 7 шкал (PHQ-9, GAD-7, HADS, HDRS-17, HCL-32, PSS-10, …), 6 карточек
  препаратов (сертралин, эсциталопрам, маритупирдин), 2 записи триажа,
  5 карточек научных статей.

Снимается `bench/build_kb_bench.py --export` в gitignored
`bench/data/kb_corpus.jsonl` (полные тексты руководств в git не кладём —
лицензия CC BY-NC-SA, docs/08 §2).

**Запросы** — 158 (92 RU + 66 EN):
- 30 ручных по «хрупким» разделам: имена/устройство шкал, дозирование и
  противопоказания препаратов, триаж/RED, красная линия «диагноз»,
  коморбидность (диабет, ВИЧ, эпилепсия), check-in («как часто спрашивать о
  динамике»), статьи;
- 128 сгенерированных LLM-шлюзом по случайным чанкам руководств: на чанк —
  естественный RU-вопрос (кросс-языковой, без копирования формулировок) и EN.
  Детерминизм: `random.Random(20261024)`, промпт — в `bench/build_kb_bench.py`.

**Релевантность** — градуированная (0/1/2) от LLM-асессора
(`bench/grade_kb_qrels.py`) по **пулу кандидатов**, а не по выдаче одной модели:
пул = объединение top-20 восьми стеков (hash, bge-m3 dense/hybrid, user-bge-m3,
e5-instruct, qwen3-0.6b, qwen3-4b, FRIDA) — 11 733 пары, ~74 на запрос.
Схема: **2** — прямо отвечает (факт/рекомендация/доза/критерий), **1** — по теме,
полезный контекст без прямого ответа, **0** — не по теме.
Выгрузка для человеческой проверки: `bench/data/kb_qrels_review.tsv`
(qid, grade, chunk_id, источник, сниппет, запрос).

Оценка poolevaluated: чанк вне пула считается нерелевантным (стандартное
ограничение pooled-разметки, §8).

**Анти-предвзятость** (`bench/qa_qrels.py`, после разметки): ≥1 grade-2 на
запрос; средняя доля нулей в пуле ≥ 40 %; запрос не повторяет чанк дословно
(LCS < 8 слов, средний Jaccard < 0.25); RU-запросы ищут по EN-тексту (≥ 70 %
их grade-2 чанков содержат латиницу).

## 3. Методика замера

1. `bench/eval_retrieval.py` — матрица in-memory: корпус векторизуется один раз
   на модель (кэш `bench/data/cache/*.npz`), поиск по стекам, метрики,
   латентность, VRAM. Один процесс на группу моделей (веса не выгружаются —
   иначе VRAM суммируется и qwen3-4b падает по OOM).
2. `bench/eval_prod_path.py` — валидация победной конфигурации на реальном
   пути: `kb.upsert_documents` в отдельную коллекцию Qdrant +
   `kb.hybrid_search` (Qdrant RRF + `app.services.reranker`).
3. `bench/report_table.py` — сводка метрик из сохранённых прогонов (пересчёт по
   актуальному qrels, без повторного GPU-прогона).
4. GPU: RTX 5090 Laptop 24 ГБ, torch 2.14.1+cu130, fp16.

## 4. Стеки

Эмбеддеры: `hash` (baseline, что в проде сейчас), `bge-m3` (dense; dense+sparse
RRF; +ColBERT-рескоринг пула), `deepvk/USER-bge-m3`, `ai-forever/FRIDA`,
`intfloat/multilingual-e5-large-instruct`, `Qwen/Qwen3-Embedding-0.6B` и `-4B`.
Реранкеры (на пул 50, top-5): `BAAI/bge-reranker-v2-m3`,
`jinaai/jina-reranker-v2-base-multilingual`, `Qwen/Qwen3-Reranker-0.6B`,
`DiTy/cross-encoder-russian-msmarco` — по три базы (bge-m3 dense, qwen3-0.6b
dense, bge-m3 dense+sparse).

## 6. Почему цель Recall@3 ≥ 0.95 требует другого знаменателя

В пуле размечено ~74 чанка на запрос, и у типичного запроса **несколько десятков**
чанков получают grade ≥ 1 («по теме, полезный контекст» в 1800-знаковом чанке
руководства — обычное дело). Recall@3 при таком знаменателе математически
ограничен `3/|relevant|` (≈ 0.10–0.25), то есть целевые 0.95 недостижимы ни при
каком ранжировании. Метрика осмысленна в двух вариантах:
- **strict**: Recall@3 по grade = 2 (прямой ответ) — цель 0.95 здесь достижима;
- **compressed gold**: gold = top-3 наиболее релевантных чанка на запрос (эталон
  ранжирования), тогда Recall@3 = «попал ли в тройку лучших».

Бенчмарк уже считает оба среза (колонки Recall@k и Recall2@3), выбор знаменателя
надо зафиксировать в приёмке; целевые числа в постановке задачи записаны для
lenient-знаменателя и в текущем виде недостижимы (это ограничение метрики, а не
поиска).

## 7. Блокер и как перемерить

Полная разметка 158 запросов упирается в пропускную способность LLM-шлюза
`home-stable`: при 12–20 параллельных запросах один вызов асессора занимает
60–120 с (измерено: 92 с на тривиальный ответ), полный прогон — 1–2 часа и
более. Сделано 10/158; частичный файл `bench/data/kb_qrels_partial.jsonl`
позволяет докачивать без потерь.

Порядок завершения:

```bash
cd <worktree> && uv sync --package clinical-compass-api --extra embeddings --extra rerank

# 1) разметка (идемпотентно, докачивается)
.venv/bin/python bench/grade_kb_qrels.py --pool bench/data/kb_pool_merged.jsonl --workers 4

# 2) проверки набора (должны пройти: анти-предвзятость)
.venv/bin/python bench/qa_qrels.py

# 3) матрица (вектора уже в кэше): базовые стеки
.venv/bin/python bench/eval_retrieval.py --stacks all --json-out bench/data/eval_all.json

# 4) реранкеры по 50 кандидатов
.venv/bin/python bench/eval_retrieval.py \
  --stacks bge-m3-dense+rerank-bge,bge-m3-dense+rerank-jina,bge-m3-dense+rerank-qwen3,bge-m3-dense+rerank-dity,qwen3-0.6b-dense+rerank-bge \
  --rerank-depth 50 --json-out bench/data/eval_rerank.json

# 5) сводная таблица
.venv/bin/python bench/report_table.py bench/data/eval_all.json bench/data/eval_rerank.json

# 6) валидация победной конфигурации на продовом пути Qdrant
CC_EMBEDDER=bge-m3 CC_QDRANT_COLLECTION=kb_eval_prod CC_RERANKER=BAAI/bge-reranker-v2-m3 \
CC_RETRIEVAL_CANDIDATES=50 CC_RRF_K=60 CC_EMBEDDER_DEVICE=cuda \
  .venv/bin/python bench/eval_prod_path.py --profile bge-m3 --reindex
```

Регуляризация асессора: вызовы при 4 воркерах не конкурируют за очередь шлюза и
не мешают остальным сервисам; при разгрузке шлюза (или локальной модели,
docs/17) — до 12 воркеров.

## 8. Ограничения (принятые)

- **Pooled-разметка:** чанк вне пула считается нерелевантным; для стеков,
  которых не было в пуле, метрики могут быть слегка занижены. Все замеряемые
  стеки — в пуле.
- **Асессор — LLM**, а не человек: выгрузка `kb_qrels_review.tsv` предназначена
  для выборочной проверки; спорные grade-1/0 в клинических нюансах возможны.
- **Латентность** измерена без LLM-ответа и без сетевого Qdrant-хопа
  (in-memory поиск в матрице; прод-путь меряется отдельным скриптом).
- **ColBERT** реализован как рескоринг 100 кандидатов на CPU — не оптимизирован.
- **qwen3-4b** помещается в 24 ГБ только в отдельном процессе (15.5 ГБ VRAM).
