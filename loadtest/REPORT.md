# Нагрузочные и ML-метрики Clinical Compass

> **Числа предыдущих прогонов удалены — они невоспроизводимы.** В старом
> отчёте не был указан git-коммит, а сырые результаты (`loadtest/results/*.json`)
> не коммитятся (`.gitignore`). Проверить или повторить те цифры нельзя,
> поэтому здесь их нет: новые числа появятся только после реального прогона.
>
> Этот файл генерируется командой `python -m loadtest.report` (её вызывает
> `run_all`) из `loadtest/results/`. Пока прогона нет, файл описывает методику
> и способ перемерить.

## Как перемерить

```bash
# коммит, на котором делается замер (обязательно зафиксировать!)
git rev-parse --short HEAD

export CC_LOADTEST_ALLOW=1          # обязательно: provision делает DROP DATABASE
export CC_LOADTEST_DB=compass_loadtest
export CC_LOADTEST_COLLECTION=kb_loadtest

# 1) инфраструктура: Postgres + Qdrant демо-стека (127.0.0.1:5432 / :6333)
docker compose -f infra/docker-compose.yml up -d postgres qdrant

# 2) безопасная проверка целей — без соединений
python -m loadtest.provision --dry-run

# 3) БД: схема, 256 пациентов, 8 врачей, drugs, Qdrant-коллекция
#    (корпус приложения с drug-чанками + bench/data/corpus.jsonl)
python -m loadtest.provision --embedder hash

# 4) полный прогон: API → ML → HTTP → ядро → REPORT.md
python -m loadtest.run_all --embedder hash

# быстрый смоук (меньше уровней/короткие прогоны):
python -m loadtest.run_all --quick --embedder hash
```

Требования: Python 3.12 с зависимостями API; `bench/data/{queries,corpus}.jsonl`
(не коммитится — см. `loadtest/README.md`); интерпретатор процесса API —
`CC_LOADTEST_PYTHON` (по умолчанию текущий `sys.executable`).

Числа зависят от машины и коммита. Сравнивать прогоны можно только на одном
железе, с одинаковыми `--embedder`/`--collection` и зафиксированными
коммитами; для этого в отчёт пишется раздел 0 (провенанс).

## Что содержит сгенерированный отчёт

- **0. Провенанс и воспроизводимость** — git-коммит (короткий) и dirty-флаг,
  дата прогона в MSK, Python, модель CPU и число логических ядер, RAM,
  эмбеддер и device, состояние LLM, БД/коллекция, число чанков, уникальных
  документов, препаратов и пользователей; блок «Как перемерить» с командами
  для этого коммита.
- **1. Стенд и методика** — конфигурация и правила замера (замкнутый контур,
  длительность уровня, прогресс 1 с не учитывается, max RPS = уровень с
  ошибками < 1 %, nearest-rank перцентили).
- **2. Ядро** — ops/s, p50/p95 и число сэмплов (`вызовов × повторов`) для
  скоринга, триажа, чек-инов, деперсонализации, hash-эмбеддера и
  `build_corpus` **по TTL-кешу**; отдельная строка
  `agent.AgentFactory.invoke` — реальный путь агента in-process (поиск Qdrant
  + сборка ответа, LLM выключен) либо `skipped` с причиной.
- **3. ML-метрики поиска** — прямой `hybrid_search` и `POST /assistant/ask`,
  Recall/nDCG/MRR/Hit, grounded/refused, red-line, латентность и число
  запросов в срезе.
- **4. HTTP-нагрузка** — max RPS/flows/s по сценариям, кривые по конкуренции
  с числом запросов на точку, предел пула соединений.
- **5. Выводы**, **6. Ограничения**.

## Предохранитель

Стенд разрушающий (`DROP DATABASE ... WITH (FORCE)`, пересоздание коллекции).
Работать можно только с БД `compass_load*` и коллекцией `kb_load*`, а
разрушающие стадии требуют `CC_LOADTEST_ALLOW=1`; проверка выполняется до
любого соединения. Подробности и отказные сообщения — `loadtest/README.md`.

## Ограничения

- Один процесс API, без nginx/TLS и без внешнего LLM.
- Postgres и Qdrant — локально в Docker; межсерверная сеть не моделируется.
- `hash`-эмбеддер — демо-база; `bge-m3` требует extra `embeddings` и
  переиндексации, его числа из старых прогонов не переносятся.
- Замкнутый контур: p95 на высоких C включает очередь к async-пулу БД.
- Сырые результаты не коммитятся; воспроизводимость обеспечивают команды
  выше и провенанс в отчёте.
